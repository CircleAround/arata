# 0071. ログインした利用者の、パスや ID の総当たり (認可の抜け漏れの探り) を、利用者ごとの時の部品で見る (`user_denied`・`user_id_enumeration`・`user_path_breadth`)

- 日付: 2026-11-17
- 状態: 提案 (文書だけ。実装は確認の後。ADR 0051 の段 1・ADR 0052 の actor の行・ADR 0065 の部分の行を前提にする)

例の値はすべて架空 (利用者は `user:42`、代わりにログインした人は `staff:5`、パスは `/orders/:id`)。

## 背景

### 手口

LLM のエージェントで攻撃を自動化する枠組みが広まっている。Google Threat Intelligence Group と Mandiant の報告
(「ARTEX とその同類: エージェント型攻撃フレームワークの登場」、2026-10-31、日本語版 2026-11-02。
https://cloud.google.com/blog/ja/topics/threat-intelligence/artex-and-friends-enter-agentic-offensive-frameworks) は、次を書いている (2026-11-17 に読んだ。引用は日本語版から):

- 「500 回以上の Web リクエストにわたり、ARTEX は各種 Web ディレクトリで様々なファイル名や拡張子を試行し、HTTP レスポンスコード（`200` または `403`）に基づいて Web サーバーがアクセスを許可する URL エンドポイントをファジング探索しました。」
- 「クエリを実行して保存されたメモを復号し、他のユーザーのメモ添付ファイルの読み取りを試みました。」
- 「書き込み可能な admin フラグを特定して活用し、数分以内に `is_admin=true` を設定したアカウントを作成しました。」

注意: 報告は「IDOR」「認可」という語を使っていない。500 回の試しがログインした状態のものかも書いていない。この ADR は、報告の 3 つの動き
(開けるパスの総当たり、他の利用者のものを読む試み、権限の印の書き換え) を、**ログインした利用者が行った場合**にアプリのログから見る形を決める。
攻撃の事例との対応は `docs/ai/threats/artex-2026-10.md` (別の PR) が持ち、「見えないもの」に「ログインした利用者の中の、パスや ID の総当たりと、その中の成功」を挙げている。
オーナーも手元でこの種の枠組みを使い、ログインした状態から認可の抜け漏れを試す動きを確かめている。

エージェントの試しは、人の操作と比べて次の形になる。

- **速く・広い**: 1 人の利用者 (1 つのセッション) が、ふだん誰も使わない数の種類のパスや API に触る
- **ID を順に回す**: `/orders/101`・`/orders/102`… のように、同じ形のパスで多数の異なる ID を開く。他人の ID はアプリの作りで 403・404・302 (権限が無い旨の転送) になる
- **成功を探す**: 拒否の中に混ざる 200 が目当て。拒否の多い試しの中で 200 が返った ID は、他人のデータを開けた可能性がある
- **ゆっくり分ける**: 1 日の閾値をくぐるように、何日にも分けて少しずつ試せる (オーナーの観点。ADR 0069 の `sign_in_failure` の窓と同じ考え)

### 今の arata で見えないこと

| チェック | 見るもの | この手口が見えない理由 |
|---|---|---|
| `login_bruteforce` | sign-in の失敗 (IP ごと) | ログインそのもの。ログインした後の試しは数えない |
| `probe_paths` | 決まった探索パスへの 403・404 (IP ごと) | パスの一覧に無いパス・ID の付いたパス・200 は数えない |
| `endpoint_abuse` | 設定した画面への、多くの IP からの集中 | 1 人の利用者が多くの画面に触る形ではない。利用者を見ない |
| `source_multi_user`・`user_multi_source` (並行して作っている) | 1 つの送信元の異なる利用者・1 人の利用者の異なる送信元 | 送信元と利用者の組だけで、パスやステータスを見ない |

材料はある。`request_lines` のソースは actor の行 (ADR 0052) から、リクエストごとに利用者の種類と ID (`http_user`) を取れる。
ステータス・パス・メソッドは同じリクエストの行にある。1 行のリクエストの行 (method・path・ip・status・利用者の ID) を出すアプリでは、`json` / `regex` の 1 行の形式でも同じ項目が揃う。

### 前提 (今の仕組みの事実)

- Logs Insights には正規表現の置換が無い。今のパスの正規化 (数字だけ・UUID の区間を `:id`) は Go の側で行い、Insights は生のパスで集計して返している (設計書 2 章)
- `request_lines` のクエリは 1 段目の `stats` を request_id のまとめに使う。`stats` は 3 段まで動くことを確かめてある (ADR 0051 の確かめた結果)
- `request_lines` は ADR 0065 の時の単位の読み方の対象外 (「時の境目をまたぐリクエストが割れる」)。日の頭から読み直す
- Insights の 1 回の結果は 10,000 行まで。超えれば sort の上位だけが残る (`AGGREGATE_TRUNCATED`)
- ストアに置くのは集計だけで、リクエストの行は置かない (ADR 0051 の 3 節)

## 決定

### 0. 全体の形

- 新しいチェックを 3 つ足す。どれも `http_user` を要り (`Needs()`)、利用者ごと (`<kind>:<id>`) に、**その利用者自身の平常帯**と**アプリの平常帯**の**両方**を超えたものだけを報告する

| チェック | 依頼の項目 | 見るもの (1 日) | 重大度 |
|---|---|---|---|
| `user_denied` | 1 (+5 の窓) | 1 人の利用者の、拒否のステータス (既定 401・403) の件数 | medium |
| `user_id_enumeration` | 2・3 (+5 の窓) | 1 人の利用者が、ID を含むパスの型ごとに開いた異なる ID の数 | medium。拒否に混ざって成功があれば **high** (3 節) |
| `user_path_breadth` | 4 | 1 人の利用者が触った、パスの型の異なりの数 | low |

- 決定: **3 つに分ける** (1 つのチェックの理由として持たない)。平常帯の材料・閾値・プロファイルへの入れ方が違い、片付け (ack・snooze) もチェックの単位で効くため。
  同じ利用者の同じ日の指摘は、finding の data の `related` で互いを指す (aratam は同じ利用者を 1 つの見出しにまとめられる)
- 決定: 3 (総当たりの中の成功) は別のチェックにせず、`user_id_enumeration` の重大度の規則にする。材料が 2 と同じ行で、2 を満たさない「成功」は単なるふだんの閲覧だから
- 段 0 の `id_enumeration` (ADR 0051。送信元ごと) とは別に持つ。この ADR はユーザー ID のある段 1 の版。パスの型の規則 (2 節) は段 0 の版も使う
- 判定は規則だけ (ADR 0001・0037)。ログ由来の値 (パス・利用者の ID) は形を絞ってから key に使う

### 1. 認可の失敗の急増 (`user_denied`)

- 数えるのは、actor の行のある (ログインした) リクエストのうち、ステータスが `statuses` (既定 `[401, 403]`) のもの。利用者ごと・UTC の日ごと
- 条件 (すべて): (a) 件数 ≥ `min_count` (既定 30)、(b) その利用者の直近 `baseline_days` (14) 日の日ごとの値の中央値 × `factor` (3) を超える
  (値の無い日は 0。login_bruteforce と同じ形)、(c) **アプリの平常帯**を超える (下)
- **アプリの平常帯**: 直近 `baseline_days` 日の、日ごとの「その日いちばん多かった利用者の値」の中央値 × `app_factor` (既定 2)。
  「ふだんの日の、いちばん多い利用者の 2 倍」。中央値を取るのは、平常帯の期間に一度あった攻撃の日で帯が上がらないため。
  最大を取るのは、上位だけを残す保存 (6 節) でも正しく作れる値だから (p99 は全部の利用者の値が要る)
- 決定 (**404 は既定に入れない**): 404 は正規のリンク切れ・消された記録・古いブックマーク・ブラウザの先読みで日常的に出る。
  入れると、ふだん 404 の多い利用者 (古い一覧を開く人) の平常帯が上がり、403 の急増が埋もれる。404 は次の 2 か所で使う
  - `user_id_enumeration`: ID を含むパスの 404 は「無い ID・他人の ID」の試しとして数える (Rails でよくある `current_user.orders.find(id)` は他人の ID で 404 を返す。認可の拒否が 404 で出るアプリが多い)
  - `user_path_breadth`: 404 になったパスの型の数を根拠に添える (総当たりのパスは多くが 404)
  - 認可の拒否を 404 で返すアプリは、`statuses: [401, 403, 404]` と書ける。そのときの雑音は利用者自身の平常帯が吸う
- 決定 (302): 権限の無い操作を転送 (302・303) で返すアプリがある (「権限がありません」を出して一覧へ戻す)。転送は正規の操作の大半なので、拒否には数えない。
  転送先で拒否を見分ける案 (転送先のパスの glob を設定に書く) も採らない: Rails の Completed の行には転送先が出ず、取り出す行の種類を足すことになる。
  必要になったら、アプリに actor の行と同じ形の「拒否した」行を足してもらう案 (下の「検討した選択肢」) で受ける
- Devise のログの 401 (ADR 0051。ログインの失敗でログに 401 が出て実際の応答は 200 / 422) は、actor の行が無い (ログインしていない) ので、このチェックには入らない

### 2. パスの型 (正規化) と ID の総当たり (`user_id_enumeration`)

#### パスの型の規則 (設定)

ソースの設定に `path_ids` を足す。利用者ごとのチェックと、段 0 の `id_enumeration` が同じ規則を使う。

```yaml
  - id: app_log
    kind: cloudwatch-logs
    log_group: prod-app.log
    format: request_lines
    path_ids:                       # パスの中の ID の位置 (ADR 0071)。書かなければ、パスの型の要るチェックは skip
      segments:                     # 区間 (`/` から次の `/` の前まで) 1 つの全体に当たれば ID とみなす (RE2。^$ は arata が付ける)
        - '[0-9]{1,20}'
        - '[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}'
      templates:                    # 区間の形では分からない ID (slug・名前・ハッシュ) の位置。`:id` の区間は形を問わず ID
        - '/users/:id/profile'
        - '/shops/:id/items/:id'
      max_segments: 8               # これより深いパスは、後ろを `/…` にまとめる
```

- 型を作る順: (1) `templates` に当たれば、その型 (先頭から順に試し、最初に当たったもの)。(2) 当たらなければ、区間ごとに `segments` のどれかに全体が当たれば `:id`、当たらなければそのまま
- **対象 ID** (同じ型で「異なる ID」を数える値) は、型の中の `:id` の区間を `/` でつないだもの。`/shops/7/items/31` なら `7/31`
- クエリと `#` 以降は今と同じく落とす。メールアドレスらしき区間は今と同じく伏せる (設計書 2 章)
- 決定 (**正規化は Insights の中で行う**): 異なる ID の数と型の異なりの数を Insights の中で数えるため (Go に生のパスを返すと、利用者 × 生のパスで行が爆発し、10,000 行の上限に当たる)。
  Insights に置換が無いので、`parse` で区間を `max_segments` 個まで取り出し、区間ごとに `if(<区間> like /^\/(?:<segments>)$/, "/:id", <区間>)` で型を組み立てる
  (`templates` は名前付きキャプチャの選択肢の 1 本の `parse` にし、当たった選択肢の名前で型を決める)。クエリの文の長さ (10,000 文字) に収まるよう、
  `segments` は 8 個・`templates` は 50 個・`max_segments` は 12 までにする (`config check` が確かめる)
- **Go の正規化 (`NormalizePath`) と同じ結果になることをテストで固定する** (同じ規則を 2 か所に持つので、ずれを規則で止める。シミュレーター `cwlogstest.Sim` がこの `fields` を解釈できるようにする)
- 決定 (**ID の値は arata に持ち帰らない**): 対象 ID は Insights の中で異なりを数えるだけに使い、結果の行に出さない。ストアにも報告にも ID の値は無い。
  調べるときは、報告の (利用者・型・日) で Insights を引く (playbook にクエリの例を書く)
- 決定 (**個人に結び付く値がパスにある場合**): 名前・ログイン名・メールアドレスをパスに使うアプリ (`/users/taro/orders`) では、その区間が型に残り、key としてストアと報告に入る。そこで
  - 名前の位置は `templates` に `:id` として書いてもらう (書けば ID と同じく持ち帰らない)。導入の文書と `arata help ai` にそう書く
  - 規則で守れる分は守る: 型の `:id` でない区間が、メールアドレスらしい・数字を含み 16 文字以上・32 文字より長い、のどれかなら `:x` に置き換えて持ち帰る (Go の側。Insights の結果は信用しない入力として扱う)
  - 英字だけの名前は規則で見分けられない。doctor の `path_ids` の行に「1 日に 1 人の利用者しか触らなかった型の数と例 (先頭 5 件。区間は伏せて長さだけ)」を出し、
    `templates` に書き足すべき位置を見つけられるようにする (名前の区間は利用者ごとに違うので、1 人しか触らない型になる)
- 決定: `path_ids` を書かないソースでは、`user_id_enumeration`・`user_path_breadth` を skip し、`coverage.checks_skipped` に `no path_ids` と出す。
  雛形 (`config init`) は `segments` の 2 つを書き出す (ADR 0014。`--diff` で見える)。`templates` は空 (アプリごとに違う)

#### 判定

- 数えるのは、型に `:id` を含むパスへの、ログインしたリクエスト。(利用者, 型, 日) ごとに、異なる対象 ID の数 `ids`、そのうち成功 (`success_statuses`、既定 `[200]`) した異なる ID の数 `ids_ok`、
  拒否 (`denied_statuses`、既定 `[401, 403, 404]`) された異なる ID の数 `ids_denied`
- 条件 (すべて): (a) `ids` ≥ `min_distinct` (既定 50)、(b) その利用者のその型の平常帯 (14 日の中央値 × `factor` 3) を超える、(c) アプリの平常帯 (その型の、日ごとのいちばん多い利用者の `ids` の中央値 × `app_factor` 2) を超える
- メソッドは問わない (GET の読み出しも PUT の書き換えも同じ型に数える)。書き換えの試し (報告の `is_admin` の印) は、メソッドごとの件数を根拠に添える (`methods`)
- `exclude_templates` (glob) に書いた型は数えない。だれでも見られる公開の画面 (`/courses/:id` など) の巡回は、認可の試しではないため
- 1 つの利用者の複数の型が条件を満たしたら、finding は利用者ごとに 1 つ (`templates` に上位 5 つの型と各々の `ids`・`ids_ok`・`ids_denied`)

### 3. 総当たりの中の成功 (重大度 high)

- 決定: 2 の条件を満たした型のうち、`ids_denied` ≥ `high_min_denied` (既定 10) **かつ** `ids_ok` ≥ 1 なら **high** (`reasons` に `success_amid_denied`)。
  「拒否が多く返る ID の範囲の中で、開けた ID がある」は、他人のデータを開けた可能性が最も高い形
- 決定: 拒否が無く成功だけの総当たり (`ids_denied` < `high_min_denied`) は **medium** のまま (`reasons` に `success_only`)。ログからは「自分のデータを大量に開いた」(出力や一括の閲覧) と
  「他人のデータを全部開けた (認可が全く効いていない)」を区別できない。後者は最も重いが、前者が日常にある以上 high にすると誤りの high が続き、
  high の ack を止める (ADR 0068) 運用と合わない。playbook に「success_only は、その型が本人のデータだけを返す作りかを確かめる」と書く。判断を仰ぎたい点 (末尾)
- 成功の数は「異なる ID の数」で数える (同じ ID を何度開いても 1)。どの ID が成功したかは持ち帰らない (2 節)。調べるクエリを playbook に書く
- 決定: high の finding は `user_id_enumeration` の 1 件に、型ごとの内訳と一緒に出す。速報 (ADR 0066) にはしない (8 節)

### 4. 触ったパスの型の多さ (`user_path_breadth`)

- 数えるのは、(利用者, 日) ごとの、触った型の異なりの数 `templates` (ID の有無を問わない)。根拠にステータスごとの型の数 (`templates_ok`・`templates_denied`・`templates_not_found`) を添える
- 条件 (すべて): (a) `templates` ≥ `min_templates` (既定 50)、(b) 利用者の平常帯 (14 日の中央値 × 3) 超え、(c) アプリの平常帯 (日ごとのいちばん多い利用者の値の中央値 × `app_factor` 2) 超え
- 重大度は **low**。型が多いだけでは、新しい機能のリリースの日・管理画面を一通り見る担当・`templates` を書いていない slug の画面 (2 節) でも起きる。
  同じ日に `user_denied` か `user_id_enumeration` があれば `related` で示し、読む人が束で見られるようにする (重大度は上げない。片方が出れば、そちらの重大度で人が動く)
- 決定: 型の多さは**時の部品の延べ**で数える (6 節)。窓 (5 節) は使わない: 延べの値は日をまたいで足すと、ふだん同じ型を毎日使う利用者の値が日数倍になり、意味を失う

### 5. 7 日の窓 (ゆっくりした試し)

`user_denied` と `user_id_enumeration` は、1 日の判定のほかに、**窓での載り方**を持つ (ADR 0069 の `sign_in_failure` の窓と同じ形)。

- 条件 (すべて): 評価する日 D に値が 1 以上あり、D を含む直近 `window` (既定 7d) 日の値の和が `min_count_window` 以上 (既定の案: `user_denied` 100・`user_id_enumeration` 150)、
  値のあった日が `min_days` (既定 3) 日以上、窓の和がその利用者の窓の前の `baseline_days` 日の中央値 × 窓の日数 × `factor` を超え、
  かつアプリの窓の平常帯 (窓の前の `baseline_days` 日の各日を終わりとする 7 日の和の、いちばん多い利用者の値の中央値 × `app_factor`) を超える
- 値は日の値 (6 節で保存したもの) を Go で足し上げる。**Insights のクエリを増やさない**
- `user_id_enumeration` の窓の値は日ごとの `ids` の和で、日をまたいで同じ ID を開けば重ねて数える (日をまたぐ異なりは ID を持ち帰らないと数えられない)。
  正規の利用者が同じ記録を毎日開いても、本人の平常帯が同じ数え方で上がるので吸える
- finding は 1 日の判定と同じ key で、`reasons` に `window` を足す (1 日でも窓でも満たせば 1 件)。閾値は**仮の値で、実データで見直す**
- 限界: `baseline_days` より長く同じ速さで続ける試しは、本人の平常帯に入る。そのときはアプリの平常帯 (いちばん多い利用者の 2 倍) だけが守りになる

### 6. 行の数と費用 (時の部品)

#### クエリ (時ごと。2 本)

| クエリ | 軸 (`request_lines` は 1 段目に request_id のまとめを挟む) | 返す行 | 使うチェック |
|---|---|---|---|
| U1. 利用者の要約 | 2 段目 (時, 利用者, 型) → 3 段目 (時, 利用者) | 利用者ごとに、件数・拒否の件数 (ステータスごと)・型の異なりの数 (ステータスごと)・メソッドごとの件数 | `user_denied`・`user_path_breadth` |
| U2. ID の総当たり | 2 段目 (時, 利用者, 型, 対象 ID) → 3 段目 (時, 利用者, 型) | (利用者, 型) ごとに、`ids`・`ids_ok`・`ids_denied`・メソッドごとの件数 | `user_id_enumeration` |

- 異なりの数は `count_distinct` (概数) を使わず、段を 1 つ足して `count(*)` で正確に数える (ADR 0051 の実装の決定と同じ)。1 行のログの形式では 1 段少ない
- 決定 (**2 本に分ける**): 1 本 (時, 利用者, 型) にまとめると、U1 の値は Go で足せるが、行の数が「その時の利用者 × 型」になる。大きなアプリで上限に当たると、
  sort で残らないのは件数の少ない行 = **広く浅く触る試し (4 節) の行そのもの**になる。U1 は 1 時間の行が利用者の数だけで収まる。U2 は ID のある型だけで、件数の多い行が残る形 (総当たりの行が残る)
- **sort と上限**: U1 は `拒否の件数 + 型の数` の降順、U2 は `ids` の降順で sort し、`limit 10000`。上限に当たった時は今と同じく `truncated` (下限)。落ちるのは値の小さい利用者で、判定の向き (見落とさない側) は崩れない。
  ただしアプリの平常帯は「いちばん多い利用者」なので、上限に当たっても正しい
- **行を Insights の中で絞る** (確かめてから): 3 段目の後に `filter ids >= <part_floor>` を置き、`ids` が `part_floor` (既定 3) 未満の行を返さない。
  `stats` の後の `filter` が動くかは未確認。動かなければ sort と limit だけで受ける (行は多いが上限で止まる)
- U1 の軸 (時, 利用者) は `user_multi_source` の軸と同じ。**`user_multi_source` のクエリと 1 本にまとめられるかを、その担当と決める** (判断を仰ぎたい点)。まとめれば本数は 1 本の増加
- Insights の費用はクエリごとに範囲のログを全部読む量で決まる。2 本を足すと、そのソースの読み取りが 2 本分増える (`request_lines` は今 3 本なので、5 本で約 1.7 倍)。
  新しいチェックをプロファイルに入れなければ流さない。doctor の cost の行が増える分を見積もる (ADR 0028)

#### 時の部品と日の値

- U1・U2 の結果の行を `metric_parts` (ADR 0065) に `query` = `user_summary`・`user_ids` で置く。保持も同じ (`retention.metric_parts`、確定した日から 3 日)
- 日の値は時の部品から作る:

| 値 | 作り方 | 今と同じ考え方か |
|---|---|---|
| 件数 (拒否・ステータスごと・メソッドごと) | 時の和 | 同じ (足せる) |
| 型の異なりの数 (`templates`)・ID の異なりの数 (`ids`・`ids_ok`・`ids_denied`) | **時の異なりの数の和 (延べ)** | 違う。正確な日の異なりではない |

- 決定 (**異なりの数は延べにする**): 日の正確な異なりの数を作るには、ID の値か (利用者, 型) の全部の行を持ち帰る必要があり、2 節 (ID を持ち帰らない) と行の数の上限に反する。
  延べは日の異なりの数以上になる (見落としの向きには間違えない)。総当たりは ID や型を重ねて開かないので延べ ≒ 異なり、正規の利用者は同じものを時をまたいで開くので延べが膨らむが、
  平常帯も同じ延べで作るので比べ方は揃う。報告と playbook では「時ごとの異なりの延べ」と書く
- 日の値の保存 (`metrics`): key は `user_denied`・`user_templates` が `<kind>:<id>`、`user_ids` が `<kind>:<id>|<型>`。
  **下限 (`store_min`。既定 `user_denied` 3・`user_ids` 5・`user_templates` 20) 以上の key だけ**を、日ごとに値の大きい順に `store_top` (既定 200) まで残す (ADR 0051 の 3 節)。
  加えて、日ごとに型ごとの分布の行 (`user_ids_dist`: 利用者の数・最大・p50・p99。p50・p99 はその日の行が上限に当たっていなければ) を 1 行ずつ持つ
- 平常帯の材料: 利用者の平常帯は、残した日の値 (無い日は 0。下限未満は 0 と同じ扱い。閾値は下限より十分大きいので判定は変わらない)。
  アプリの平常帯は、日ごとの最大 (`user_ids_dist` と `user_denied`・`user_templates` の 1 位) から作る
- 窓 (5 節) のために下限を低くしてある。ゆっくりした試しが 1 日に下限を超えなければ窓にも入らない (1 日 3 件の拒否を 7 日、など)。それは見落とすと決める
- 見積もり: 1 日に `store_top` 200 行 × 3 種類 + 分布の行 (型の数) で 1,000 行未満。保持 400 日で 40 万行未満 (ADR 0051 の見積もりと同じ桁)。
  時の部品は U1 が 1 時間に「ログインした利用者の数」行 (sort と上限で最大 10,000)、U2 は `part_floor` を超えた (利用者, 型) の数。3 日分で多くても数十万行

#### `request_lines` を時の単位で読む

- `request_lines` は ADR 0065 の対象外で、日の頭から読み直す。時の部品にするには、**日の境目で既にしている扱いを時に下げる**: 1 段目の前に `fields bin(1h) as <名前>` を置き、
  リクエストを最初の行の時に数え、問い合わせの範囲の後ろに `request.max_duration` (既定 60s) の余白を付け、余白の中で始まったリクエストは捨てる (次の時が数える)。
  境目は時に揃うので、日の境目と同じ理由で二重には数えない (設計書 2-4 の「範囲を分ける境目」)
- 余白の分だけ読み取りが増える (1 時間に 60 秒で約 1.7%)。時を 1 時間より細かくは分けない (上限に当たれば `truncated`)
- 決定: **この扱いは `source_multi_user`・`user_multi_source` と同じ決定にする** (同じ request_lines のソースを同じ時の単位で読むため)。どちらの ADR が先に決めても、
  もう片方は合わせる。設計書 2-4 と 3 章の「request_lines は時の単位にできない」を、この決定が入る版で書き直す
- `collect: hourly` を書かない `request_lines` のソースでは、U1・U2 を日の頭から日の単位で流す (時の部品を作らず、日の値を直に作る。異なりの数は正確になる)。チェックの判定は同じ

### 7. 代わりにログインした操作 (`by=`) は数えない

- actor の行に `by=<kind>:<id>` が付いたリクエストは、**3 つのチェックのどれにも数えない** (ADR 0052: by の付いたリクエストは利用者本人の行動ではない)。U1・U2 の 1 段目の後で除く
- 除いた件数を日ごとに `user_requests_by` (ADR 0052 で既にある) と並べて coverage に出す。代わりにログインして調べる担当の操作が、利用者の総当たりに見えないため
- 決定: by の付いたリクエストを、**実際に操作した人 (`staff:5`) の行動**として数えることは、この ADR ではしない。代わりのログインは調べ物で多くの記録を開くのが仕事で、
  平常帯の作り方が利用者と違う。担当の権限の濫用を見るチェックは、別の ADR の候補にする
- 決定: actor の行の無いリクエスト (ログイン前) も数えない。それは段 0 のチェック (`probe_paths`・段 0 の `id_enumeration`) が送信元ごとに見る

### 8. 速報 (ADR 0066) との関係

- 決定: **アプリ全体の認可の失敗の急増は、arata の速報に入れない**。利用者の側の CloudWatch のアラーム (アプリのメトリクスかログのメトリクスフィルター) が見る予定で、
  arata が同じものを鳴らすと二重になる。arata は利用者ごとに絞り、アラームでは分からない「誰が」を出す
- 決定: 利用者ごとの急増も速報にしない (最初の版)。系列が利用者の数だけあり、時間帯ごとの平常帯 (ADR 0066 の 2 節) を利用者ごとに持つのは重く、少ない件数で揺れる。
  3 つのチェックは daily のプロファイルに入れる。ただし時の部品から当日の途中の値を作れるので、`user_id_enumeration` の high だけを hourly で評価する案は候補に残す
  (high は人がすぐ動く理由になる。入れるなら、途中の日の値で鳴らす規則を別に決める)

### 9. 怪しい IP の一覧 (ADR 0069) とのつなぎ (後の段)

- 決定: **後の段**。`user_id_enumeration` か `user_denied` の finding が出た利用者の、その日の送信元を、一覧に理由 `authz_probe` で載せる
- 送信元は U1・U2 に持たせない (行が利用者 × 送信元に増える)。`source_multi_user` の時の部品 (時, 送信元, 利用者) から、その利用者の行を引く。そのため、その部品ができてから入れる
- 共有の送信元 (会社・携帯の回線) で他の利用者を巻き込む点は ADR 0069 の 6 節と同じ扱い (使い道の側で理由を選ぶ)。理由を分けるのは、ログインした利用者の試しという性質が違うため

### 10. 平常帯が無いとき・新しい利用者

- 新しい利用者 (平常帯の日数が `min_baseline_days` (既定 7) に満たない) は、**本人の平常帯を使わず、アプリの平常帯と下限だけで判定する**。
  作ったばかりのアカウントで試すのが典型なので、新しい利用者を skip しない
- アプリの平常帯の日数が `min_baseline_days` に満たない間 (導入の直後) は、3 つのチェックを skip し、`coverage.notes` に「利用者ごとのチェックは平常帯の蓄積待ち (あと N 日)」を出す
- ID の付いたリクエストが 0 件の run は skip (ADR 0051・0052。既にある仕組み)
- 自動の利用者 (アプリの API を利用者のトークンで叩く連携など) は、allowlist に利用者の種類と ID で書いて除く (形は実装のときに `source_multi_user` とそろえる)

## 報告の形 (案)

- key は `<kind>:<id>` (3 つとも)。主体は ID だけで表す (メールアドレス・氏名は持っていない。ADR 0052)
- data: `user` (`kind`・`id`)・`day`・`reasons` (`above_user_band`・`above_app_band`・`window`・`new_user`・`success_amid_denied`・`success_only`)・
  値と帯 (`value`・`user_band`・`app_band`)・`templates` (`user_id_enumeration` は型ごとの `ids`・`ids_ok`・`ids_denied`・`methods`)・`truncated`・`related`
- 見出しの例: 「user:42 が /orders/:id で 1 日に 480 の異なる ID を開き、412 が拒否・6 が成功 (ふだんの最多の利用者は 12)」
- playbook (ADR 0025) に、Insights で (利用者, 型, 日) を引いて成功した ID とその持ち主を確かめるクエリの例、`success_only` の確かめ方、`templates` の書き足し方を書く
- 攻撃の事例の対応表 (ADR 0058) の `artex-2026-10` の「見えないもの」を、実装の PR で「見えるもの」に移す

## 検討した選択肢

- **送信元 (IP) ごとに見る (段 0 の `id_enumeration` だけで足りるとする)**: アプリを変えずに動くが、ログインした利用者が携帯の回線や会社の回線 (多数の利用者が 1 つの送信元) から試すと、
  他の利用者と混ざって平常帯に埋もれる。エージェントは送信元を変えられるが、セッション (利用者) は試しの間変えにくい。段 1 のある利用者では利用者ごとが強い。両方を持つ
- **1 つのチェック (`user_authz_probe`) にまとめ、理由で分ける**: 通知が 1 件にまとまる。閾値・平常帯・プロファイル・片付けの単位が混ざり、ack が 3 つの見方を一度に黙らせる。却下 (0 節)。まとまりは `related` で示す
- **ID の値 (または ID のハッシュ) を持ち帰り、日の正確な異なりの数と、成功した ID の一覧を作る**: 正確で、報告に「開けた ID」を出せる。行が利用者 × ID になって上限に当たり、
  ID は他人の記録を指す値で、ストアと報告に置く理由が弱い (調べる人は原本の Insights を引ける)。ハッシュも、ID の範囲が狭い (連番) ので元に戻せる。却下 (2・6 節)
- **パスの正規化を Go で行い、Insights からは (利用者, 生のパス) を返す**: 規則が 1 か所で済む。総当たりの 500 個の ID がそのまま 500 行になり、利用者の多いアプリでは 1 時間でも上限に当たる。却下。
  Insights の中で型を作り、Go と同じ結果になることをテストで固定する
- **パスの型を自動で学ぶ (区間の値の種類が多い位置を ID とみなす)**: 設定が要らない。学ぶには生のパスを持ち帰る必要があり、学んだ型がログの値 (攻撃者が作れる) で変わる (ADR 0037)。却下。規則は設定に書く
- **日の正確な異なりを、日の頭からの読み直しで作る (時の部品にしない)**: 異なりの数が正確になる。`source_multi_user` と時の部品をそろえる方針・ADR 0065 の「続きだけ読む」と合わず、
  1 日分の 1 本で行の上限に当たりやすい。`collect: hourly` を書かないソースではこの形になる (6 節)
- **アプリの平常帯を全部の利用者の p99 で取る**: 分布の言葉として自然。全部の利用者の値が要り、上位だけを残す保存・上限で落ちる行と合わない。いちばん多い利用者の中央値なら、上位の行だけで正しく作れる。却下
- **404 を既定の拒否に入れる** (`user_denied`): 認可の拒否を 404 で返すアプリを最初から拾える。正規のリンク切れで平常帯が揺れる。既定では入れず、設定で足せるようにする (1 節)
- **拒否の転送 (302) を数える**: 権限の無い操作を転送で返すアプリが多い。Completed の行に転送先が無く、行の種類を足すことになる。アプリに「拒否した」の 1 行
  (`deny kind=user id=42 reason=forbidden`。actor の行と同じ規則) を足してもらう案のほうが確か。最初の版では採らず、拒否を転送で返すアプリが実際にあれば ADR 0052 の追補で足す
- **成功だけの総当たりも high にする**: 認可が全く効いていない最悪の場合を最も重く出せる。正規の大量の閲覧と区別できず、誤りの high が ack を止める運用 (ADR 0068) を詰まらせる。却下 (3 節)。判断を仰ぎたい点
- **速報に入れる**: 早く知らせられる。アプリ全体はアラームが見て、利用者ごとは系列が多い。却下 (8 節)
- **代わりにログインした操作を、実際に操作した人の行動として数える**: 担当の濫用が見える。調べ物の仕事と区別する平常帯が要り、別の性質のチェック。却下 (7 節。候補に残す)

## 結果 (良い点・引き受けるコスト)

- 良い点: ログインした後の総当たり (エージェントの自動化の典型) を、利用者の ID で報告できる。拒否の中の成功を high として、他人のデータを開けた可能性を最も重く出せる
- 良い点: ID の値・生のパス・送信元をストアに持たない。日の値は上位だけで、行の数は ADR 0051 の見積もりの桁に収まる
- 引き受けるコスト: アプリのログのクエリが 2 本増える (`user_multi_source` とまとめられれば 1 本)。異なりの数は時の延べで、正確な日の異なりではない
- 引き受けるコスト: パスの型の規則を Insights の文と Go の 2 か所に持つ (テストで同じ結果を固定する)。名前をパスに使うアプリは `templates` を書く手間がある
- 引き受けるコスト: 拒否を転送で返すアプリ・成功だけの総当たりは、最初の版では medium 以下か見えない

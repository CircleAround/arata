# 0036. 公開できない情報の検査は、一般的な秘密を gitleaks、禁止語を secrets の一覧と tools/wordscan で行い、CI で常に回す

- 日付: 2026-11-04
- 状態: 採用

## 背景

このリポジトリは公開する可能性があり、顧客の情報を書かない規則 (CLAUDE.md、設計書 1 章) がある。これまでは人とレビューの注意だけで守っていた。
公開の前に一度点検するだけでは、その後の変更で崩れる。規則を CI で機械的に確かめ続けたい。

難しい点が 3 つある。

- 禁止語 (顧客名など) の一覧そのものが公開できない情報なので、リポジトリに置けない
- CI のログは公開時に誰でも読める。一致した語をログに出すと、検査が情報を漏らす
- フォークからの PR と Dependabot の PR には Actions の secrets が渡らない

## 決定

検査を、公開してよい規則と公開できない一覧の 2 つに分ける。

- **一般的な秘密 (`gitleaks` ジョブ)**: gitleaks のバイナリを版と sha256 で固定して使う (`tools/install-gitleaks.sh`)。`.gitleaks.toml` で既定の規則に 12 桁の数字・文書用の範囲の外の IPv4・架空のドメイン以外のメールを足し、架空の値を許可する。secrets が要らないので、すべての実行で全履歴・コミットメッセージ・PR のタイトルと本文を読む
- **禁止語 (`words` ジョブ)**: 一覧は Actions の secrets の `SENSITIVE_PATTERNS` に置き、標準ライブラリだけの `tools/wordscan` で読む。全参照から届く全オブジェクト (削除されたファイル、コミットの作者とメッセージ、タグ) と参照の名前が対象
  - 出力は場所だけ。語・一致した行を出さず、語を含むファイル名は番号に置き換える。regexp のエラーはパターンを含むので行番号だけを返す。これらはテストで固定する
  - ロックファイルのハッシュとコミットの署名は読み飛ばす。短い語が base64 に偶然現れて誤検知するため
- **secrets が読めない実行**: フォークと Dependabot の PR は notice を出して `words` を飛ばす。main への push と定期実行で必ず読む。それ以外で一覧が空なら失敗にする (黙って通さない)
- **GitHub の本文 (`github-text` ジョブ)**: 毎日の定期実行で、PR・Issue・コメント・レビュー・Release の本文を両方の検査にかける。作者のアカウント名は PR の表示として公開時に必ず見えて隠せないので、自動生成のリリースノートの `@login` だけを除いて照合する。手で書いた本文は検出する。Dependabot の PR の本文は上流の変更履歴の転載なので読まない
- **ローカル**: `make scan-sensitive` / `scan-sensitive-history` / `scan-sensitive-github`。一覧はリポジトリの外のファイルから読む

運用 (secrets の登録・更新、必須チェックの設定、見つかったときの対処) は `docs/sensitive-scan.md` に書く。

## 検討した選択肢

- **gitleaks-action を使う**: 組織のリポジトリではライセンスキーが要る。バイナリを直接使えば要らず、チェックサムも自分で固定できる
- **trufflehog を使う**: 実在するかを外部のサービスに問い合わせて確かめる機能が強みだが、ここで欲しいのは架空の値の許可リストと独自の規則で、gitleaks で足りる
- **禁止語も gitleaks の規則にする (実行時に設定を作る)**: 道具は 1 つで済むが、コミットメッセージと参照の名前を読まない。語を出力しないことをテストで固定することもできない
- **`pull_request_target` でフォークの PR にも secrets を渡す**: フォークのコードと同じ実行に secrets を置く事故が起きやすい。フォークの PR は開いた時点で公開なので、マージの前に止めても漏れは防げない。main と定期実行で検出して対処する
- **一覧を暗号化してリポジトリに置く**: 鍵は結局 secrets に要り、語の数などの手がかりも残る

## 結果 (良い点・引き受けるコスト)

- 良い点: 規則が CI で崩れなくなる。ツリーだけでなく履歴と PR の本文も見続ける
- 引き受けるコスト
  - `SENSITIVE_PATTERNS` が未登録だと `words` が失敗する。一覧の原本は secrets から読み戻せないので別に保管する
  - gitleaks は Dependabot の対象外なので、版を手で上げる
  - 同じリポジトリの枝からの PR は、ツールを書き換えて secrets を読める。書き込み権限を持つ人を信頼する前提で、GitHub のマスクと PR のレビューに任せる
  - 履歴に残る試験値 (文書用の範囲の外の IP) は、履歴を書き換えない限り許可リストに残る
  - `.gitleaks.toml` の許可リストは値で書くので、同じ値を新しく書いても検出しない

# 0041. 信用できない入力を解釈する箇所を、Go 標準のファズテストで確かめる

- 日付: 2026-11-09
- 状態: 採用

## 背景

arata と aratam は、攻撃者が書ける文字列を解釈する (ADR 0037)。ログの行と Insights の結果、CloudTrail のイベントの本文、LLM の出力、
それに利用者が書くファイル (設定・allowlist・report.json) である。守りは規則に置いているが、規則が「どんな入力でも」成り立つかは、
固定値のテストでは確かめきれない。ADR 0037 の点検で見つけた抜け (検査のすり抜け、切り詰めでの押し出し) も、人が入力を思い付いて初めて見つかった。

## 決定

- Go 標準のファズテスト (`testing.F`) を、信用できない入力を解釈する箇所に足す。依存は足さない。対象と性質の一覧は `docs/fuzzing.md`
- 性質は「パニックしない」だけにしない。その関数が守る規則を書く。例: Slack に出す文字列に `<` `>`・目に見えない文字・URL・メンションが残らない、
  緊急の finding の行が本文に残る、伏せ字の後にメールアドレスが残らない、公開の判定が条件を外しても公開のまま、など
- 入力は 2 種類を使い分ける。バイト列をそのまま渡すもの (LLM の出力、report.json、YAML、CSV) と、任意の文字列を決まった場所に置くもの
  (ログ由来の値を finding の summary や Insights の行の項目に置く)。後者は、解釈器の入口を越えた先の規則を確かめられる
- seed は既存のテストの値と testdata から取る。架空の値だけを使う (顧客の情報を書かない)
- 見つかった失敗は、`testdata/fuzz/` の入力か意味の分かる seed としてコミットし、本体を直す。ふだんの `go test ./...` が seed と testdata/fuzz を毎回走らせ、回帰を守る
- 探索は `.github/workflows/fuzz.yml` が週 1 回と手動で、対象ごとに 30 秒ずつ回す (`tools/fuzz.sh`)。PR では回さず、必須チェックにしない。
  失敗した入力は成果物に残す。外部の action は足さない (checkout・setup-go・upload-artifact だけ)
- テストは実 AWS・実 LLM・実 Slack に接続しない。収集は偽の API、通知は偽の Sender を使う

### ファズで見つけて直したこと

導入の時点で次が見つかった。1〜7・9・12 は、性質を書いて seed (コードを読んで書いた入力) を走らせた時点で落ちたもの。
8・10・11 は探索 (入力の変異) が見つけたもので、入力を `testdata/fuzz` に残した。

1. **WAF の提案の設定例で検査をすり抜けられた** (aratam): 設定例は複数行なので `oneLine` を通さず、Block の action とコードフェンスの検査を原文に掛けていた。
   ゼロ幅の文字を挟むと (`"Bl<ゼロ幅>ock":`) 検査を通り、Slack と waf-proposals.md にそのまま出た。検査の前に目に見えない文字を除く (改行とタブは残す)
2. **LLM が任意の節を増やして、緊急の finding の行を押し出せた** (aratam、text の書式): インシデント候補と approve の提案は件数の上限が無く、
   切り詰めでも必ず残していたので、大量に返すと本文が 3,800 字を超え (1 万字を超える)、分類の行が全部切られた。
   インシデント候補は 10 件まで (同じ id の重ね書きも 1 つに)、approve の提案は finding 1 件に 1 つにする。収まらないときは緊急の finding と
   取れなかったものを先に並べ直し、インシデント候補と approve の提案は短いとき (800 字まで) だけ必ず残す。`fit` はどの入力でも上限を超えない
3. **期間レポートの report.md で、summary の改行がそのまま出た** (arata): run の report.md は改行を空白にしていたが、期間レポートは抜けていて、
   ログ由来の summary で偽の見出しや指摘の行を作れた (Slack の本文にもなる)
4. **期間レポートの text の通知に、目に見えない文字が残った** (aratam): report.md を整形して送る経路だけ `oneLine` を通らなかった。行ごとに除く
5. **Insights の結果の `NaN`・`Inf`・負の数を件数として読んだ** (arata): `fmt.Sscan` はこれらを数として読む。metric の値になると JSON に書けず、
   その run の保存が失敗する。0 として扱う
6. **長さの設定の日数が桁あふれした** (arata・aratam): `213504d` が 25 分になった。time.Duration に収まらない日数はエラーにする
7. **解釈できなかった行の例に制御文字が残った** (arata): doctor が端末に出す行に、ログのエスケープシーケンスがそのまま入った。伏せ字と一緒に除く
8. **壊れた形のセッション ARN からロールの ARN を作った** (arata): `arn:aws:sts::assumed-role/x` (アカウントの欄が無い) を
   `arn:aws:iam::arn:aws:sts::role/x` にしていた。接頭辞を外してから `:assumed-role/` を探す
9. **知らない種類の userIdentity では、セッションの ARN が主体に残った** (arata): AssumedRole などの決まった種類だけロールに寄せていた。
   AWS が種類を足すと、セッション名 (個人名やメール) が主体に入り、セッションごとに新しい主体になる。ARN がセッションの形なら種類に依らず寄せる
10. **allowlist の glob で、UTF-8 として不正なバイト列どうしが一致した** (arata): 不正なバイトは 1 つの置き換え文字として扱われる。
    YAML からは届かないが、承認の照合を曖昧にしないよう、不正な glob はエラーにする
11. **`store: s3://<bucket>/<prefix>//` が通った** (arata): 空の区間の検査が末尾の `/` を外した後だったので、接頭辞が `<prefix>/` になり、
    キーに `//` が入る。外す前に検査する
12. **静かな通知と入力の問題の通知に上限が無かった** (aratam): 名前・プロファイル・`kind`・`generated_at` が極端に長い report.json で、
    本文が 3,800 字を、通知用の text が 300 字を超えた。どの通知も上限で切る

## 検討した選択肢

- **OSS-Fuzz / ClusterFuzzLite で常時回す**: 見送り。外部の action と外部の基盤に依存する (使う action は GitHub 製と scorecard-action だけ、という方針に合わない)。
  対象は小さな解釈器で、短い時間でも性質の破れは見つかる。規模が大きくなったら見直す
- **PR ごとに探索を回して必須チェックにする**: 却下。対象が 20 を超え、1 つ 30 秒でも 10 分以上かかる。結果が乱数に依るので、関係のない PR が落ちる。
  回帰は seed と testdata/fuzz で毎回確かめられる
- **性質ベースのテストのライブラリ (rapid など) を足す**: 却下。標準の `testing.F` で足りる (ADR 0019)
- **パニックだけを見る**: 却下。この製品の守りは「解釈した後の出力」に置いているので、パニックが無いだけでは規則の破れを見つけられない。実際、見つかった 12 件にパニックは無い
- **YAML・JSON のライブラリ自体を主な対象にする**: しない。入力として通りはするが、見るのは読めた後の検証 (allowlist の主体の指定、設定の id など)

## 結果

- 良い点: 守りの規則を「どんな入力でも」の形で書いたテストが残り、規則を変える PR はこれを通す必要がある。新しい解釈器を足すときの型ができた
- 引き受けるコスト: 週次のジョブが失敗したら、人が入力を見て直す (手順は `docs/fuzzing.md`)。性質が厳しすぎると誤検知になるので、
  規則の文言 (設定のメンション、案内の `<check>`) を除くなどの調整が要る。通知の切り詰めの決定 (インシデント候補と approve の提案を必ず残す) を、長さの条件付きに変えた
- 既知の限界: 伏せ字は ASCII のメールアドレスの形だけを見る。assumed-role のセッション名はカンマと引用符で切るので、カンマを含むセッション名は後ろが残る
  (文の中の ARN の並びと見分けられないため。必要になったら別に判断する)

# 0013. 記録の遅延は窓の終わりをずらさず、各ソースが `ingest_delay` だけ前を再走査して拾う

- 日付: 2026-10-21
- 状態: 採用

## 背景

CloudTrail はイベントが記録されて LookupEvents で引けるようになるまで通常 5〜15 分かかる。CloudWatch Logs の取り込みにも数分の遅延がある。
これまでの `run` の窓は `[From, now)` で、次回の From は前回の WindowTo (設計書 3 章の追いつき)。そのため
**前回の窓の末尾数分に起きて遅れて記録されたイベントは、前回にも今回にも入らず永久に漏れていた**。

本番試用での実例: init (窓の終わり 06:43:40) が 06:42:40 の AssumeRole を取れず、直後の run で初めて見えた
(run の窓がたまたま init の終わりより前から始まっていたので拾えたが、連続する run の間では漏れる)。

## 決定

- ソースごとに `ingest_delay` (ParseDuration 形式) を設定できるようにする。既定は cloudtrail-lookup = 15m (記録の遅延の上限側)、cloudwatch-logs = 5m。`0` で再走査しない
- 窓の終わり To は now のまま記録する (次回の From になる)。**各ソースの収集範囲は `[From - ingest_delay, To)`** とする (前回の窓の末尾を遅延分だけ再走査する)
- 重なり区間 `[From - ingest_delay, From)` の扱い:
  - events: event_id で重複排除済み。最初に収集した run の時刻を `events.collected_at` に残す (再走査で来ても変わらない)
  - イベント型チェック (root_usage / unknown_assume_role / iam_changes): `[From, To)` に加えて、重なり区間のうち **今回の収集で初めて保存したもの** (遅れて届いたもの) を評価する。
    範囲は全ソースの ingest_delay の最大まで。収集済みのものは前回評価済みなので含めない
  - principal_seen: 主体の初出・最終観測 (principals) と新規主体の判定には使う。件数 (`principal_ips.count`) には **数えない**。
    ただし (arn, ip) の行を初めて作るときは、前回まで一度も数えていないことが確かなので重なり区間の件数 (`rescan_count`) も足す
  - metrics: 日の頭から引き直して置き換える (ADR 0009) ので二重計上にならない。再走査が日をまたぐと前日分も丸 1 日で置き換わる。アプリ層チェックの評価は日単位なので窓は広げない
- recurred の境界は **再走査を含まない本来の From** (`last_seen < From`) のまま。チェックが評価する重なり区間のイベントは今回初めて届いたものだけなので、
  前回の run で観測した事象 (last_seen = 前回の実行時刻 ≥ From) が再走査で recurred になることは無い。重なり区間に遅れて届いたイベントで、
  前回より前に沈んでいた事象が再び現れた場合は正しく recurred になる
- init のチャンクは再走査しない。init は取り込み済みの過去の日を古い順に続けて引くので、チャンクの境目で遅れて記録されるものは無い。
  窓の終わり (init の実行時刻) 側は、次の run の再走査が拾う。`collect` (窓を直接指定する手動収集) も再走査しない

## 検討した選択肢

- **To を now - ingest_delay にずらす** (窓全体を遅延分だけ過去にずらす): 重なりが無く単純で、events / principal_seen の扱いも変わらない。
  しかし hourly の検知が常に 15 分遅れ、窓の最新 15 分は (記録済みのものも含めて) 次の run まで見ない。ルート利用や既知外の AssumeRole は
  早く知りたい事象で、記録済みのものまで待たせる理由が無い。再走査なら最新分も一応見て、遅れた分は次回拾える。却下
- **重なり区間を素朴に再評価する** (イベント型チェックの窓を `[From - delay, To)` に広げるだけ): 前回報告済みのイベントが毎回評価に戻り、
  件数 (`count`) が水増しされ、人が resolve した事象が次の run で new として再報告される。却下 (collected_at で今回届いた分だけに絞る)
- **principal_seen の件数を重なり区間も足す**: 再走査の度に重なり分が二重に足される。LookupEvents の全イベントは保存しないので
  event_id 単位で数え済みかを判定することもできない。件数は判定に使わない (ADR 0011) ので、二重にしない側 (過少になり得る) を採る
- **principal_seen の件数から重なり区間を完全に除く**: 重なり区間でだけ見えた (arn, ip) が count 0 になり、new_principal の `count: 0` が読み手を混乱させる。
  行を初めて作るときだけ足す形にした
- **recurred の境界を再走査の始まり (From - delay) にする**: 評価するのが今回届いたイベントだけなので、本来の From で誤発火しない。
  境界を前に広げると、重なり区間内に別 profile の run が観測した事象の扱いが分かりにくくなる。本来の From のまま

## 結果

- 前回の窓の末尾に起きて遅れて記録されたイベントを次の run で検知できる。ingest_delay を超えて遅れたものは引き続き漏れる (CloudTrail の遅延の上限を見て既定 15m)
- 1 回の run の LookupEvents の範囲が 15 分伸びる (hourly で 1.25 倍)。Logs Insights は日の頭から引くので、日をまたぐときだけ前日分が増える
- 窓の From より少し前の時刻の事象がレポートに載ることがある (report の `window` は変えない)
- events に `collected_at` 列を足した (schema 3)。移行前に収集したイベントは「収集済み」として扱う
- raw JSONL には重なり区間の注目イベントが再び追記される (rebuild は event_id で重複排除し、最初の collected_at を残す)
- init の直前に起きて遅れて記録された主体は、次の run で baseline ではなく unknown として入り、new_principal になり得る (実際に init の時点で見えていなかった主体なので、人が確認する)

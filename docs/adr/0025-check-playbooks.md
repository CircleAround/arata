# 0025. チェックごとの対処手順 (playbook) を `docs/ai/playbooks/<check>.md` としてバイナリに埋め込み、全チェックに必須にする

- 日付: 2026-11-03
- 状態: 採用 (ADR 0012 の `arata help ai` にトピックを足す)

## 背景

目的は「セキュリティの観点から素早く的確な助言」。これまでの `arata help ai report` は report.json の読み方と分類の基準までで、
finding が出たときに「何をどの順に確かめ、どこで正規 / 要対応を分け、何をすればよいか」はチェックごとに LLM が考えていた。
そのため助言の質が LLM と実行ごとにぶれ、確かめる場所 (arata のコマンド、AWS のコンソールと CLI) が抜けたり、封じ込めの操作を LLM が自分で行うように書いたりする恐れがあった。

aratam (ADR 0018) は LLM の system に文書を入れて要約させる。並行して、利用者の事情 (アプリの構成・正規の送信元など) を渡す context_file を足している。
汎用の手順 (arata 側) と利用者の事情 (利用者側) を組み合わせれば、アプリに合わせた助言を決まった手順で書ける。

## 決定

- チェックごとの対処手順を `docs/ai/playbooks/<check>.md` に書き、`docs/ai` の embed に入れる。`arata help ai playbook <check>` で本文、`arata help ai playbook` で一覧 (埋め込んだ playbook の題から作る)。
  `arata help ai` と `arata help ai report`、ルートのヘルプから案内する
- 書式は固定: 題 `# <check>: <内容>`、見出し `この指摘の意味` / `まず確かめること` (番号付きの手順。arata のコマンドを含む) / `判断の分かれ目` / `対処の選択肢` (緊急度順) / `やってはいけないこと`。テストで固定する
- **登録済みのチェックすべてに playbook がある** (逆に、登録されていないチェックの playbook は無い) ことを `internal/checks` のテストで固定する。新しいチェックを足すと playbook が無ければ落ちる
- 封じ込め (認証情報の無効化・セッションの失効・公開の取り消し) と状態の変更 (approve / ack / snooze / resolve) は**人が判断して実行する**。LLM は提案まで (approve と同じ方針)。
  「対処の選択肢」に必ず書く (テストで「人が」を含むことを確かめる)。LLM が自分で行ってよい AWS の操作は読み取りだけ
- 手順は汎用だけ。顧客固有の事情は書かず、利用者の事情 (aratam の context_file など) で補う。例の値は架空 (アカウント ID は 123456789012 / 111122223333)。12 桁の数字とメールアドレスをテストで見張る
- aratam から使えるように、`docs/ai` に `Playbook(check) (string, bool)` と `PlaybookNames()`・`PlaybookSections` を置く (標準ライブラリだけ。aratam の依存の許可リストに `docs/ai` は既にある)。
  aratam の system への埋め込み (その run に出たチェックの分だけ) は context_file の変更の後に行う

## 検討した選択肢

- **Check インターフェースに `Playbook() string` を足し、Go のコードに手順を書く**: 却下。aratam は `internal/checks` に依存してはならない (ADR 0018、`cmd/aratam/deps_test.go`)。
  Markdown の方が書く・読む・レビューするのが楽で、`help ai` の他の文書と同じ扱いにできる
- **`report.md` にチェックごとの節を足す**: 却下。14 チェックで数百行になり、aratam がその run に出たチェックの分だけを system に入れられない (長さの上限)
- **手順を書かず、LLM に毎回考えさせる**: 却下。助言の質がぶれ、確かめる場所の抜けや、封じ込めを LLM が実行するような書き方を防げない
- **利用者ごとの手順 (顧客固有の対処) も同梱する**: 却下。リポジトリは公開する可能性があり、顧客の情報を書かない。利用者の事情は context_file 側

## 結果 (良い点・引き受けるコスト)

- 良い点: 助言が決まった手順に沿う。バイナリと同じ版の手順が顧客環境で読める (ADR 0012)。新しいチェックの手順の書き忘れをテストで防げる
- コスト: チェックの判定や Data の欄を変えたら playbook も直す必要がある (テストは見出しと存在だけを見るので、中身のずれはレビューで防ぐ)。
  AWS のコンソールの表示名や CLI が変わると古くなる (自信の無い操作は書かない方針で抑える)

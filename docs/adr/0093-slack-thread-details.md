# 0093. aratam は 1 通目に一番伝えたいことと概要を、2 通目 (1 通目のスレッドへの返信) に詳細を送る (`slack.details: thread`)

- 日付: 2026-11-28
- 状態: 採用 (開発リードの判断)

## 背景

- aratam の通知は 1 通で、3,800 文字 (Block Kit は blocks 50 個・section 3,000 字) までに切り詰める (`docs/aratam.md` 3-4 章)。
  入らないものは「ほか N 件は `arata review` で確認してください」に縮む。件数は残るが、中身は Slack から見えなくなる
- 利用者ごとのチェック (ADR 0071・0087) のように、1 日に何件も出うるチェックが増えた。件数が増えると、1 通の中で「まず対応」と「確認推奨」が枠を取り合い、
  読む人は長いメッセージの中から大事な指摘を探すことになる
- 利用者の求め: 2 通に分けたい。1 通目には一番伝えたいことと概要を入れる。2 通目は 1 通目のスレッドに、詳細と優先度の低い内容を入れる
- 事実 (今の仕組み):
  - 勧める送り方は bot トークンの方式だけ (ADR 0061)。`chat.postMessage` は投稿の `ts` を返す。スレッドへの返信は、同じ API に `thread_ts` を付けるだけで、scope は `chat:write` のまま足りる
  - Webhook の方式は `ts` を返さないので、スレッドに返信できない (非推奨のまま残っている)
  - 今は「スレッドへの返信・更新・削除はしない。状態を持たない」と決めている (`docs/aratam.md` 4-1 章、ADR 0061 の「今後」)
  - WAF の改善提案は、別の 2 通目として常に通常用に送る (ADR 0024)

## 決定

### 1. 設定

- `slack.details` を足す。値は `inline` (今までどおり 1 通) か `thread` (この ADR の形)。
  書かなければ `inline` (今の設定は変えずに動く)。`aratam config init` と `arata repo init` の雛形は `thread` を書き出す
- `thread` は bot トークンの方式だけで使える。Webhook の方式と `thread` の組は設定エラーにする (返信できないのに、詳細を黙って落とさないため)
- `config check --format json` に値を出す (機械はそこから読む)
- `slack.format` (`blocks`・`text`) のどちらでも使える。分け方は 2 節と同じ

### 2. 何をどちらに入れるか (規則で決める。LLM に任せない)

**1 通目 (親)** には、読む人が最初に知るべきことを入れる。

- メンション・注記・警告、見出し、件数の欄、要約 (LLM か規則)
- 取れていないもの (取れなかったソース・解釈率の警告・スキップ)。「取れなくなった」を「何も起きていない」と取り違えないよう、親に残す
- 「まず対応」(urgent_severity 以上の new / changed / recurred) の項目を、今と同じ形 (1 件ずつ、「→」と id)
- 「確認推奨」は**概要だけ**: グループの見出しと件数を 1 行ずつ (例 `🟠 MFA の無いコンソールユーザー 5 人`)。主体・値・id・「→」は 2 通目に回す
- 末尾の context に「詳細はスレッド」と書く

**2 通目 (スレッドへの返信)** には、詳細と優先度の低いものを入れる。

- 1 通目に入りきらなかった「まず対応」の項目 (あれば先頭に「まず対応 (続き)」として)
- 「確認推奨」の項目を、今と同じ形 (主体・値・id・「→」)
- 情報の件数、本日報告済みの件数、全文と対処手順の案内 (`arata review`・playbook・report.md)

- 2 通目に入れるものが無ければ (確認推奨が 0 件で、まず対応も 1 通目に入りきった)、返信しない
- 長さの上限は 1 通ずつ今と同じ。2 通目が入りきらなければ、続きを同じスレッドに返信する。返信は**3 通まで**で、それでも入らないものは今と同じく「ほか N 件は `arata review` で確認してください」に縮める
- メンションは 1 通目だけに付ける。返信はチャンネルに出さない (`reply_broadcast` を使わない)
- 緊急用のチャンネルに送るときも、返信は 1 通目と同じチャンネルのスレッドに付ける

### 3. 状態

- 返信に使う `ts` は、同じ run の中で 1 通目の応答から受け取るだけで、ストアにもファイルにも残さない。run をまたぐ状態は持たない (`docs/aratam.md` 4-1 章の「状態を持たない」を、
  「run をまたぐ状態を持たない」と書き直す)。1 通目の更新・削除はしない (指摘が片付いたときの更新は、この ADR の範囲外)
- `ts` は Slack の応答から取る、信用しない入力として扱う。`^[0-9]{1,16}\.[0-9]{1,16}$` の形だけを受け付け、それ以外なら返信せず失敗にする (ファズを足す)

### 4. 失敗

- 1 通目の送信に失敗したら、今と同じ (返信は送らない)
- 1 通目を送れて返信に失敗したら、終了コード 5 (WAF の提案の 2 通目と同じ)。`.aratam-notified` は書く (1 通目を二重に送らない)。返信だけの送り直しはしない
- 縮退 (LLM の失敗・原文の送信・入力の問題の通知・静かな 1 行) は、1 通に収まる短い通知なので返信しない。
  LLM の失敗で規則だけの Block Kit を送るときは、`thread` の分け方を使う (詳細が規則で組めるため)

### 5. ほかの通知

- WAF の改善提案は、今と同じ別の 2 通目 (常に通常用。ADR 0024)。スレッドにはしない (本文が緊急用のチャンネルのときに、通常用に送る決まりと両立しないため)
- `test-notify` は、`thread` のとき、試しの 1 通目にスレッドの返信を 1 通付ける。返信が届くこと (受け口の転送を含む) を、本番の前に確かめられるようにする
- `--dry-run` は、1 通目と返信を、区切りの行を挟んで標準出力に書く

## 検討した選択肢

- **1 通のまま、切り詰めの順を見直す**: 大事なものを先頭に回すことは今もしている。件数が増えると、詳細が Slack から見えなくなる問題が残る。採らない
- **別のメッセージを 2 通、チャンネルに並べて送る** (スレッドにしない): Webhook でもできるが、チャンネルの流れが 2 倍になり、どの詳細がどのまとめのものかが分からなくなる。採らない
- **指摘ごとに 1 通ずつ返信する** (ADR 0061 の「今後」の案): 件数の多い日に返信が数十になる。Slack の rate limit にも近づく。まとめた形で 3 通までにする
- **既定を `thread` にする**: 今の利用者の通知の形が、版を上げた日に黙って変わる。Webhook の利用者は設定エラーになる。書いた人だけが変わる形にし、雛形で勧める (ADR 0014)
- **`ts` をストアに残し、次の run で更新する**: 片付けの状態とつなげられるが、状態の持ち方 (どの投稿がどの指摘か、ストアとの整合) を決める必要があり、この求めには要らない。範囲外にする

## 結果

- 良い点
  - 1 通目が短くなり、一番伝えたいこと (まず対応・取れていないもの・件数) がチャンネルの流れで読める
  - 詳細を Slack から見られる量が、1 通分から最大 4 通分 (1 通目 + 返信 3 通) に増える
  - scope は `chat:write` のまま。Slack アプリの作り直しは要らない
- 引き受けるコスト
  - 確認推奨の中身は、スレッドを開かないと見えない。概要の 1 行に件数と見出しは残す
  - 返信の失敗という新しい失敗の形が増える (終了コード 5)
  - Webhook の方式では使えない (非推奨の方式に新しい機能を足さない。ADR 0061)
  - 受け口 (Slack の転送の仕組みなど) がスレッドの返信をどう扱うかは、利用者の側の確かめが要る (`test-notify` で確かめる)
- 攻撃の対応表 (ADR 0058): 新しいチェックではないので変えない

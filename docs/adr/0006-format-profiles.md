# 0006. ロググループと形式プロファイルの紐付け、Logs Insights での集計取得

- 日付: 2026-10-21
- 状態: 採用

## 背景

ロググループ名は顧客ごとに違い、中身の形式も言語・フレームワークで変わる (nginx の 1 行ログ、JSON 行ログ、ECS の混在ストリーム)。
形式が合っていないのに気づかず「静かだから平和」と誤解するのが最も危険。

## 決定

- 設定で **ロググループ → 形式プロファイル → 正規化レコード** を紐付ける。プロファイルは組み込み (`nginx_access`, `alb_access`, `wafv2`, `cloudtrail`) と
  汎用 (`json`: フィールド対応表、`regex`: 名前付きキャプチャ) の 2 系統
- チェックは必要な正規化レコードの種類だけを宣言する。該当ソースが無ければ skip し、`coverage.checks_skipped` に出す
- 取得は **Logs Insights の集計クエリ**で行い、生ログは引かない。形式プロファイルの実体はクエリテンプレート集
- 解釈率 (必須フィールドが取れた行 / 総行数) を毎回計測し、閾値未満は `FORMAT_MISMATCH`、急落は `FORMAT_DRIFT` として
  標準エラーの JSON ログ (固定語彙の `code`) と report.json の `coverage` に出す。`doctor` は同じ検査を事前に行う

## 検討した選択肢

- 生ログをダウンロードしてエンジン内でパースする: 転送量と処理時間が大きく、Insights の課金より高くつく。却下
- 顧客ごとにチェックをプラグイン実装する: 共通化の利点が消える。却下 (regex プロファイルで吸収する)

## 結果

- アプリ層のチェックは「設定で指定するパターン集」として全顧客で共通化できる
- Insights のスキャン量課金に上限を設ける仕組み (設計書 11 章の未決事項) が必要
- Insights の正規表現方言に合わない regex は `doctor` で検出する必要がある

# 0010. approve は allowlist.yaml を構造として書き直さず、principals の末尾に行を差し込む

- 日付: 2026-10-21
- 状態: 採用

## 背景

allowlist.yaml は人が承認した既知リストで、git で管理しレビューする (ADR 0004)。人が書いたコメント (なぜ承認したか、契約の期限など)、
エントリの順序、空行による区切りには意味がある。`arata approve` はこのファイルに追記するが、
YAML を読み込んで構造を書き換え、書き出し直すと次のことが起きる (yaml.v3 の Node でも同じ)。

- 空行が消える、コメントの位置がずれる、引用符の種類やフロー形式 (`tags: [deploy]`) が変わる
- git の差分が承認と無関係な行に広がり、レビューで「何を承認したか」が読み取りにくくなる

## 決定

- yaml.v3 の Node で **principals の位置 (行番号) だけを特定**し、元のテキストはバイト単位でそのまま残して、新しいエントリの行を差し込む。
  - principals がブロック形式の列: 最後の要素の後ろ。挿入位置は次のトップレベルのキーの直前で、その直前にある 0 桁目のコメントと空行は次のキーのものとして残す
    (インデントされたコメントは最後の要素のものとして、その下に入れる)
  - `principals: []` / 値なし: その行を `principals:` にし (行末コメントは残す)、直後に差し込む
  - principals が無い / ファイルが無い: 末尾に `principals:` ごと足す
  - 中身のあるフロー形式 (`principals: [{arn: ...}]`): 書き換えずにエラーにする (人がブロック形式に直す)
- 要素のインデントは既存の最初の要素に合わせる。値は yaml.v3 で 1 スカラーずつ直列化して必要なときだけ引用する。アカウント ID は数字だけなので常に引用する
- 書く前に、結果を Parse して「エントリが 1 件増え、末尾が新しい対象である」ことを確かめる。満たさなければ書かない。書き込みは一時ファイル + rename、権限は元のファイルに合わせる
- 同じ対象 (arn / account / arn_pattern) のエントリが既にあれば拒否する。期限の延長やメモの修正は人が直接編集する
- `--commit` は allowlist.yaml だけをパス指定で commit する (`git commit -- <file>`)。他に stage されている変更を巻き込まない
- approve の効果は finding 1 件に閉じない。追記後の allowlist で対象主体が承認済みになる new_principal / unknown_assume_role の finding をすべて resolved にし、
  allowlist.yaml を直接編集した場合も次の evaluate で同じ解消を行う (設計書 6-2。2026-10-21 のリーダーレビューで追加)

## 検討した選択肢

- yaml.v3 の Node を書き換えて Encode し直す: コメントは概ね残るが空行と書式が変わる。却下
- 承認を別ファイル (allowlist.d/approved-YYYYMMDD.yaml) に書く: 書き換えは不要になるが、既知リストが分散してレビューと棚卸しがしにくい。却下
- approve は追記内容を表示するだけにして人が貼り付ける: 安全だが、手で貼る際の誤り (インデント、arn の写し間違い) が増える。却下
- 既存エントリの更新 (expires の延長) も approve で行う: 行の書き換えはコメントとの対応が崩れやすく、意図しない変更をレビューで見落とす。今回は対象外

## 結果

- git の差分は追記した数行だけになり、PR / コミットで承認内容がそのまま読める
- 想定外の書き方 (中身のあるフロー形式) のファイルには追記できない。エラーメッセージでブロック形式への書き換えを促す
- 期限の延長は手作業のまま

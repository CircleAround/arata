# 0004. 「新規」の判定は既知リスト (git 管理) と前回状態の二層で行う

- 日付: 2026-10-21
- 状態: 採用

## 背景

この仕組みの中核は「前回から新しく発生したもの」を報せること。毎回同じ指摘を繰り返すと通知が無視され、
本当に見るべき通知まで埋もれる。設定不備のように対処に時間がかかるものはイベントではなく状態として扱う必要がある。

## 決定

比較基準を 2 種類に分ける。

- **既知リスト (allowlist.yaml)**: 人が承認した正常なもの。承認者・承認日・メモ・任意の有効期限を持ち、**git で管理**する。
  エンジンは読むだけで、`approve` コマンドが書く。承認は人 (または人の承認を得た LLM) が行う
- **前回の観測状態 (ストア)**: 機械が前回見たもの。報告後はここに入るので翌日は鳴らないが、人が承認するまで既知リストには入らず、
  週次の「未承認の新規主体」一覧に残り続ける

初回実行はベースライン作成のみで通知しない (全部が新規になるため)。
対処時間で 4 区分 (即時 / 日次 / 週次 / 四半期) に分け、設定不備は「増えた指摘・解消した指摘」の差分だけを通知する。

## 検討した選択肢

- 既知リストもストア (SQLite) に持つ: 承認の履歴とレビューが git に残らない。顧客間での雛形共有もしにくい。却下
- 「新規」を既知リストだけで判定する: 承認待ちの間、毎日同じ主体が鳴り続ける。却下

## 結果

- 承認の履歴が PR / コミットとして残る
- 既知リストの期限切れ (`expires`) や 90 日未観測の主体の棚卸しをエンジンが提案できる
- 顧客ごとに allowlist.yaml を置くリポジトリ (または場所) を決める必要がある

# 0029. aratam の Slack 通知を Block Kit にし、同じチェックの指摘は規則でまとめ、LLM は要約と「→ 何をするか」だけを書く

- 日付: 2026-11-03
- 状態: 採用

## 背景

aratam の通知は mrkdwn の本文 1 つだった (docs/aratam.md 8 章の未決「まずは本文だけ」)。
試験チャンネルで今の通知と Block Kit の見本を見比べたところ、今の通知は「文章が多くて脳の負荷が高い」、見本は「だいぶ見やすい」と判断された。
今の通知の重さの原因は次のとおり。

- finding 1 件ごとに「重大度・概要・チェック名」と「主要キー · id (初出)」の 2 行、LLM のときはさらに理由文が付く。同じチェックの指摘 (MFA の無いユーザー 5 人など) が 5 件並ぶ
- 件数・期間・取れなかったものが本文の中に埋もれ、最初に何をすべきかが分からない

aratam は判定を LLM に任せない (docs/aratam.md 2 章)。まとめ方・振り分け・件数は規則で決める必要がある。

## 決定

- **Slack への送信を Block Kit (blocks + 通知用の text) にする**。構成は header (重大度の絵文字 + `arata <profile> — <name>`) → fields
  (期間・新規の件数を重大度別・変化/再発・解消/未対応・情報の件数) → 要約 1〜2 文 → 取れていないもの (あれば) → 「まず対応」→「確認推奨」→ context
  (`arata review`・`arata help ai playbook <check>`・WAF の改善提案は別のメッセージ・report.md のパス)
- **「まず対応」= new / changed / recurred のうち `urgent_severity` 以上** (緊急の振り分けと同じ下限)。1 件ずつ、1 行の「→ 何をするか」を付ける。
  **「確認推奨」= それ未満**。info・解消・未対応・報告済みは fields の件数だけ
- **同じチェックの指摘は規則でまとめる**。(チェック、または チェック/key の種類) ごとの対応表 (`internal/notify/blocks.go` の `groupRules`) で、
  見出し・単位・並べる値 (IAM ユーザー名・ARN の末尾・IP・ルール名) を決める。並べる値は 10 個まで。対応表に無いチェックと 1 件だけのグループは 1 件ずつ。
  個人を特定できる値 (メールアドレス・氏名) は並べない
- **LLM (claude-cli / bedrock) が書くのは要約 1〜2 文と「まず対応」の「→」だけ**。契約は `{"summary", "next": [{"finding_id", "action"}]}`。
  「まず対応」の finding_id は規則で決めて system に列挙する。system には対処手順 (playbook) と `context_file` を入れる (3-3 章と同じ)。
  検査: summary が空なら形が不正 (再試行 1 回)。知らない ID・「まず対応」以外の ID・重複は捨て、漏れた項目は規則の「→」で補う。summary は 200 字、action は 80 字で切る
- **provider: none (と LLM が書かなかった項目) は規則で書く**。要約は「まず対応 N 件 (最も重いのは「…」)、確認推奨 M 件。」。
  「→」は playbook の「対処の選択肢」の先頭の項目を、太字とコマンドの括弧を除いて最初の文まで (80 字まで)。条件の括弧 (「封じ込め (侵害の疑い)」) は残す (条件を落とすと過剰な対処を勧めることになる)
- **LLM が失敗したら、規則だけの Block Kit を送る** (原文の mrkdwn ではなく)。先頭に「要約に失敗したため規則で組み立てました」。終了コード 3 は同じ
- **Slack の上限を守る**: blocks 50 個、section の text 3,000 字、header 150 字、fields 10 個・各 2,000 字。入らない項目は後ろから「ほか N 件は `arata review` で確認してください」に縮める
  (「まず対応」を優先して残す。件数は落とさない)
- WAF の改善提案の 2 通目・静かな 1 行・入力の問題の通知も Block Kit にする。提案 1 件は「種類の日本語 + 主な数字」の見出し、「→ 次の一手」、根拠の context の 3 行だけにする。
  規則の長い summary・LLM の何を・なぜ・進め方・設定例は Slack に出さず、入力ディレクトリに `waf-proposals.md` として書き出して (notify の副作用。`--dry-run` では書かない) パスを添える。
  LLM は Slack 用に「→」の 1 行 (`next`) を書く。COUNT のルールの状況は 1 ルール 1 行、一致なしは 1 行にまとめる
- fields は 1 つの欄に「解消 1 件 ・ 未対応 0 件」のように 1 行で書く (ラベルと値を 2 段に分けない)
- **`slack.format: blocks | text` で切り替える** (text は v0.3.0 までの mrkdwn の本文と LLM の契約のまま)。暗黙の既定を持たない (ADR 0014) ので**必須**にし、雛形は `blocks` と明記する。
  v0.3.0 の設定には無いので、エラー文に「v0.4.0 から必須。従来どおりなら `slack.format: text`」と書く
- `notify --dry-run` は `--format text` (既定。人が読む簡易表示) と `--format json` (Webhook に送る payload そのもの) を選べる

## 検討した選択肢

- **mrkdwn の本文のまま行を減らす**: 見出し・件数・区切りを視覚的に分けられず、見本ほど読みやすくならない。却下
- **まとめ方を LLM に任せる**: 指摘が消える経路ができ、件数の正しさを規則で保証できない。aratam の原則 (判定を LLM に任せない) に反する。却下
- **text の契約 (headline・items・incidents・approve_suggestions) を blocks でも使い、reason を「→」に流用する**: reason は「なぜ問題か」で「次に何をするか」ではない。
  使わない分類・incidents・approve を毎回書かせるのも無駄。blocks 用に契約を分けた
- **slack.format の未記載を text (従来どおり) とみなす**: 暗黙の既定になる (ADR 0014)。正式に使っている利用者はまだいないため、必須にして更新時に 1 行足してもらう
- **LLM 失敗時に原文 (mrkdwn) を送る**: 書式が通知ごとに変わり読む負荷が上がる。規則だけの Block Kit で件数・まとめ・「→」は出せるので、そちらにした

## 結果

- 良い点: 最初に「まず対応」が見え、同じチェックの指摘は 1 項目で読める。件数・まとめ方・重大度は規則なので、LLM の出来に左右されない
- 良い点: LLM の出力が短くなり (要約と「→」だけ)、検査も単純になる
- 引き受けるコスト: まとめ方の対応表をチェックの追加に合わせて保守する (無いチェックは 1 件ずつ出るだけで、壊れはしない)
- 引き受けるコスト: 通知には finding の id・主要キーの全部は出ない。詳細は `arata review` と report.md で見る
- 引き受けるコスト: v0.3.0 の設定は `slack.format` を足すまで設定エラーになる
- 引き受けるコスト: aratam が入力ディレクトリに書くファイルが `.aratam-notified` に加えて `waf-proposals.md` になる (書けなくても通知は続ける)

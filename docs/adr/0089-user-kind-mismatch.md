# 0089. ログインした利用者の種類に合わないパスの型への要求を見る (`user_kind_mismatch`)。あわせて、1 つの要求に actor の行が複数あるときの読み方を決める

- 日付: 2026-11-26
- 状態: 採用 (2026-11-26、開発リードの判断。閾値は仮の値で、実データで見直す)

例の値はすべて架空 (種類は `user`・`shop`・`staff`、パスは `/shop/orders/:id`)。

## 背景

### 手口

認証の単位 (scope、arata の言葉では利用者の**種類** `kind`) が複数あるアプリでは、ある種類でログインした利用者が、別の種類の画面 (`/shop/...` や `/staff/...`) を直に開いて、
認可の抜けを探れる。

- 画面のリンクには出ないので、ふだんの利用ではほとんど起きない。起きれば、探りか、アプリのリンクの誤りのどちらか
- アプリが正しく拒めば、401・403 か、自分の種類の画面への 302 が返る。**2xx が返れば、別の種類の画面がその利用者に見えている** (認可の穴)
- 0071 の 3 つのチェックは、1 人の利用者の「量」(拒否の件数・異なる ID の数・型の数) を見る。種類に合わない画面を数回だけ開く探りは、量が小さく、0071 の下限に届かない

### 今の arata で見えないこと

- どの種類の利用者がどの型を使うかを、arata は数えていない。U1 (ADR 0087) は (日, 利用者, 型) で数えるが、種類ごとの型の使い方を平常帯にしない
- 1 つの要求に actor の行が複数あるとき (複数の種類に同時にログインしている)、arata は**最後の形に合った行**の種類と ID だけを使う (ADR 0052、#178 で種類と ID を同じ行の組にした)。
  ほかにどの種類でログインしていたかは捨てている。種類に合わないかを決めるには、**ログインしているすべての種類**が要る
  (`shop` と `user` の両方でログインしている人が `/shop/...` を開くのは、ふつうの利用)

### アプリの側の変更 (この ADR を書いたときに分かっていること)

利用者の ID の行を出すアプリの担当と、actor の行の形を次のように決めた (2026-11-26。本番に入る日は未定)。

- セッションでログインしている scope を、**1 つにつき 1 行ずつ**出す。パスから「その画面の scope」を選ばない
  (前の決まり「その画面の認可に使った単位の行を出す」(`docs/ai/user_id.md`) を置き換える)
- 行の順はアプリが固定する。**代わりに使われる側を先、実際に操作する側を最後**にする
- `by=` は、代わりにログインした印がセッションにあるときだけ、代わりに使われる側の行に付ける。両方のセッションがあるだけでは付けない
- 代わりにログインしたとき、操作する人のセッションも残っていれば、その人の行も別に出る (2 行)
- remember me の cookie だけ (セッションが無い) で別の種類の画面を開いた要求には、行が出ない

### 前提 (今の仕組みの事実)

- U1・U2 は `request_lines` の 1 段目 (request_id のまとめ) の後に 2 段目・3 段目の stats を置き、UTC の 1 日ずつ流す (ADR 0087、`internal/collect/cwlogs/userprobe.go`)
- 1 段目は、actor の行の種類と ID を同じ行の組として `latest` で取る。`by` の組も同じ。`by` の付いた行が 1 つでもあれば、0071 の 3 つのチェックはその要求を除く
- パスの型は `path_ids` (ADR 0071 の 2 節・0087 の 5・6 節) で Insights の中で作る。`path_ids` の無いソースには型が無い
- 0071 の 3 つのチェックは、`sources` が空なら止まっている (既定)。daily のプロファイルに入る

## 決定

### 1. 1 つの要求の actor の行が複数あるときの読み方

- **利用者 (0071 の 3 つのチェックの key) は、最後の形に合った行の組のまま**にする (今の実装)。アプリの決まり (操作する側を最後) により、代わりのログインのときは操作する人、
  そうでないときはアプリが決めた順の最後の種類になる
- **代わりのログイン**: どれかの行に `by=` があれば、その要求は 0071 の 3 つのチェックに数えない (今の実装。0071 の 7 節)。操作する人の行が別にあっても、その人の行動にも数えない
  (0071 の 7 節の「代わりのログインの操作を、操作した人の行動に数えない」のまま)
- **ログインしている種類の組** (`kinds`) を、1 段目で新しく作る。この ADR のチェック (2 節) だけが使う。作り方は 3 節
- 決定 (利用者を「型をふだん使う種類」に寄せない): 種類ごとの型の使い方は平常帯から決まるので、1 段目 (Insights の中) では分からない。
  寄せるには、平常帯を Insights の文に渡す (型 × 種類の一覧で文が長くなる) か、1 段目の行を Go に持ち帰る (行が多すぎる) ことになる。どちらも見合わない
- 引き受けること: 代わりのログインでなく複数の種類にログインしている要求は、最後の種類の利用者に数える。アプリが行の出し方を変えた日から、
  その利用者の平常帯がずれる (移った側は新しい利用者として判定され、報告が増える向き)。`baseline_days` (既定 14 日) で落ち着く。実データで目立てば、新しい ADR で決め直す
- `docs/ai/user_id.md` の行の出し方の決まりを、背景の「アプリの側の変更」のとおりに書き換える (この ADR の PR で)

### 2. 新しいチェック `user_kind_mismatch`

ある日、ログインしている種類の組が S の要求が、型 T に来たとき、S のどの種類も T をふだん使わず、ほかの種類が T をふだん使うなら、**種類に合わない要求**とする。

- **ふだん使う** (種類 k が型 T をふだん使う): 平常帯の日々 (直近 `baseline_days` 日、既定 14) のうち、`min_days` (既定 3) 日以上で、
  **種類 k だけでログインした要求** (S = {k}) が T に来ていて、その要求の異なる利用者の数が `min_users` (既定 2) 以上の日がある
  - 決定 (1 つの種類だけの要求で学ぶ): 複数の種類でログインした要求からは、どの種類が T を使ったか分からない。そこから学ぶと、`shop` と `user` の両方の人が `/shop/...` を開くたびに、
    `user` も `/shop/...` をふだん使うことになり、`user` だけの人の探りが見えなくなる
  - 決定 (2 人以上): 1 人だけが使う型を「ふだん使う」にすると、探りを続けた 1 人が自分で平常帯を作る
- **種類に合わない** (組 S の要求が型 T に来た): S のどの種類も T をふだん使わず、S に無い種類のどれかが T をふだん使う
  - どの種類もふだん使わない型 (新しい画面、あまり使われない画面) は判定しない。新しい画面のたびに報告しないため。量は 0071 の `user_path_breadth` が見る
  - ログインしていない要求 (S が空) は数えない。段 0 のチェック (`probe_paths` など) が送信元ごとに見る
  - `by` の付いた行のある要求は数えない (1 節と同じ)
- **重大度** (その日の (S, T) ごと):
  - **high**: 成功 (`success_statuses`、既定 `[200]`) が 1 件以上。別の種類の画面が見えている
  - **medium**: 成功が無く、要求が `min_requests` (既定 3) 件以上で、異なる利用者が `max_users` (既定 3) 人以下。少ない人が繰り返し開いている
  - 報告しない: 要求が `min_requests` 未満 (1〜2 回は、ブックマーク・別のタブ・片方の scope からのログアウトの後でも起きる)
  - **low**: 成功が無く、異なる利用者が `max_users` より多い。多くの人が同じように開くのは、アプリのリンクの誤りの見込みが高い (アプリの担当に伝える材料)
- finding は (組 S, 型 T) ごとに 1 つ。data に、組 S、型 T、要求の数、異なる利用者の数、ステータスの内訳 (2xx・3xx・4xx・5xx)、T をふだん使う種類を書く
  - 利用者が 1 人なら、その利用者 (種類と ID。1 節の最後の行の組) も書く。2 人以上なら数だけ書く (調べるときは playbook の Insights のクエリで引く)
  - `related`: 同じ利用者・同じ日に 0071 の 3 つのチェックの finding があれば指し合う (利用者が 1 人のときだけ)
- 決定 (平常帯は型の使い方だけ。件数の平常帯は持たない): 種類に合わない要求は、ふだん 0 件が当たり前で、件数の中央値を取っても 0 になる。下限 (`min_requests`) と重大度の規則で決める
- 決定 (アプリの平常帯の蓄積待ち): 平常帯の日々のうち、アプリの記録のある日 (`user_requests` のある日。0071 と同じ) が `min_baseline_days` (既定 7) に満たない間は判定せず、
  `coverage.notes` に残りの日数を出す (0071 の 10 節と同じ)
- 片付け: `exclude_templates` (glob。0071 と同じ形) に書いた型は数えない (どの種類でも開ける共通の画面)。ack は medium と low だけに許す (high は上がる余地が無い。ADR 0068)

### 3. クエリ (U3。1 本。UTC の 1 日ずつ)

```
<1 段目。種類ごとの行の数 rl_k0 … rl_k(n-1) と、その他の種類の行の数 rl_kx を足す>
| filter ispresent(tpl) | filter not ispresent(by_id)
| fields concat(rl_k0, ",", rl_k1, …, ",", rl_kx) as u_kinds
| parse status (成功・3xx・4xx・5xx の印)
| stats count(*) as u_n, count_distinct(user_id) as u_users, latest(user_kind) as u_kind1, latest(user_id) as u_id1,
        count(成功の印) as u_ok, count(3xx の印) as u_3xx, … by day, u_kinds, tpl
| sort u_n desc | limit 10000
```

- 種類の一覧はソースの設定 `request.user_id.kinds` に書く (8 個まで。書かなければこのチェックは skip。暗黙の既定を持たない。ADR 0014)。
  1 段目で、行ごとに `parse user_kind /^(?<rl_m0>kind0)$/` の形で印を作り、`count(rl_m0) as rl_k0` で数える (`count(<項目>)` が値のある行だけを数えることは、ADR 0087 の実装で使っている形)。
  一覧に無い種類は `rl_kx` に数える
- 組 S は Go の側で、`u_kinds` の各数が 1 以上の種類にする (数が 2 以上でも同じ。アプリの決まりは 1 種類 1 行)。`u_kinds` は数字と `,` だけの形で確かめ直す (Insights の結果は信用しない入力)。
  同じ S になる行は足す
- `u_kind1`・`u_id1` は、`u_users` が 1 のときだけ使う (その組の利用者は 1 人なので、`latest` がその人になる)。種類と ID は 0071 と同じ形の規則で確かめ直す
- 行の数: (日, 組, 型)。組は種類の数が少ないので多くない。型はアプリの画面の数 (数百) まで。上限 10,000 に当たる見込みは小さい。当たれば `truncated` (今の規則)
- 日の値 (`metrics`。From は `http_user`): key は `<組>|<型>` (組は種類を `+` でつないだもの。例 `shop+user`)。
  `user_kind_requests`・`user_kind_users`・`user_kind_ok`・`user_kind_3xx`・`user_kind_4xx`・`user_kind_5xx`。1 人のときの利用者は `user_kind_actor` (key に `|<種類>:<ID>` を足し、値は要求の数)
  - 平常帯 (「ふだん使う」) は、S が 1 つの種類の行の `user_kind_requests` と `user_kind_users` から作る。すべての (組, 型) を残す (ストアの下限・上位は置かない。行が少ないため)
- 費用: `request_lines` のクエリが 1 本増える (`yields: http_user` のソースで、0071 を入れた後の 3 本が 4 本)。流すのは、ソースを `checks.user_kind_mismatch.sources` に書いたときだけ (0087 の流し方と同じ)
- 決定 (U1 に足さない): U1 の 3 段目は利用者ごとにまとめるので、(組, 型) の列が残らない。U1 の 2 段目 (日, 利用者, 型) に組を足すと行が利用者 × 型のままで、上限に当たりやすい。別の 1 本にする

### 4. 見えないもの (playbook と threats に書く)

- remember me の cookie だけで別の種類の画面を開いた要求 (actor の行が出ない)。ログインしていない要求として、段 0 のチェックだけが見る
- パスの型が同じで、中身 (パラメータ) で種類を分ける画面。型が同じなので種類に合わないとは言えない
- 種類の一覧 (`kinds`) に書いていない種類だけでログインした要求の組は「その他」にまとまる (その他どうしは区別しない)
- `path_ids` の無いソース (型が無い) と、型を持たないパス

### 5. 設定の形 (案)

```yaml
sources:
  - id: app_log
    request:
      user_id:
        from: app_line
        regex: '…'
        kinds: [user, shop, staff]     # ログインしている種類の組を作る種類 (8 個まで)。書かなければ user_kind_mismatch は skip
checks:
  user_kind_mismatch:
    sources: []                        # 空なら数えない (Logs Insights も流さない)。集計条件
    success_statuses: [200]            # 集計条件
    baseline_days: 14
    min_baseline_days: 7
    min_days: 3                        # 「ふだん使う」: 平常帯の日々のうち、その種類だけの要求が来た日の数の下限
    min_users: 2                       # 「ふだん使う」: その日の異なる利用者の数の下限
    min_requests: 3                    # 報告する要求の数の下限 (仮の値)
    max_users: 3                       # これより多い利用者なら low (仮の値)
    exclude_templates: []
```

## 検討した選択肢

- **種類ごとのパスの接頭辞を設定に書く** (`shop: ['/shop/']`): 却下。アプリの画面の割り当てを利用者が書き写し、画面が増えるたびに直すことになる。
  ユーザーの方針は「セッションから取れる事実で出す。パスで機械的に決めるなら、そもそもパスがあればいい」。使い方は平常帯から学ぶ
- **1 つの要求に 1 行 (アプリがパスから scope を選ぶ)**: 却下 (アプリの担当と決めた)。複数の種類にログインしている人の正規の利用と、1 つの種類の人の探りを、arata が区別できない
- **1 行に複数の種類を並べる** (`actor kind=a id=1 kind=b id=2`): 却下。今の正規表現 (1 組で `$` で終わる) に当たらず、行そのものが読まれない (形に合わずに捨てた数にも入らない)
- **0071 の利用者を「型をふだん使う種類」に寄せる**: 却下 (1 節)
- **すべての種類の利用者に数える** (0071 の 3 つのチェックで、組の全員に 1 回ずつ): 却下。ある種類の利用者に、ほかの種類の画面の要求が数えられ、
  `user_path_breadth` の型の数が膨らむ。この ADR のチェックとも食い違う
- **件数の平常帯で判定する**: 却下 (2 節。ふだん 0 件)

## 結果 (良い点・引き受けるコスト)

- 良い点: 量の小さい、種類をまたぐ探りが見える。別の種類の画面が 2xx で見えている穴は high で出る。アプリの画面の割り当てを書き写さない
- コスト: `request_lines` のクエリが 1 本増える。種類の一覧をソースの設定に書く。アプリの actor の行の出し方の変更 (背景) が本番に入るまで、組は 1 つの種類だけになり、
  複数の種類の人の正規の利用が「種類に合わない」に見えうる (変更が入るまで、このチェックをソースに当てない。導入の手順に書く)
- 0071 の 3 つのチェックの利用者の数え方は変えない (1 節)

## 未確認の点 (実装の前に sandbox で)

- 1 段目の `count(<印>)` を種類の数だけ並べたときの文の長さ (0087 の上限の検査に入れる)
- 数の項目を `concat` に渡したときの文字列の形 (`1`・`0` になるか。小数や空にならないか)
- `count_distinct` の値が、小さい数で正確か (Insights の `count_distinct` は近似。1 と 2 以上の区別に使う)
- 2 段目の by に `u_kinds` と `tpl` を入れたときの行のまとまり

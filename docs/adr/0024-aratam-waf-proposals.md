# 0024. aratam は WAF の修正提案の候補を 2 通目として通常用に送り、LLM には候補だけを渡して書き起こさせる (アプリの事情は `llm.context_file`)

- 日付: 2026-11-03
- 状態: 採用

## 背景

arata の weekly の report.json に、WAF の修正提案の候補 `proposals` (提案と observation) が出るようになった (ADR 0023)。これを Slack の通知に載せたい。
利用者は「汎用の手順を基準にしつつ、アプリの事情に合わせた提案」を求めている (決済画面はリクエストが多いのが仕様、監視の送信元、ログインのパスなど)。

aratam は判定を LLM に任せない (docs/aratam.md 2 章)。候補を作るのは arata の規則で、LLM は書き起こしだけをする (ADR 0023)。
通知にヘッダー・クエリ・Cookie などの生の値や、個人を特定できる値を出さない。

## 決定

- **2 通目として常に通常用の Webhook に送る**。本文が緊急用でも、提案は通常用に送る (proposals だけでは緊急にしない)。
  本文の 3,800 文字の枠を findings と取り合わない。`on_quiet: short` なら静かな 1 行の後に、`silent` なら 2 通目だけを送る (週 1 回の改善提案のまとめ)。
  2 通目の送信に失敗したら終了コード 5。1 通目を送れていれば `.aratam-notified` は書く (本文を二重に送らない)
- 書式: 提案 (kind が observation 以外) を先に、observation を後ろに、count_rule_status を最後に 1 行ずつ。observation は合わせて 10 行までで、残りは「ほか N 件は report.json」
- **数字は規則の行に必ず出す**。種類・段階・概要・根拠 (evidence の主なキー) は report.json の値を aratam が規則で書く。LLM の文字列は「何を・なぜ・進め方・設定例」だけ
- **observation は LLM に渡さない**。LLM の入力は提案の候補だけ (id p1.. を振り、kind・stage・WebACL・ルール・パス・summary・evidence)。
  observation は規則の書式だけで出すので、提案への格上げが構造上起きない (プロンプトでも禁じる)
- LLM の呼び出しは要約とは別の 1 回 (再試行は要約と同じく 1 回まで)。system は出力の契約・縛り・`docs/ai/report.md` の「WAF の修正提案の候補」の節
- 出力の検査: 知らない id・重複は捨てる。漏れた候補は規則の行だけで載る。BLOCK に強める記述 (設定例の Block の action、文中の「BLOCK に切り替える」など) を含む項目は捨てる。
  ``` を含む設定例は例だけ捨てる。文字数の上限 (各文 200 字、設定例 800 字・20 行)。3,800 文字を超えたら設定例 → LLM の文 の順に削る
- 縮退: 提案の書き起こしだけが失敗したら、候補を規則の書式で載せて節の冒頭に注記し、`LLM_PROPOSALS_FAILED` の WARN を出す。終了コードは変えない (本文の要約は成功している)。
  本文の要約が失敗したら書き起こしは呼ばない (LLM が使えない見込みが高い。終了コード 3 のまま)
- **アプリの事情は `llm.context_file`** (Markdown。利用者の環境に置き、リポジトリには置かない)。相対パスは設定ファイルのディレクトリ基準。
  要約と書き起こしの両方の system に「この監査対象の前提」として区切って入れる。重大度・分類の基準・規則より優先しないと明記する。振り分け (緊急用か) は規則なので変わらない。
  provider: none では読まない。無い・読めない・UTF-8 でない・16 KiB を超えるときは設定エラーにせず、WARN (`CONTEXT_UNREADABLE` / `CONTEXT_TOO_LARGE`) を出して前提なしで続ける。
  超えたときは切り詰めない (途中で切った前提は誤解を招く)。doctor が読めるかを表に出す

## 検討した選択肢

- **本文の末尾に節を足す**: 却下。本文が緊急用のときに提案も緊急用に流れる。設定例を含めると findings と 3,800 文字の枠を取り合い、収まるかどうかで出し方が変わる
- **要約の 1 回の呼び出しで提案も書かせる (出力の契約に proposals を足す)**: 却下。入力が report.json 全体になり、候補だけを渡すことにならない。
  失敗が本文の要約の失敗と結び付き、提案のためだけに本文が原文送りになる
- **observation も LLM に渡し、プロンプトで格上げを禁じる**: 却下。検査で「格上げした」ことを見分けるのが難しい。渡さなければ構造上起きない
- **LLM の文中の数字が evidence にあるかを検査する**: 見送り。「5 分」「1〜2 週間」など根拠でない数字で誤って捨てることが多い。数字は規則の行に必ず出すので、LLM の文は補足に留まる
- **提案の書き起こしの失敗で終了コード 3 にする**: 却下。本文は要約できており、3 (原文で送った) の意味と合わない。WARN と節の注記で知らせる
- **context_file を上限で切り詰めて使う**: 却下。途中で切れた前提は誤った前提になり得る。使わずに WARN で知らせる
- **context_file を設定エラーにする (無い・大きすぎる)**: 却下。前提は補助で、通知そのものを止める理由にならない

## 結果 (良い点・引き受けるコスト)

- 良い点: 提案の数字と段階は規則で再現でき、テストで固定できる。LLM が壊れても候補は必ず届く。アプリの事情を設定ファイルの外に書ける
- コスト: weekly の run は LLM の呼び出しが 1 回増える。Slack に 2 通届く。BLOCK の検査は正規表現なので、言い回しで抜ける・誤って捨てることがある (捨てる側に倒している)

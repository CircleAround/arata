# 0064. 集めることと判定することを分ける (ソースごとの位置から続きだけを集め、日単位の判定はストアから組み立てる)

- 日付: 2026-11-15
- 状態: 提案

## 背景

大きなアカウントでは 1 回の run の収集が長く、重い (ADR 0063・0065 の背景)。1 日に 1 回まとめて読む形では、

- 1 回の量が日の量そのもので、止まった後の追いつきでは数日分になる。GitHub Actions の資格情報 (役割の連鎖で最長 1 時間) の中に収まらない
- `max_scan_gb` (1 回の上限) は日の量より大きくしないと毎回止まる。上限が費用の歯止めとして効かない

短い間隔 (6 時間ごとなど) で前回の続きだけを集め、日単位の判定は貯めたものから組み立てれば、1 回の量は 4 分の 1 になる。そのための今のコードの状態を調べた。

### 今の状態 (2026-11-15 の main)

- **判定は既にストアから行っている。** `Check.Evaluate` が受け取るのは `store.Query` と窓だけで、収集したレコードを直接は見ない (`internal/checks/check.go`)。
  run は「収集 → ストアに反映 → 評価」の順で、収集と評価の境目はストアにある。`arata collect` と `arata evaluate` も別のコマンドとしてある (設計書 8 章)
- **結び付いているのは「位置」と「窓」**:
  - 窓はプロファイルごと。`From = min(now - window, 同じプロファイルの前回の window_to)` (設計書 3 章)。hourly で引いた CloudTrail を、daily はもう一度 24 時間分引く
  - ソースごとの位置 (`source_covered_to`。ADR 0038) は run の stats にあり、**同じプロファイルの直近の run** から読む (`internal/engine/catchup.go` の `planCatchup`)。
    プロファイルをまたいで共有していない
  - `init` の進捗は init の run の stats (`chunks_done`・`done_until`。ADR 0011) で、日の単位
  - `arata collect` は `--window` の固定の範囲を引くだけで、位置を読みも進めもしない。再走査もしない
- **評価が「この run で集めたこと」に頼っている所が 2 つある**:
  1. イベント型のチェック (`root_usage`・`iam_changes`・`access_denied`・`secret_access` など) の遅れて届いたものの扱い (ADR 0013):
     `[ScanFrom, From)` のうち `collected_at` が**今回の収集の時刻以降**のものを評価する (`internal/checks/helpers.go` の `windowEvents` が `EventFilter` の `LateFrom`・`CollectedSince` に渡す)。
     別の run が集めたものは評価されない
  2. CloudTrail の主体の活動の日次集計 (`principal_source`・`principal_source_writes`・`principal_write_region`。ADR 0027) は、
     「その日を最後に引いた run が見た件数」で置き換える (`internal/record/record.go` の注記)。6 時間ごとに引くと、最後の 6 時間の件数だけが残る
- **Logs Insights の日次集計**は「日の頭から引き直して置き換える」(設計書 3 章、`internal/collect/cwlogs` の `collectFormat`)。6 時間ごとに回すと、
  同じ日を 4 回 (0〜6・0〜12・0〜18・0〜24 時) 読み、読み取り量は 2.5 倍になる。これは ADR 0065 で直す
- `new_principal` (状態型) は `principals` の表を見るので、どの run が集めたかに依らない。`principal_ips.count` は再走査の分を `RescanCount` に分けているので、
  続きだけを集めても二重に数えない

## 決定

### 1. 位置はソースごとに 1 つ (プロファイルをまたいで共有する)

- 位置を「同じプロファイルの直近の run」ではなく、**全プロファイル (init・collect を含む) の、ok / partial の run のうち、そのソースの位置の最も新しい値**から読む。
  表は足さない (ADR 0038 と同じく runs の stats に置く。移行が要らず、rebuild で引き継がれ、S3 では SQLite と一緒に確定する)
- 位置を持たない古い run は、今と同じく「全ソースがその `window_to` まで取れた」とみなす
- 位置の意味は種類で違う:
  - `cloudtrail-lookup`・`cloudtrail-unused-regions`: イベントの時刻で「ここまで引いた」(今と同じ)
  - `cloudtrail-s3` (ADR 0063): 配信時刻で「ここまでのファイルを読んだ」。直前の `ingest_delay` の分のファイルのキーを stats に残し、次の run で同じファイルを読み直さない
  - `cloudwatch-logs`: 「ここまでの時を読んだ」(時の境目に揃える。ADR 0065)
- 状態のスナップショットのソース (`iam-credential-report`・`posture`・`waf-config` など。ADR 0015) は位置を持たない (今と同じ)

### 2. どの run も、ソースの位置から続きだけを集める

- 各ソースの収集範囲は `[位置 − ingest_delay, now)` (位置が無ければ今と同じ `[From − ingest_delay, To)`)。窓 (評価の範囲) とは別に決まる
- 決定: **1 回の run で 1 つのソースが集める範囲の上限 `max_collect` を持つ** (ソースの設定。書かなければ上限なし = 今と同じ)。
  上限まで集めたら、そのソースの位置をそこまで進めて `partial` にし、`SOURCE_COLLECT_LIMITED` の WARN を出す。次の run が続きから集める。
  資格情報が 1 時間で切れる環境では、`max_collect` を 1 回で収まる量 (LookupEvents なら 12h など) にすれば、追いつきが途中で全部を失わない
- 決定: 途中で失敗したソースも、**古い側から連続して取れた所までは位置を進める**。今は「途中まで取れたソースは進めない」(ADR 0038。LookupEvents は新しい順に返すので、
  取れたのは新しい側だった)。続きだけを集める形では、古い側から時間の区切り (LookupEvents は 1 時間ずつ、S3 は配信時刻の順) で引くので、取れた所までを確定できる。
  LookupEvents の引き方を「範囲を 1 時間ずつに分けて古い順に引く」に変える (呼び出しの回数は変わらない。ページの数はイベントの数で決まる)
- 収集だけの run: `arata collect --incremental` を足す (プロファイルを取らない)。全プロファイルが必要とする種類を出すソース (`neededKinds` の和) を、位置から続きだけ集める。
  評価・報告・通知はしない。報告を出さないので aratam は動かない。`--window` とは同時に使えない
- `arata collect --window` (今の固定の範囲) は残す。位置を進めない (今と同じ)

### 3. 日単位の判定はストアから組み立てる

- 評価の窓は今と同じ (`From = min(now − window, 同じプロファイルの前回の window_to)`)。窓はプロファイルごとに持ち、プロファイルをまたいで共有しない
  (daily の窓は daily の前回から決まる。hourly が先に評価しても daily の窓は縮まない)
- **評価の前提**: プロファイルのチェックが必要とする各ソースの位置が、窓の終わり − `ingest_delay` 以上であること。足りなければ、その run で続きを集めて追いつく (2 の規則)。
  それでも足りない (上限・失敗) ソースのチェックは今と同じく `coverage` に出し、run は `partial`
- **イベント型のチェックの「今回の評価で初めて見るもの」**を、収集の時刻ではなく**評価の時刻**で決める:
  - 窓 `[From, To)` に入るイベント (今と同じ)
  - 窓の前 (`< From`) で、`collected_at` が**このプロファイルの前回の評価の後**のもの (遅れて届いたもの。収集した run がどれでもよい)
  - 前回の評価の時刻は、同じプロファイルの前回の ok / partial の run の開始時刻 (runs にある)。`collected_at` は今と同じく最初に保存した run の時刻
  - こうすると、収集だけの run が先に拾った遅れて届いたイベントも、次の評価で 1 回だけ評価される。再走査の幅 (`ingest_delay`) に頼らないので、6 時間遅れて届いても拾える
    (今は `[From − ingest_delay, From)` の分だけ)
- **主体の活動の集計を時ごとにする**: `principal_source`・`principal_source_writes`・`principal_write_region` を、日ではなく **UTC の時** (YYYY-MM-DDTHH) ごとの件数にし、
  同じ (時, source, metric, key) は置き換える。CloudTrail の収集は位置 − `ingest_delay` を含む**時の頭から**引き直す (引き直しは最大 1 時間 + 遅れの分)。
  日の値は時の値の和で作る (どれも件数なので足せる)。チェックは今と同じく日の値を読む。置き場所は ADR 0065 の時ごとの表と同じ (`metrics_hourly`)
  - これで日の値は「その日の全件」になり、今の「最後に引いた run が見た件数 (下限)」より正しくなる。判定の閾値の意味は変わらない (下限で比べていたものが全件になる)
- 状態型のチェック (`new_principal` など) は今のまま (表を見るだけ)
- 試しの実行 (`run --dry-run`。ADR 0049) の「短い窓では評価する日 (前日など) が抜ける」(設計書 3 章の注記) は、ストアに前日の分が揃っていれば (位置が前日の終わりを越えていれば) 抜けない。
  抜けるのは位置が足りないときだけになり、`coverage.notes` の文言をそれに合わせる

### 4. プロファイルとの対応と、通知の回数

| 実行 | 間隔の例 | 集める | 評価 | 報告・通知 |
|---|---|---|---|---|
| `arata collect --incremental` | 6 時間ごと (または 1 時間ごと) | 全プロファイルが要るソースの続き | しない | しない |
| `run --profile hourly` | 1 時間ごと | hourly のチェックが要るソースの続き (CloudTrail。これで位置が進む) | hourly のチェック | 新しい finding があれば送る (今と同じ) |
| `run --profile daily` | 1 日 1 回 | daily が要るソースの残りの続き (ほとんど残っていない) | daily のチェック (日の値はストアから) | 1 日 1 回 (今と同じ) |
| `run --profile weekly` | 週 1 回 | スナップショット (今と同じ) | weekly のチェック | 週 1 回 |

- 決定: **通知は今の回数のまま (daily は 1 日 1 回)。** 収集を細かくしても、日単位の判定の結果を間隔ごとに送らない (同じ日の値が途中の値で何度も鳴るのを防ぐ。
  日の途中の値で平常帯と比べると、時間帯の偏りで誤って鳴る)。速く知らせたいものは hourly のチェックと、下の 5 節の候補が担う
- hourly を回している利用者は、hourly が CloudTrail の位置を進めるので、`collect --incremental` を CloudTrail のためだけに足す必要は無い。daily は CloudTrail を引き直さなくなる
  (今は hourly が引いた 24 時間分を daily がもう一度引いている)
- `examples/audit-repo` (repo init の出力) のワークフローに、6 時間ごとの `collect --incremental` を足すかは、雛形の版で決める (この ADR では足し方だけを決める)。
  足すなら S3 ストアの確定 (ADR 0034) の衝突を避けるため、同じ concurrency の組にする

### 5. 速報 (量の急変を短く知らせる) — 今後の候補 (この ADR では決定にしない)

続きだけを細かく集めると、ストアに時ごとの値が貯まる (この ADR の主体の活動、ADR 0065 の Logs Insights の小計)。これを使えば、
「急激な変化があったときに、とりあえず連絡だけする」通知が作れる。今の hourly とは性質が違うので、形を先に決めておく。

**今の hourly との違い**

- hourly のチェック (`root_usage`・`unknown_assume_role`・`oidc_assume_role`・`guardduty_findings` の High) は**起きたこと自体が異常**な事象で、1 件で鳴る。平常帯は要らない
- 速報は**量の急変**で、平常帯との比べ方が要る。判定は「ふだんより多い」で、1 件ずつの事象ではない。中身は日次の `access_denied`・`login_bruteforce` などと同じ材料の、時の単位の版

**対象の候補**

| 候補 | 材料 | 使えるようになる時期 |
|---|---|---|
| 拒否の急増 | events の拒否 (主体ごと、時ごとの件数) | この ADR の後 (events は時刻を持つ) |
| 秘匿値の一括読み出し | events の `GetSecretValue` など (主体ごと、時ごとの異なり秘匿値の数) | この ADR の後 |
| ふだん使わないリージョンへの書き込みの量 | `cloudtrail-unused-regions` の events | この ADR の後 (今は 1 件から日次で出る。量の急変は別の軸) |
| ログインの失敗の急増 | `sign_in_failures` の時ごとの小計 | ADR 0065 の後 |
| WAF の BLOCK の急増 | `waf_block`・`waf_block_ip` の時ごとの小計 | ADR 0065 の後 |

**急変の基準 (案)**

- 平常帯は**時間帯ごと** (同じ UTC の時の、直近 14 日の中央値とばらつき) を主にする。日の平常帯は昼と夜の差を均してしまい、夜の急増を見落とし、昼のふだんの山で鳴る
- 時間帯ごとの平常帯は、14 日 × 1 時間で 1 つの時に 14 点しかなく荒い。そこで「直近 6 時間の中央値の k 倍」も同時に満たすことを条件にする (両方を超えたら急変)。
  ゆっくり増えるもの (キャンペーン・リリースの後の増加) は直近の値に追従して鳴らない。それは日次の平常帯の比較が拾う
- 絶対の下限 (`min_count`) を必ず持つ (少ない件数の 2 倍・3 倍で鳴らさない)
- **平常帯が貯まっていない間** (新しい監査対象・新しいソース) は速報を出さず、`coverage.notes` に「速報は平常帯の蓄積待ち (あと N 日)」を出す。
  init のベースライン (ADR 0011) で時ごとの値を作れるなら、それで始める (Logs Insights の init は費用が増えるので、作るかは選べるようにする)

**雑音の抑え方**

- finding の key に日を入れ (`<種類>|<主体か IP>|<日>`)、同じ日の同じ急変は 1 回だけ送る。同じ日に重大度が上がったら再報告する (ADR 0022 の上げ方と同じ)
- 1 日に送る速報の上限 (`max_per_day`。例 3 件)。超えた分は送らず、日次の報告の「本日報告済み」と並ぶ欄に回す
- 日次の報告に回す境目: 速報で送った急変は、日次の報告では `already_reported` に回る (今の hourly と daily の関係と同じ。設計書 3 章)

**速報の形**

- arata が規則で 1 行の見出しと件数を作る (例「拒否が急増: <主体の ARN> 14:00 UTC の 1 時間に 1,240 件 (ふだんの同じ時間帯 30 件前後)」)。LLM の要約を待たない
- aratam は、速報のプロファイルの report.json を LLM に通さず、規則の見出しをそのまま送る (LLM が失敗したときの原文の送信と同じ道。`docs/aratam.md` 2 章)。
  末尾は「詳しくは次の日次の報告」。送り先は今の規則のまま重大度で決める (既定は medium で通常用。秘匿値の一括読み出しのように high のものは緊急用)
- ADR 0018 の役割分けは崩さない: 急変かどうかと文の中身は arata が規則で決め、report.json に書く。aratam は送り方だけを決める

**推奨: 今後の候補に留める。** 理由:

1. 時間帯ごとの平常帯は、時ごとの値が 14 日貯まってからでないと試せない。この ADR と ADR 0065 の実装の後に、試験環境と利用者のアカウントで 2 週間貯めた値を見て、
   基準 (k・`min_count`) を実データで決めたい
2. 速報は通知の回数を増やす変更で、利用者が通知を見なくなる危険がある。日次と hourly の今の通知が落ち着いてから入れる方が安全
3. 材料 (時ごとの値) はこの ADR と ADR 0065 で揃うので、決定を後にしても手戻りは無い

決めるときは別の ADR にし、最初は「拒否の急増」と「WAF の BLOCK の急増」の 2 つから始めるのを推奨する (どちらも主体・IP の単位で鳴り、対処が分かりやすい)。

## 互換

- ストア: 主体の活動の集計を時ごとの表 (`metrics_hourly`。ADR 0065 と共有) に移すので、`schema_version` を上げる。既存の日次の行 (metrics) はそのまま残し、
  チェックは「時ごとの表に行がある日は時ごとの和、無い日は metrics の日の値」を読む (移行の日より前の平常帯を捨てない)。
  rebuild (ADR 0033) は raw の時ごとの集計から作り直す (raw に時ごとの集計を足す)
- 位置: 古い run の stats の読み方は今と同じ。プロファイルをまたいで読むようになるので、hourly と daily を両方回している利用者は、daily の CloudTrail の読み取りが減る
  (同じイベントは event_id で重複しないので、結果は変わらない)
- 設定: `max_collect` は新しい任意の項目。書かなければ今と同じ (上限なし)。`config init` の雛形はコメントで示し、`config init --diff` で見える (ADR 0014)
- コマンド: `arata collect --incremental` は新しい旗。今の `arata collect --window` は変えない
- 判定の結果: イベント型のチェックの遅れて届いたものの扱いが広がる (`ingest_delay` より遅れて届いたものも評価する)。今まで黙って落ちていたものが出るようになる向きの変化だけ。
  主体の活動の日の値が「全件」になるので、`principal_new_source`・`secret_access` の件数の閾値に当たる日が増えることがある (今は下限で少なめに見ていた)

## 検討した選択肢

- **ソースの位置を新しい表に持つ**: 採らない。ADR 0038 と同じ理由 (移行と rebuild の carriedTables の変更)。runs の stats で足りる
- **評価の窓もプロファイルをまたいで共有する**: 採らない。daily と hourly は見るチェックが違い、hourly が評価した窓を daily が飛ばすと、daily のチェックが見逃す
- **収集だけの run を、チェックの無いプロファイル (`checks: []`) で表す**: 採らない。プロファイルは報告を出す単位で、報告を出さないプロファイルを作ると、
  aratam・`report` の期間集計・`RUN_MISSED` の扱いが曖昧になる。コマンドの旗の方が意味がはっきりする
- **日単位の判定を間隔ごとに回して、間隔ごとに送る**: 採らない。上の 4 節の理由 (日の途中の値で比べると誤って鳴る、同じ日が何度も鳴る)
- **主体の活動の集計を「足し込み」にする (置き換えずに足す)**: 採らない。再走査の重なり (`ingest_delay`) で二重に足される。時の頭から引き直して置き換える方が、
  今の日次の集計 (日の頭から引き直して置き換える) と同じ考え方で、重なりに強い

## 結果

- 良い点: 1 回の収集が間隔の分だけになり、資格情報の 1 時間と `max_scan_gb` の中に収まる。止まった後の追いつきも `max_collect` ずつ確実に進む
- 良い点: 遅れて届いたイベントの評価が再走査の幅に頼らなくなる。主体の活動の日の値が正しくなる
- 良い点: hourly と daily の CloudTrail の二重の読み取りが無くなる
- 引き受けるコスト: run の数が増える (6 時間ごとなら 1 日 4 回)。S3 ストアの確定 (ADR 0034) の回数と、衝突の可能性が増える
- 引き受けるコスト: 位置がプロファイルをまたぐので、1 つのプロファイルの run を消したり失敗させたりしたときの影響が他に及ぶ (たとえば dry-run は位置を進めないことを保つ)

## 手間の見積もり

- 位置の共有 (planCatchup の読み方)・`max_collect`・途中まで取れたソースの位置・LookupEvents を 1 時間ずつ古い順に引く: 2 日
- イベント型のチェックの「評価の時刻」での境目 (全イベント型チェックの共通部と各テスト): 1.5 日

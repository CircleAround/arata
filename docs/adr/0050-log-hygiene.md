# 0050. アプリのログに残った「載せるべきでない値」を、種類ごとの件数だけで週次に報告する (`log_hygiene`。値は取り出さない)

- 日付: 2026-11-14
- 状態: 提案

## 背景

アプリのログ (CloudWatch Logs) には、載せるべきでない値が残ることがある。

- **隠し忘れた個人情報の送信項目**: Rails は受け取ったパラメータを `Parameters: {...}` の行に書く。`filter_parameters` に無い項目
  (`name`・`address`・`tel` など) は `[FILTERED]` にならず、値がそのまま残る
- **S3 の署名付き URL**: `X-Amz-Credential` と `X-Amz-Signature` を含む URL は、期限までそれだけでオブジェクトを読める。
  長期のアクセスキー (`AKIA` で始まるキー ID) で署名したものは、期限を最長 7 日にでき、キー ID もログに残る
- **秘密の値**: AWS のアクセスキー、Slack のトークン (`xoxb-` など)、PEM の秘密鍵
- **本番での debug の出力**: SQL の文に値が入った行。形の決まっていない値がまとめて残る

ログを読める人と仕組み (運用者、ログの転送先、監査の道具) は、アプリのデータベースを読める人より広いのがふつうである。
ログに残った値は、保持期間のあいだ (無期限の設定もある) 読め続ける。

arata の今のチェックは、ログから「誰が何をしたか」を数えるもので、**ログの中身そのものの衛生**は見ていない。
`credential_hygiene` は IAM のキーの状態 (未使用・MFA)、`secret_access` は秘匿値の読み取りで、どちらもログに漏れた値は見ない。

確かめてあること (実際の AWS で):

- Logs Insights は、1 本のクエリで種類ごとの件数だけを返せる。`fields (<条件>) as f_x` で行ごとの 0 / 1 を作り、`stats sum(f_x)` で足す。
  結果は数の 1 行で、ログの値を返さない
- Insights は、同じ名前の一時フィールドを 2 度定義できない。条件ごとに名前を分ける必要がある
- 読み取りの費用はごく小さい。1 週間で 1 GB のロググループなら、1 回の読み取りは約 0.008 USD (東京の単価。ADR 0028)

## 決定

**週次の状態型のチェック `log_hygiene` を足す。ロググループごとに Logs Insights のクエリを 1 本流し、載せるべきでない値の「種類ごとの行数」だけを受け取る。
値は取り出さない・保存しない・通知しない。**

### 値を取り出さない (このチェックの中心)

- クエリの形は `fields` (条件ごとの 0 / 1) と `stats sum(...)` だけに固定する。`display`・`sort`・`limit`・`parse`・group by を使わず、
  `@message` もその一部も結果に出さない。結果は数の 1 行である
- **サンプルの行も引かない。** 伏せた形 (`MaskSample`) でも引かない。秘密の値や個人情報は形が決まっておらず、伏せ漏れが漏えいになる
- arata が受け取るのは数だけ。結果の値は「有限で負でない整数」として読み、読めなければそのソースの収集を失敗にする (0 件として解消に倒さない)。
  結果に文字列が返ってきても finding・ストア・ログに写さない
- finding・report・通知に載るのは、ソースの id、ロググループの名前、種類、行数、設定に書いた項目名、保持期間だけ。aratam と LLM にも値は渡らない (渡すものが無い)
- クエリの文は CloudTrail (`StartQuery` の要求) と Insights の履歴に残る。入るのは arata の固定の正規表現と設定の項目名だけで、値は入らない
- 「どの行か」は arata では分からない。場所を探す手順は playbook に書き、ログを読む権限のある人が自分で行う

### 種類と重大度

| 種類 (設定に書く名前) | 数えるもの | 重大度 |
|---|---|---|
| `secret_aws_access_key` | 長期のアクセスキーの ID の形 (`AKIA` + 英大文字と数字 16 字)。署名付き URL の `X-Amz-Credential=` の中のものは除く | high |
| `secret_slack_token` | Slack のトークンの形 (`xoxb-` などの接頭辞 + 決まった字) | high |
| `secret_private_key` | PEM の秘密鍵の先頭の行 (`-----BEGIN … PRIVATE KEY-----`) | high |
| `presigned_url_long_term_key` | `X-Amz-Credential=AKIA…` を含む行 (長期のキーで署名した URL) | medium |
| `presigned_url` | `X-Amz-Signature=` を含み、上に当たらない行 | medium |
| `unfiltered_param` | 設定に書いた項目名が、`"<項目>"=>"<値>"` か `"<項目>":"<値>"` の形で、値が空でも `[` 始まりでもない行 | medium |
| `debug_sql` | 実行時間の付いた SQL の文の行 (ORM の debug の出力の形) | low |

重大度の理由:

- **秘密の値は high。** ログを読める人なら誰でも、その値でログの外の資源に届く。期限が無く、気づいたら無効化と作り直しが要る。
  アクセスキーは ID だけでは使えないが、ID が出る行 (環境変数や設定の書き出し) にはシークレットも並ぶことが多く、arata は値を見ないので区別しない。
  ID だけと確かめたものは ack する
- **署名付き URL は medium。** 読めるのは 1 つのオブジェクトで、期限がある。長期のキーの分も medium にするが、種類を分ける
  (期限が長く取れ、キー ID が残り、対処がロールでの署名への移行になるため。件数を別に見せる)
- **隠されていない個人情報の項目は medium。** 外の資源には届かないが、ログを読める範囲に個人情報が広がる。設定の直しで止まる
- **本番の debug は low。** それ自体は漏えいではなく、他の種類を増やす原因 (値が SQL に入る) と量の問題。直ちに調べる必要は無い

正規表現の細部は実装とテストで固定し、設計書 7 章に書く。先読み・後方参照は使わない (Go の RE2 でも同じ意味にして、テストで確かめられるようにする。下の「クエリの組み立て」)。
`unfiltered_param` が「値が `[` 始まりでない」としているのは、`[FILTERED]` でないことを先読みなしで書くためである。

### finding

- 状態型 (ADR 0005・0015)。weekly のプロファイルで動く。窓 (7 日) の行数が 1 以上なら finding、0 なら次の週に解消する (posture と同じ扱い)
- key は `<ソースの id>|<種類>`。**ロググループ × 種類**で 1 件 (1 ソース = 1 ロググループ。同じロググループを `stream_prefix` で分けた 2 つのソースは別に数える)
- Data: `log_group`、`kind`、`count` (行数)、`retention_days`、`unfiltered_param` では `fields` (項目名 → 行数)
- Fingerprint は重大度 + 種類 (+ `unfiltered_param` では当たった項目名の集合)。行数と保持期間は入れない (毎週 changed にしない)。
  ack した後に別の項目が当たり始めたら changed として出る
- **解消は「直近 7 日のログに無い」という意味で、古い行が消えたという意味ではない。** 直した週は窓に直す前の行が残るので、解消はその次の週になる。
  古い行は保持期間が過ぎるまで読める。秘密の値は、解消しても無効化が済むまで終わりではない。見出しと playbook にこう書く
- 行数の下限は置かない。1 行でも出す (秘密の値は 1 行で足りる)

### 保持期間

- ロググループの保持期間 (`retentionInDays`。未設定は無期限) を、finding の Data の `retention_days` (無期限は `0`、取れなければ `unknown`) と見出しに載せる。
  例: 「ロググループ prod-app のログに、隠されていない送信項目 (name, tel) が 12 行 (直近 7 日。保持期間は無期限)」
- **重大度には加えない。** 重大度は「何が漏れたか」で決める。「長い」の境目を arata が持つと暗黙の既定になる (ADR 0014)。
  保持期間はロググループの性質で、加えるとそのロググループの全部の種類が一緒に上がるだけである。読む人は、見出しの保持期間で対処の順を決められる
- 権限は足さない。`logs:DescribeLogGroups` は配布用の読み取り専用ロール (`deploy/iam/readonly-role.yaml`) に既にあり、
  cloudwatch-logs の collector は問い合わせの範囲の判定のために既に 1 回引いている (設計書 2 章)。その結果を使う
- `DescribeLogGroups` が失敗しても、このチェックは止めない (`retention_days: unknown`)

### 設定 (暗黙の既定なし。ADR 0014)

```yaml
sources:
  - id: app_prod
    kind: cloudwatch-logs
    log_group: prod-app
    format: text            # 行を解釈しない。log_hygiene だけが使う (名前は仮)
    max_scan_gb: 5

checks:
  log_hygiene:
    sources: [app_prod]     # 見るソース。書いたものだけ
    kinds: [secret_aws_access_key, secret_slack_token, secret_private_key, presigned_url_long_term_key, presigned_url, unfiltered_param, debug_sql]
    param_fields: [name, address, tel]   # unfiltered_param が見る項目名
```

- 既定値は `sources`・`kinds`・`param_fields` とも空。空なら何も流さず、チェックは理由を付けて skip になる。
  見るロググループ・種類・項目名は利用者が書いたものだけ
- 雛形 (`config init`) は、上の例をコメントで示す。チェックは Registry から weekly のプロファイルに並ぶが、設定を書くまで読み取りは起きない。
  既にある設定には `config init --diff` で、増えたチェックとパラメータとして見える
- アプリのログ (http のアクセスログでないもの) を登録できるように、cloudwatch-logs の形式に「解釈しない」もの (`text`) を足す。
  既存の形式 (`nginx_access` など) のソースも `sources` に書ける (アクセスログのクエリ文字列に署名付き URL が残る場合がある)
- `param_fields` の項目名は 1〜64 字の英数字・`_`・`-` に限り、32 個まで。外れたら `CONFIG_INVALID`。`kinds` は上の表の名前だけ
- 利用者が正規表現を書く種類は、今回は入れない (検討した選択肢)

### クエリの組み立て (エスケープとファズ。ADR 0037・0041)

- 項目名は、形を検査したうえで `regexLiteral` (`internal/collect/cwlogs`。`regexp.QuoteMeta` + `/` のエスケープ) を通して Insights の `/.../` に入れる。
  形の検査と二重にする (検査が緩んでもリテラルを抜け出さない)
- 一時フィールドの名前は、設定の値から作らず、種類の名前と番号で作る (`f_secret_aws_access_key`、`f_param_0`、`f_param_1`、…)。
  同じ名前の 2 度の定義が起きず、設定の値が識別子に入らない
- 項目名は鍵として完全に一致させる (前後の `"` まで含める)。`name` は `file_name` に当たらない
- ファズで確かめる性質 (「パニックしない」だけにしない):
  - どんな設定の値でも、クエリの段の数と並び (`fields` と `stats` だけ) が変わらない。`/.../` の中にエスケープされていない `/` が無い。
    一時フィールドの名前は全部異なり、決まった字だけ
  - 組み立てた正規表現は Go の regexp でも読め、`"<項目>"=>"x"` に一致し、`"<項目>"=>"[FILTERED]"`・値が空・別の鍵 (`"x<項目>"`) に一致しない
  - 結果の行 (偽の API が返す任意の文字列) から作る record と finding に、結果の文字列が残らない。数でない値・負の値・無限大は収集の失敗になり、0 件にならない
  - 設定の検査を通った項目名は、形の規則どおり (受け入れた値は書いたとおりの意味)

### 収集と失敗

- weekly の run で、`sources` の各ソースに 1 本だけ流す。範囲は窓 (7 日)。そのソースの他の集計 (http_access の日次集計など) は weekly では流さない
- 結果は種類ごとの行数のスナップショットとして保存し、**クエリが成功したときだけ**ソース単位で丸ごと置き換える (ADR 0015)。
  失敗 (権限、`max_scan_gb` の超過、タイムアウト、読めない結果) したら前回のままにし、そのソースの finding を維持して、
  `coverage.sources_failed` に出す。読めなかったことを「直った」と誤認しない
- ロググループが窓の範囲に無い (作成前・保持期間の外) ときは、既存の扱いどおり「データなし」(0 件) とする
- 権限は足さない (`logs:StartQuery`・`GetQueryResults`・`StopQuery`・`DescribeLogGroups` は既にある)。書き込み系の API は呼ばない
- `arata doctor` は、このクエリの構文検査 (`QUERY_INVALID`) と、cost の行への週 1 本分の加算をする

### 誤検知

- `unfiltered_param`: `name` という項目が個人情報でない (商品名など) 場合は、`param_fields` から外すか、より限定した項目名だけを書く。
  項目ごとには黙らせられない (key は種類ごと)。全体を ack した場合も、別の項目が当たり始めたら changed で出る
- 秘密の値の形: テスト用の値、文書の例、キー ID だけの行は、確かめたうえで理由を付けて ack する
- 署名付き URL: 期限が短く、ログを読める人が元から対象を読める場合は ack する

### 限界

- **形の決まっていない個人情報は拾えない。** 自由文の住所、本文、設定に書いていない項目名、JSON でも Rails の形でもない書き方は数えない。
  このチェックが 0 件でも「ログに個人情報が無い」ことにはならない。playbook と見出しの説明に明記する
- 値が `[` で始まる項目は、隠されていなくても数えない
- 数えるのは行数で、1 行に複数あっても 1。形が同じだけの別物 (似た文字列) も数える
- 秘密の値が本物か・有効かは確かめない (arata は値を見ない)
- 見るのは週次の窓だけ。窓より前から残っている行は、導入しても出ない

### playbook (`docs/ai/playbooks/log_hygiene.md`) に書く対処の筋

1. **場所を探す**: ログを読む権限のある人が、Insights で時刻とログストリームだけを返すクエリを流す (値を画面に出さない形を例として載せる)。
   LLM のエージェントは値を表示するクエリを流さず、値を会話・通知・Issue に写さない
2. **秘密の値**: 漏れたものとして扱う。先に無効化と作り直し、次にそのキーの利用を CloudTrail で確かめ、最後に出力元を直す
3. **隠されていない項目**: `filter_parameters` に項目を足す。足した次の次の週に解消する
4. **署名付き URL**: URL をログに出さない (クエリ文字列を落として書く、オブジェクトのキーだけを書く)。期限を短くする。
   長期のキーでの署名は、ロール (一時的な認証情報) での署名へ移し、キーを廃止する
5. **本番の debug**: 本番のログレベルを info 以上にする
6. **残った行**: 保持期間を決める (無期限をやめる)。必要なら、値の残るログストリームを利用者が消す。ログを読める主体と、転送先 (サブスクリプションフィルター・エクスポート) の複製も見直す
7. **入口で伏せる**: CloudWatch Logs のデータ保護ポリシーを案内する (検討した選択肢)
8. **誤検知**: 上の「誤検知」の手順

### 既存のチェックとの関係

- `credential_hygiene` は IAM のキーの**状態** (未使用・MFA なし・ルートのキー)。`log_hygiene` はログの**中身**。
  長期のキーがログに出ていれば両方に出ることがあり、対処 (キーの廃止) がつながる。playbook で相互に参照する
- `secret_access` は秘匿値の**読み取り** (CloudTrail)。ログに漏れた値は見ない
- `FORMAT_MISMATCH` の行の例の伏せ (`MaskSample`) は arata 自身の出力の守りで、ログの中身の報告ではない

## 検討した選択肢

- **当たった行を伏せて数行だけ取り、場所の手がかりにする**: 却下。伏せる規則 (メールアドレスなど) は形の決まった値にしか効かない。
  ここで探しているのは、まさに伏せ漏れた値である。場所は、権限のある人が自分のコンソールで探す
- **イベント型にして、出た週ごとに報告する**: 却下。直るまで毎週「新規」が出て、ack が効かない。直ったことも分からない。
  「今のログがどうか」という状態として扱い、直れば解消にする
- **daily で見る**: 見送り。早く気づけるが、読み取りが 7 倍になり、原因 (コードの設定) は日ごとに変わらない。
  秘密の値だけ daily にする案は、実際に出る頻度を見てから決める
- **key をロググループだけにし、種類を Data にまとめる**: 却下。種類ごとに重大度と対処が違い、1 つ直しても解消にならず、ack が種類ごとにできない
- **key を項目名ごとにする (`unfiltered_param|name`)**: 却下。項目ごとに ack できるが、finding が項目の数だけ増える。
  誤検知の項目は設定から外すほうが、理由が設定の履歴 (PR) に残る。当たった項目は Data と見出しで分かる
- **保持期間で重大度を上げる (無期限なら 1 段上げる)**: 却下。上の「保持期間」のとおり。見出しに出せば、読む人の判断には足りる
- **解消を保持期間が過ぎるまで待つ (古い行が消えるまで open のまま)**: 却下。確かめるには保持期間の全体を毎週読むことになる (無期限なら全量)。
  直したのに長く残り続ける finding は、読まれなくなる。「直近 7 日に無い」と明記して解消にする
- **保持期間が無期限のロググループを、posture の項目として報告する**: 今回は入れない。対象 (全部のロググループか、見ているものだけか) の決めが要る。必要なら別の ADR で決める
- **種類と項目名に既定を持つ (よくある個人情報の項目名を入れておく)**: 却下。ADR 0014。項目名はアプリごとに違い、既定の `name` は誤検知の元になる。
  例は雛形のコメントで示す
- **利用者が正規表現を書ける種類を足す**: 見送り。件数だけを返す形は保てるが、重大度と種類の名前を利用者が決めることになり、
  Insights の方言の検査とファズの対象が広がる。固定の種類で始め、要望が出たら足す
- **アクセスキーの ID だけの行を数えない (シークレットの形と並んだときだけ数える)**: 却下。シークレットは形が決まっておらず (40 字の英数字と記号)、
  誤検知なしに書けない。ID の形を high で出し、ID だけなら ack する
- **CloudWatch Logs のデータ保護ポリシーに任せる**: arata の代わりにはしない。取り込みの時点で伏せられる強い手段だが、
  利用者が設定する書き込みで、取り込み量に費用がかかり、隠し忘れた送信項目のようなアプリ固有の形は拾わない。arata は読み取り専用で、
  入れていない環境でも状態を報告できる。対処の 1 つとして playbook で案内する
- **ログを S3 にエクスポートして arata が走査する**: 却下。生のログが arata の実行環境を通り、値を取り出さないという性質が保てない。書き込み系の操作も要る

## 結果 (良い点・引き受けるコスト)

- これまで何も出なかった「ログに値が残っている」が、種類と量で見えるようになる。値は arata・ストア・通知・LLM のどこにも入らない
- 権限は増えない。費用は、見るロググループごとに週 1 本の読み取り (1 GB で約 0.008 USD)。`max_scan_gb` が効く

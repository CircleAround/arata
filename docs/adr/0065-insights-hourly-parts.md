# 0065. Logs Insights を時の単位で続きだけ読み、時ごとの小計 (部分の行) を残して日の値を Go で組み立てる。集計のクエリは確かめてから 1 本にまとめる

- 日付: 2026-11-15
- 状態: 採用 (ADR 0031 の「読み直しをやめる案を採らない」を置き換える。ADR 0064 の位置を前提にする)

## 背景

ある利用者のアカウントの実測 (`cloudwatch-logs`、形式 `wafv2`):

- 1 日約 4.5 GB のロググループで、1 回の daily が 15.2 GB を読み、`max_scan_gb` を超えて止まった (`QUERY_LIMIT`)
- 集計の行数の上限 (10,000) にも当たった (`AGGREGATE_TRUNCATED`)

### 今、何本を、どの範囲で流しているか (`internal/collect/cwlogs`)

範囲はどのクエリも**窓の始まり (再走査を含む) を含む UTC の日の 0 時から、窓の終わりまで** (`collectFormat` の `DayStart(w.Start())`)。日次の値を置き換えで保存するため (設計書 3 章)。

| 形式 | クエリ | 範囲の流し方 | 軸 (group by) |
|---|---|---|---|
| wafv2 | 1. 解釈率 + `waf_rule_action` | 範囲全体を 1 本 (上限に当たれば半分に分ける。1h まで) | 日, WebACL, ルール, action |
| | 2. 止めた・出した系 (`waf_block_ip`・`waf_block_path`(`_ips`)・`waf_allow_probe`(`_ips`)・Challenge) | 同上 | 日, WebACL, ルール, action, グループの中のルール, method, path, ip, Challenge の項目… |
| | 3. カウントの一致 (`waf_rule_count_match`・`_suspect`) | 同上 | 日, WebACL, カウントのルールの位置…, 探索パスの印 |
| | 4. レート (`waf_ip_rate_p50`・`_p99`・`_max`) | UTC の 1 日ずつ | 1 段目 (5 分, WebACL, パスの組, ip) → 2 段目 pct・max (WebACL, パスの組) |
| http_access | 1. 解釈率 + `probe_paths` | 範囲全体を 1 本 (request_lines なら 1 日ずつ) | 日, status, 探索パス |
| | 2. `sign_in_failures` + `probe_hits` | 範囲全体を 1 本 | 日, ip, method, status, パスの印 |
| | 3. endpoint_abuse (設定があれば) | UTC の 1 日ずつ | 時間幅, ip, ua, … |

Logs Insights はクエリごとに範囲のログを全部読んだ量で課金し、`max_scan_gb` もその合計で見る。wafv2 は **4 本 × 範囲**を読む。daily を UTC 00:40 に回す見本
(`examples/audit-repo`) では範囲が約 1 日なので、4 本 × 1 日分 ≈ 4 日分になり、実測の 15.2 GB (1 日約 4.5 GB の約 3.4 倍) と合う。実行の時刻が悪ければ範囲は最大約 2 日になり、倍になる (ADR 0031)。

行数の上限は範囲全体の 1 本に効く。2 の止めた・出した系は (ルール, path, ip) の組が多く、攻撃の多い日に 10,000 行を超える。分けて引き直すのは 1h までで、それでも超えれば `truncated`。

ADR 0031 は「前回の続きから読み、時間幅の小計を足す」案を、(1) 日の値の多くが足せない (異なり IP の数・日ごとの上位・その日 BLOCK された IP・p50 / p99)、
(2) 細かい行の保存の容量とプライバシー、(3) rebuild・再走査との整合、(4) 効果は実行時刻次第で、時刻を合わせれば 1 倍、という理由で採らなかった。
今回の実測では時刻を合わせても 1 回の量が上限を超えるので、(4) は当たらない。ADR 0064 の位置と短い間隔の収集があれば (3) にも答えられる。

## 決定

### 1. 時の単位で、続きだけを読む

- 集計のクエリの軸を `bin(1d)` から **`bin(1h)`** にする (endpoint_abuse は今の時間幅のまま)
- 範囲は**ソースの位置 (ADR 0064) の時から、`now − ingest_delay` を切り捨てた時まで**。**終わっていない時は読まない**。
  同じ時を 2 度読まないので、1 日に読む量は「本数 × 1 日分」になり、実行の時刻にも間隔にも依らない
  (今の「日の頭から読み直す」は、6 時間ごとに回すと同じ日を 4 回読む)
- 位置は読み終えた時の終わりに進める。失敗した時は進めない (ADR 0038 の追いつきが同じ時から読み直す)
- 決定: ログの取り込みの遅れが `ingest_delay` を超えた行は、その時を読んだ後に届くと数えられない。今も同じ (日の頭から読み直すので翌日には入るが、
  日が変わって前日を読み直さなくなれば落ちる)。遅れの大きいロググループは `ingest_delay` を大きくする。doctor が直近の時の行数を前の時と比べ、取り込みの遅れの疑いを WARN にする
- 1 回に読む範囲の上限は ADR 0064 の `max_collect` に従う。`max_scan_gb` は 1 回の上限のまま (時の単位で区切るので、上限に当たったらそこまでの時を確定して `partial`)
- 行数の上限 (10,000) は **1 時間の範囲**に効く。当たったら時を半分ずつに分けて引き直す (下限は 15 分。今の `minSplit` の 1h を下げる。分けてもスキャン量は増えない)。
  それでも当たれば今と同じく `truncated`

### 2. 時ごとの部分の行を残し、日の値を Go で組み立てる

- 足せない値があるので、時ごとの**最終的な値**ではなく、**クエリが返した行 (部分の行)** を残す。行は今も Go が受け取って振り分けている形
  (ADR 0031。`collectWAF`・`collectHTTP` は行を受け取って日の metric を作る) なので、日の値は「その日の 24 時間分の行を合わせて、今の振り分けに通す」で作る
- 新しい表 `metric_parts` (hour, source, query, row の JSON) に置く。日の値は今の `metrics` に今と同じ名前・key で書く (**チェックの読み方は変えない**)
- 足せない値の扱い:

| 値 | 扱い | 今と同じ値か |
|---|---|---|
| 件数 (`waf_block`・`waf_block_ip`・`sign_in_failures`・`probe_hits`・`lines_total`…) | 時の行の件数の和 | 同じ |
| 異なり IP の数 (`waf_block_path_ips`・`waf_allow_probe_ips`・`waf_challenge_*_ips`) | 行が ip の軸を持つので、日の行を合わせて IP の集合を取る | 同じ |
| その日 BLOCK された IP (`waf_rule_count_match_suspect`) | 日の行から集合を作ってから、カウントの一致の行を振り分ける (日が揃ってから作る) | 同じ |
| 日ごとの上位 (`top_paths` など) | 日の行を合わせてから並べる | 同じ |
| レートの p50 / p99 / max | 2 段目を `stats count(*) by WebACL, パスの組, n` (5 分あたりの件数 n の度数) に変え、時の度数を日で足して、Go で分位数を取る | **p50 / p99 は少し変わる** (下の「互換」) |
| endpoint_abuse | 今も時間幅の単位なので、時の範囲で流してもそのまま | 同じ (幅が時の境目をまたがないように、幅は 1 時間を割り切る値に限る。今の設定の検査で確かめる) |
| request_lines (ADR 0051) | request_id で行をまとめるので、時の境目をまたぐリクエストが 2 つに割れる | **この ADR の対象外**。request_lines のソースは今のまま日の頭から読む (部分の行にしない) |

- 決定: **日の値は、その日の 24 時間分の部分の行が揃うまで「途中の値」として毎回作り直す** (今の当日分と同じ扱い)。揃った日 (位置が日の終わりを越えた日) は確定とし、
  以後は作り直さない。日の値は今と同じく raw (JSONL) にも追記する
- 決定: **部分の行は raw に書かない**。日の値が作れれば要らない作業用の行で、raw に入れると原本が日の行の数十倍に膨らむ。`metric_parts` は確定した日から
  `retention.metric_parts` (既定 3 日。`config init --diff` で見える) を過ぎたら消す。rebuild (ADR 0033) は `metric_parts` を既存の SQLite から引き継ぐ
  (raw から作れない表の扱いと同じ)。引き継げなかった未確定の日は、位置をその日の頭に戻して読み直す
- 速報 (ADR 0066) の `sign_in_failure_spike` のために、http_access の日の値を作るとき、時ごとの sign-in の失敗の和を `metrics_hourly` に `sign_in_failures_hourly` として書く
  (部分の行は 3 日で消えるが、平常帯は 14 日分の時ごとの値を要るため。1 ソース 1 時間 1 行)
- 主体の活動の時ごとの集計 (ADR 0064) は件数だけなので、部分の行ではなく時ごとの値 (`metrics_hourly`) に置く。表を分ける理由: こちらは足せる値で、
  日の値の作り直しに行の振り分けが要らない

### 3. ストアの行数の見積もり

部分の行の数は「時ごとにクエリが返した行の数」の和。上限は 1 時間 10,000 行 × 24 × 本数 (分けて引き直せばさらに増える)。

| クエリ (wafv2) | 1 時間の行の見込み | 1 日 | 3 日残す |
|---|---|---|---|
| 1. 解釈率 + rule_action | 数十 (WebACL × ルール × action) | 〜1,000 | 〜3,000 |
| 2. 止めた・出した系 | 数百〜数千 (BLOCK の (ルール, method, path, ip)) | 1 万〜5 万 | 3 万〜15 万 |
| 3. カウントの一致 | 数十〜数百 | 〜5,000 | 〜1.5 万 |
| 4. レートの度数 | 数百 (WebACL × パスの組 × n の種類) | 〜5,000 | 〜1.5 万 |

1 行は JSON で 200〜500 バイトほどなので、wafv2 の 1 ソースで多い日でも数十 MB。SQLite で困る量ではない。S3 ストアは SQLite を毎回出し入れする (ADR 0034) ので、
ADR 0064 の短い間隔と合わせて転送量を実データで測る (未確認)。行は今の metrics の key と同じく IP・正規化したパスを含むが、新しい種類の値は入れない (メールはマスク済み)。

### 4. 集計のクエリを 1 本にまとめる (確かめてから)

時の単位で続きだけを読んでも、**本数 × 1 日分**は残る。wafv2 の 4 本を減らすには、本数を減らすしかない。

- 1〜3 を 1 本にするには、「止めた・出した行だけ path・ip を持ち、ほかの行では空」の軸が要る。空にしないと全行の (path, ip) で行が爆発する (ADR 0031 で却下した理由)。
  Logs Insights で「ある行だけ値を持つフィールド」を作る方法 (フィールドに対する `parse` で捕獲したものを軸にする、`concat` と null の扱い) は未確認 (ADR 0031)
- 決定: **sandbox で「条件を満たす行だけ値を持つフィールド」を作れること、それを group by の軸にしたときに空の行がまとまる (1 行になる) ことを確かめてから、1〜3 を 1 本にする**。
  確かめられなければ 1〜3 は今の 3 本のまま (この ADR の 1〜3 節だけを入れる)
- 4 (レート) は 1 段目が全行の (5 分, ip) なので、ほかとまとめられない。2 段の stats のまま別の 1 本に残す
- まとめた 1 本は 1 時間で今の 3 本の行の和を返すので、行数の上限に当たりやすくなる。時を分けて引き直す (1 節) で受ける。分けてもスキャン量は増えない

### 5. 見積もり (1 日 4.5 GB の wafv2)

| | 本数 | 1 日に読む量 | 1 回に読む量 (daily 1 日 1 回 / 6 時間ごと) | 30 日 (東京 0.0076 USD/GB) |
|---|---|---|---|---|
| 今 (UTC 00:40 に daily) | 4 | 約 18 GB (実測 15.2 GB) | 約 18 GB / — | 約 4.1 USD |
| 今 (実行の時刻が悪いとき) | 4 | 最大約 36 GB | 最大約 36 GB / — | 最大約 8.2 USD |
| 1〜3 節 (時の単位・続きだけ) | 4 | 約 18 GB | 約 18 GB / **約 4.5 GB** | 約 4.1 USD |
| 1〜4 節 (1 本にまとめられたとき) | 2 | **約 9 GB** | 約 9 GB / **約 2.3 GB** | 約 2.1 USD |

- 1〜3 節だけでは 1 日の量 (費用) は今の最良の時刻と同じで、効くのは「1 回の量が間隔の分だけになる」(`max_scan_gb` に収まる)・「実行の時刻に依らない」・「行数の上限が 1 時間に効く」の 3 つ
- 1 日の量を半分にするのは 4 節 (本数を減らす) だけ
- http_access は 2 本 (+ endpoint 1 本) で、1〜2 を 1 本にできれば同じく減る (同じ確かめ方)

## 互換

- ストア: `metric_parts` と `metrics_hourly` (ADR 0064) を足すので `schema_version` を上げる。既存の `metrics` の日の行はそのまま残る (チェックは今と同じく metrics を読む)。
  移った日 (時の単位で読み始めた日) はその日の 0 時からの部分の行が無いので、その日だけは今の方法 (日の頭から 1 本で読む) で作り、翌日から時の単位にする
- 値: レートの p50 / p99 は、Insights の `pct` (近似) から Go の分位数 (度数から正確に) に変わる。`waf_review` の提案 (ADR 0023) のレートの値が少し変わる。
  ほかの値は今と同じ。今と同じことはシミュレーター (`cwlogstest.Sim`) とゴールデン (`testdata/equiv_*.golden`。ADR 0031) で確かめる (レートの行だけゴールデンを変え、理由を PR に書く)
  決定: **この変更を入れる版の Release の本文に、`collect: hourly` のソースでは `waf_ip_rate_p50`・`waf_ip_rate_p99` の値の出し方が変わる (近似から正確な分位数へ) ことを書く**。
  `report.json` の型と `schema_version` は変わらない (値の意味は同じ「5 分あたりの件数の分位数」で、計算の精度だけが変わる。ADR 0054)
- 設定: 新しい項目は `retention.metric_parts` だけ。時の単位で読むことは、`cloudwatch-logs` のソースに `collect: hourly` を書いたものだけに効かせる (最初の版)。
  書かなければ今と同じ (日の頭から読み直す)。雛形はコメントで示し、`config init --diff` で見える (ADR 0014)。実データで確かめた後の版で既定にするかを決める
- doctor の cost の行: 「範囲が最小になる時刻」の案内 (ADR 0031) は、`collect: hourly` のソースでは「1 日 = 本数 × 1 日分。1 回 = 間隔の分」に変える

## 検討した選択肢

- **時ごとの最終的な値だけを残し、足せない値は日の頭から別に読む**: 採らない。足せない値は wafv2 の 2・3 のほぼ全部で、読み直しが残る
- **足せない値を近似のスケッチ (HyperLogLog など) で持つ**: 採らない。Insights の中でスケッチを作れず、行 (ip) を Go に返す今の形と変わらない。値も今と変わる
- **日の値を確定した後も部分の行を長く残す (平常帯を時の単位で持つ)**: 採らない (今は)。ADR 0064 の速報が時間帯ごとの平常帯を要るなら、そのときは部分の行ではなく
  時ごとの最終的な値 (`metrics_hourly`) を残す。部分の行は IP の軸を持ち重い
- **フィールドインデックス (`filterIndex`) で 2・3 の読み取りを絞る**: 記録だけにする (ADR 0031 と同じ)。利用者側の設定 (`PutIndexPolicy`) と読み取り専用ロールへの
  権限の追加が要り、効果は sandbox で測ってから。4 節 (まとめる) と相性が逆
- **WAF のログを S3 や Firehose から読む**: この ADR では採らない。WAF の配信先を変えるのは利用者側の構成の変更で、ADR 0046 (ALB の S3) と同じく次の段の候補にする

## 結果

- 良い点: 1 回の読み取りが間隔の分だけになり、`max_scan_gb` が日の量より小さくても止まらない。実行の時刻に費用が依らない。行数の上限が 1 時間に効き、当たりにくい
- 良い点 (4 節が通れば): wafv2 の 1 日の読み取りが約半分
- 引き受けるコスト: 作業用の表 `metric_parts` と、その消し方・rebuild での引き継ぎが増える。日の値を作る道が「Insights の行 → Go」から「部分の行の表 → Go」になり、
  確定した日と途中の日の 2 つの状態を持つ
- 引き受けるコスト: `ingest_delay` より遅れて取り込まれた行は数えられない (今は翌日の読み直しで入ることがある)

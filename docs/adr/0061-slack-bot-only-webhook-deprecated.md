# 0061. Slack への送り方を bot にそろえ、aratam の Webhook の方式は非推奨にする (当面は動くまま残す)

- 日付: 2026-11-14
- 状態: 採用
- 関係する判断: `docs/aratam.md` 4-1 章の「決定 (両方を残す)」(この ADR が置き換える)、ADR 0044 (aratam の秘密は環境変数)、0054 (WARN には code)、
  0059・0060 (監査を回すリポジトリの一式)、0029 (Block Kit)

## 背景

aratam は、Slack へ 2 つの方式で送れる。Incoming Webhook (`slack.webhook_env`) と、bot トークンとチャンネル ID (`slack.bot_token_env` と `slack.channel`。`chat.postMessage`)。
bot の方式を足したとき、Webhook は「チャンネルが 1〜2 個の利用者には一番狭い権限」として、並べて残した (`docs/aratam.md` 4-1 章)。

2 つを並べて持つことの費用が、見えてきた。

- **一式の形が、送り方の数だけ増える**。監査を回すリポジトリの一式 (ADR 0059) は、どちらの方式でも動くように、3 つの Slack の秘密を全部参照し、
  実行のたびに送り方を判別していた。要る秘密が利用者ごとに違い、「足りない秘密」を機械で出せない (ADR 0060)
- **Webhook では、この先の機能が作れない**。Webhook は、次の性質を持つ
  - 送り先が、URL を作ったときのチャンネルに固定される。チャンネルを足す・変えるたびに、新しい URL (秘密) が要る
  - 投稿したメッセージの識別子 (`ts`) が返らない。自分の投稿を後から指せない
  - そのため、投稿を**消せない・更新できない**。スレッドに続きを付けることもできない
- 文書と雛形が 2 通りになり、利用者は最初に「どちらにするか」を決めることになる

**Slack が Webhook を非推奨にしているわけではない**。アプリの Incoming Webhook は、Slack の公式の文書 (docs.slack.dev) では非推奨と書かれていない (2026-11-14 に、利用者と開発リードが公式の文書で確かめた)。
これは、上の性質を理由にした、arata としての判断である。

## 決定

### bot にそろえる

- **arata が勧める送り方・書き出す送り方は、bot トークンの方式だけ**にする
  - 監査を回すリポジトリの一式 (`arata repo init`) は、bot の方式だけを書き出す (ADR 0060)
  - `aratam config init` の雛形は、bot の方式にする (`bot_token_env: ARATAM_SLACK_BOT_TOKEN`、`channel` は空で、利用者が書く。Webhook の項目は空)
  - 文書 (`docs/aratam.md`、`examples/github-actions/README.md`)・`help ai`・見本から、Webhook を勧める記述と手順を外す。
    Webhook の項目の説明は、「非推奨の方式」の節に、今の利用者が読める形で残す

### Webhook は非推奨 (当面は動くまま残す)

- **Webhook の方式の設定は、これまでどおり動く**。送る中身・振り分け・終了コードは変えない
- **`aratam config check` と `aratam doctor` が、Webhook の方式の設定に WARN を出す**
  - ログの code は `SLACK_WEBHOOK_DEPRECATED` (`internal/codes` に足す。ADR 0054 の決まりで、WARN には code を付ける)
  - 文は、bot へ移すことと、読む場所 (`docs/aratam.md` 4-1 章の移し方) を案内する。「Slack が非推奨にした」とは書かない
  - `config check` は終了コードを変えない (WARN だけなら 0)。`doctor` は `warn` の行を 1 つ足す (ng にはしない)
  - `--format json` は、今ある項目 (`config check` の `.slack.method`) で読める。項目は消さない・意味を変えない
- **`aratam notify` と `aratam test-notify` は、WARN を出さない**。定時の実行のたびに同じ警告が出ると、ログの「INFO 以外」の行 (運用で気づくべきもの) が毎日 1 行増え、ほかの警告が埋もれる。
  気づく場所は、設定を直すとき (`config check`。PR の検査でも流れる) と、点検のとき (`doctor`) にする
- **外す (動かなくする) 時期は、決めない**。外すときは、別の ADR で決め、Release の本文で知らせる (互換を壊す変更)
- Webhook と bot の両方を書いた設定は、これまでどおり設定エラー (混在を受け付けない)

### bot へ移す手順 (文書に載せる)

1. Slack アプリを manifest (`deploy/slack/app-manifest.yaml`) から作り、ワークスペースに入れる。bot を、通知のチャンネルに招待する
2. トークン (`xoxb-…`) を、実行環境の秘密に入れる (`ARATAM_SLACK_BOT_TOKEN`)
3. `aratam.yaml` の `slack` の節を直す: `webhook_env` と `urgent_webhook_env` を空に、`bot_token_env` と `channel` (分けるなら `urgent_channel`) を書く
4. `aratam config check` → `aratam test-notify` (通常用と緊急用) で、届くことを見る
5. 届いたら、Webhook の秘密を消し、Slack の側で Webhook の URL を取り消す

### 気をつける点 (文書に載せる)

- **bot のトークンは、bot が入っているどのチャンネルにも書ける**。Webhook が 1 つのチャンネルにしか書けないのと比べて、漏れたときに書ける範囲が広い。
  読むことはできない (scope は `chat:write` だけ。`deploy/slack/app-manifest.yaml` とテストが固定している)。bot が入っていないチャンネルには書けない (`chat:write.public` を使わない)
- **範囲は、会社 (監査を任される組織) ごとに、リポジトリと Slack アプリを分けることで閉じる**。同じトークンを複数の会社のリポジトリに置かない。
  bot を招待するのは、通知に使うチャンネルだけにする

## 今後 (この ADR では決めない)

bot にそろえると、投稿の `ts` が返るので、次が作れる。どちらも今回の範囲ではない。作るときは、状態 (どの投稿がどの指摘か) の持ち方を、別の ADR で決める
(今は「スレッドへの返信・メッセージの更新や削除はしない。状態を持たない」と決めている。`docs/aratam.md` 4-1 章)。

- **スレッド**: 日次のまとめの投稿に、指摘ごとの詳細を返信として付ける
- **更新**: 指摘が対応済みになったときに、元の投稿を書き換える (`chat.update`)

## 検討した選択肢

- **両方を、同じ扱いで持ち続ける** (これまで): 背景のとおり、一式・文書・雛形が 2 通りになり、この先の機能は片方でしか作れない。採らない
- **Webhook を、いま外す**: 今の利用者の通知が、版を上げた日に止まる。通知が止まることは、監査が止まることと同じ重さ。当面は動くまま残し、WARN で知らせる
- **外す時期を、いま決める** (N 版後、など): 今の利用者が移るのにかかる時間が分からない。決めずに置き、外すときに別の ADR で決める
- **WARN を `notify` でも出す**: 気づきやすいが、毎日同じ行が出て、ほかの警告が埋もれる。設定を触るときと点検のときに限る
- **WARN ではなく、設定エラーにする**: 「当面は動くまま残す」にならない。採らない
- **「Slack が非推奨にした」と案内する**: 事実ではない。arata の判断として、理由 (送り先が固定、`ts` が返らない、消せない・更新できない) を書く
- **Webhook を「チャンネルが少ない利用者向け」として勧め続ける** (これまでの位置づけ): 権限は一番狭いが、利用者が最初に方式を選ぶことになり、後から bot の機能が要るときに移行が要る。
  書ける範囲の広さは、会社ごとにアプリを分けることと、招待するチャンネルを絞ることで抑える

## 結果

- 良い点
  - 勧める形が 1 つになる。一式が使う Slack の秘密は 1 つで、チャンネルを足す・変えるときに秘密は動かない (ADR 0060)
  - スレッドと更新を、1 つの方式の上に作れる
- 引き受けるコスト
  - **Slack アプリを作れない利用者** (ワークスペースの管理者の承認が得られない、など) には、勧める形が無くなる。Webhook は動き続けるが、非推奨の警告が出る
  - **トークンで書ける範囲が、Webhook より広い** (上の「気をつける点」)
  - 今の Webhook の利用者は、`config check` と `doctor` に WARN が出る。移すには、Slack アプリの作成と、設定の 4 行の変更が要る
  - `aratam config init` の雛形は、`channel` を書くまで `config check` を通らない (これまでの Webhook の雛形は、そのまま通った)。送り先は、利用者にしか決められない
  - 非推奨の方式のコードとテストを、外すまで持ち続ける
- 攻撃の対応表 (ADR 0058): 新しいチェックではないので変えない

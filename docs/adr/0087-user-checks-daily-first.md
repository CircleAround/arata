# 0087. ログインした利用者の総当たりのチェック (ADR 0071) を、利用者ごとのチェックの土台より先に、日の単位のクエリで実装する (0071 の 6 節の一部を置き換え)

- 日付: 2026-11-26
- 状態: 採用 (2026-11-26、開発リードの判断)

例の値はすべて架空 (利用者は `user:42`、パスは `/orders/:id`)。

## 背景

ADR 0071 は、ログインした利用者の総当たり (`user_denied`・`user_id_enumeration`・`user_path_breadth`) を、利用者ごとの**時の部品**で見ると決めた。
その 6 節に、次の決定がある。

- U1 (利用者の要約。軸は (時, 利用者)) は `user_multi_source` と共用し、クエリの持ち主は利用者ごとのチェックの土台 (`source_multi_user`・`user_multi_source` の担当)。
  この ADR の 3 つのチェックは U1 の値を読む側になる
- `request_lines` の時の単位の扱いは、土台の担当が決めて実装する。0071 はその決定に合わせる
- 異なりの数 (型の数・ID の数) は、時の異なりの数の和 (延べ) にする
- `collect: hourly` を書かない `request_lines` のソースでは、U1・U2 を日の頭から日の単位で流す (異なりの数は正確になる)

このままでは、0071 の実装は土台 (`request_lines` を時の単位で読む仕組み・U1・`source_multi_user`・`user_multi_source`) ができるまで始められない。
ユーザーが利用者ごとの分析の優先度を上げたので、順番を次にする。

1. 0071 の 3 つのチェックを、**日の単位**で実装する
2. 利用者の種類に合わないパスの型への要求を見る新しいチェック (別の ADR)
3. 段 1 の残り (`source_multi_user`・`user_multi_source`、`request_lines` の時の単位の読み方)

今の仕組みの事実 (この ADR を書いたときに読んだもの):

- `request_lines` のソースに `collect: hourly` を書くと、設定の誤りになる (`internal/config/collect_hourly.go`。時の境目をまたぐリクエストが割れるため。ADR 0065 の対象外)。
  つまり今、`request_lines` のソースはすべて日の頭から読み直す
- 日の頭から読み直すソースは、`collect --incremental` (ADR 0064) も、取得の回の `hourly` の判定 (ADR 0082。CloudTrail だけを要る 4 つのチェック) も読まない。
  読むのは、そのソースを要るチェックのあるプロファイル (0071 の 3 つは daily。0071 の 8 節) の run だけ
- 1 回の run は、窓の始まりを含む日の 0 時 (UTC) から窓の終わりまでを読む (設計書 3 章)。daily (窓 24h) なら、1 日に読む量は 1 日分から最大で約 2 日分 (実行の時刻が UTC の遅い時刻ほど多い)
- `request_lines` のソースが今流すクエリは、`yields: http_user` (ADR 0075) なら解釈率の 1 本、`yields: http_access` なら 2〜3 本
- `request_lines` の日次の集計は、行の数の上限 (10,000) に当たっても 1 日より細かくは分けない (当たれば `truncated`。設計書 2-4)

## 決定

### 1. U1 と U2 のクエリは 0071 の実装の PR が作る。最初は日の単位だけ

- U1 (利用者の要約) と U2 (ID の総当たり) のクエリは、**0071 の実装の PR が作って持つ**。0071 の 6 節の「U1 のクエリの持ち主は土台」を置き換える
- 軸は 0071 の 6 節の表の「時」を「日」に替えたもの。U1 は 2 段目 (日, 利用者, 型) → 3 段目 (日, 利用者)、U2 は 2 段目 (日, 利用者, 型, 対象 ID) → 3 段目 (日, 利用者, 型)。
  返す列・sort・`limit 10000`・`part_floor` の `filter` (確かめてから) は 0071 の 6 節のまま
- **すべての `request_lines` のソースで**、0071 の 6 節の最後の形 (日の頭から日の単位で流し、時の部品を作らず、日の値を直に作る) を使う。
  時の部品 (`metric_parts` の `user_summary`・`user_ids`) は作らない
- 決定: U1・U2 は、範囲の中の **UTC の 1 日ずつ**流す (解釈率のクエリと同じ。設計書 2-4)。各クエリは自分の範囲だけを読むので、読む量の和は変わらない。
  1 本に 2 日分を入れると、行の上限が 2 日の利用者の和にかかり、前日の完全な値の行が当日の途中の行に押し出されうる。日ごとに流せば上限は 1 日ごとにかかる。
  上限に当たっても割らずに `truncated` (下限) にする (日より細かく分けない今の規則のまま)
- 日の値 (`metrics`) の key・下限 (`store_min`)・上位 (`store_top`)・分布の行 (`user_ids_dist`) は 0071 の 6 節のまま。異なりの数は**その日の正確な異なり**になる (延べではない)
- 3 つのチェックの判定 (平常帯 2 種・閾値・7 日の窓・新しい利用者・`by` の除外・`related`) は 0071 のまま変えない
- `arata doctor` の費用の行 (ADR 0028) が U1・U2 の本数を数えるようにする (`QueryCount` に入れる)

### 2. 後で土台が時の単位にするときの約束

- 土台が `request_lines` を時の単位で読めるようにするとき、**U1 の持ち主は土台に移り**、土台が `user_multi_source` の列を U1 に足す (0071 の 6 節の「U1 は共用」はそのときに効く)
- 約束 (土台の PR が守る):
  - 0071 の 3 つのチェックの判定 (平常帯の作り方・閾値・窓) を変えない
  - 日の値 (`metrics`) の **key と意味を変えない**。件数 (拒否・ステータスごと・メソッドごと) は時の和でも同じ値になるので、時の部品から作ってよい
  - 異なりの数 (`user_templates`・`user_ids` とその `ids_ok`・`ids_denied`) の意味は「その日の正確な異なり」。時の延べに変えると、正規の利用者の値が膨らみ (0071 の 6 節)、
    切り替えた日から `baseline_days` の間、正確な値で作った平常帯と延べの値を比べることになる (誤りの報告が増える向き)。
    そのため、**U2 と U1 の異なりの列は、土台が時の単位にした後も日の単位で流す**。延べに変えたいときは新しい ADR で、平常帯の切り替え (混ぜない日の扱い) と合わせて決める
- 0071 の 6 節の「決定 (異なりの数は延べにする)」は、この約束で置き換える (時の部品を作らないので、延べにする理由が無くなった)
- 0071 の 8 節の「`user_id_enumeration` の high だけを hourly で評価する案」は、時の部品が前提なので、土台の後の候補のまま残す
  (日の頭から読み直すソースを毎時に読むと、毎回その日の 0 時から読むので、1 日に読む量が約 12 倍になる。ADR 0064 が `collect --incremental` で集めない理由と同じ)
- 0071 の 9 節 (怪しい IP の一覧とのつなぎ) は、`source_multi_user` の部品が前提なので、土台の後のまま

### 3. 当面、U1・U2 は日の単位だけで流す (費用と行の上限)

- 今は `request_lines` に `collect: hourly` を書けない (背景)。土台がそれを許した後も、2 節の約束のとおり U2 と U1 の異なりの列は日の単位で流す。
  `metric_parts` の U1・U2 の部品は、この ADR では作らない

#### 費用 (Insights のスキャン量)

Insights の費用は、クエリごとに範囲のログを全部読む量で決まる (ADR 0028・0031)。U1・U2 は `request_lines` の 1 段目 (request_id のまとめ) から流すので、1 本が 1 日に読む量は、ほかの `request_lines` のクエリ 1 本と同じ。

| `request_lines` のソース | 今の本数 | 0071 を入れた後 | 増え方 |
|---|---|---|---|
| `yields: http_user` (入口のアクセスログを別に読む。ADR 0075) | 1 (解釈率) | 3 | 3 倍 |
| `yields: http_access` | 2〜3 | 4〜5 | 約 1.7〜2 倍 |

- 1 本が 1 日に読む量は、daily の 1 日 1 回で、1 日分 (UTC の早い時刻に回す) から最大で約 2 日分 (遅い時刻に回す)。
  例 (架空の量): アプリのログが 1 日 1 GB なら、U1・U2 で 1 日に 2〜4 GB、30 日で 60〜120 GB、東京の単価 (0.0076 USD/GB) で月に約 0.46〜0.91 USD 増える。
  量はソースの量に比例するので、1 日 10 GB のアプリは約 4.6〜9.1 USD
- 0071 の 6 節の見積もり (U1 を共用して増えるのは U2 の 1 本、約 1.3 倍) との違い: U1 を共用しないので 1 本多く、時の単位で各時を 1 回だけ読む形
  (1 日に 1 日分) でもないので、1 本あたりも最大で約 2 倍になる。土台が U1 を時の単位にすれば、U1 の分は `user_multi_source` と共用になり、その分は減る
- 新しいチェックをプロファイルに入れなければ流さない (0071 の 6 節のまま)。daily を UTC の早い時刻に回すと 1 日分に近づく (ADR 0065 の 5 節の記録と同じ考え)

#### 1 日の窓で 10,000 行の上限に当たる心配

- U1 の行は「その日にログインして要求のあった利用者の数」(時の単位なら「その時の数」)。**1 日にログインした利用者が 10,000 を超えるアプリで当たる**
- U2 の行は、`part_floor` の `filter` が動けば `ids` が `part_floor` (既定 3) 以上の (利用者, ID のある型) の数。動かなければ ID のある型を開いた (利用者, 型) の全部
  (例: 1 日 3,000 人が ID のある型を 3 つずつ開けば 9,000 行で、上限に近い)。時の単位より 1 本に入る利用者が多いので、上限に当たりやすい
- 当たったときに落ちるのは sort の下の側 (U1 は `拒否の件数 + 型の数` の小さい利用者、U2 は `ids` の小さい行) で、0071 の 6 節のとおり判定の向き (見落とさない側) は崩れない。
  閾値 (`min_count` 30・`min_distinct` 50・`min_templates` 50) は、上限の境目になる値 (10,000 番目の値) より大きいと見込む。アプリの平常帯はいちばん多い利用者から作るので、当たっても正しい
- 当たったときに崩れるもの: 分布の行の p50・p99 (0071 の 6 節のとおり、その日の行が上限に当たっていなければだけ持つ) と、`store_min` から上限の境目までの値 (0 と同じ扱いになる)。
  どちらも判定の閾値より下なので、判定は変わらない。`truncated` は finding の data と coverage に出す (今の規則)
- 見込み: 利用者が 1 日 10,000 を超えるアプリは、段 1 の行を入れる利用者の中では大きい側。当たる利用者が出たら、上限で割らずに、土台の時の単位 (1 時間に 10,000) を待つか、
  そのアプリに合わせた別の手当て (U1 を利用者の種類で分けて流す、など) を新しい ADR で決める。実データの行の数は、アプリの利用者の ID の行が本番に入ってから `--dry-run` で確かめる

### 4. 設計書の「`request_lines` は時の単位にできない」は、土台の PR で書き直す

- 設計書 2-4 と 3 章 (ADR 0065 の決定の「対象外」と「既定にする道筋」) の「`request_lines` は時の単位にできない」は、**この ADR では触らない**。
  この ADR の後も `request_lines` は日の頭から読み直すので、その記述は正しいまま。書き直すのは、時の単位の読み方を実装する土台の PR (0071 の 6 節のまま)
- 0071 の実装の PR は、設計書に U1・U2 のクエリ (日の単位) と日の値を足す。そのとき「時の部品」の記述は書かず、2 節の約束 (異なりの列は日の単位のまま) を「決定:」で残す

## 検討した選択肢

- **土台を先に作る (0071 の 6 節のまま)**: U1 を初めから共用でき、クエリの本数と読む量が少ない (各時を 1 回)。利用者ごとの分析の優先度が高く、
  土台の時の単位の読み方 (時の境目をまたぐリクエストの扱い・余白・日の頭から読む形との同値の確かめ・`config` の許し方) は設計が大きい。
  土台を待つと、優先度の高い 3 つのチェックが遅れる。却下
- **0071 の実装の PR で、`request_lines` の時の単位の読み方まで作る**: U1・U2 を初めから時の部品にでき、後で作り直さない。
  土台の決める部品を 0071 の担当が先に決めることになり、0071 の 6 節の「1 人が持つほうが食い違わない」と合わない。範囲も 0071 の見積もりの外。却下
- **土台が時の単位にした後、U2 と U1 の異なりの列も時の延べにする (0071 の 6 節のまま)**: クエリが時の部品にそろい、毎時に途中の値を作れる。
  日の値の意味が正確な異なりから延べに変わり、切り替えの前後で平常帯と比べる値の数え方がずれる。却下 (2 節)。要るときは新しい ADR で切り替えと合わせて決める
- **U1・U2 を 1 本にまとめる (軸 (日, 利用者, 型))**: 本数が 1 本減る。行の数が「利用者 × 型」になり、日の単位では上限に当たりやすく、落ちるのは広く浅く触る試しの行そのもの (0071 の 6 節)。却下
- **U1・U2 を範囲の全部 (2 日分) で 1 本に流す**: 本数の数え方は同じ。行の上限が 2 日分にかかる。却下 (1 節)

## 結果 (良い点・引き受けるコスト)

- 良い点: 0071 の 3 つのチェックを、土台を待たずに実装できる。異なりの数が日の正確な値になり、延べの膨らみ (正規の利用者が同じものを時をまたいで開く) が無い
- 良い点: 土台の後も、チェックの判定と日の値の key・意味が変わらない (2 節の約束)。平常帯をためなおさない
- 引き受けるコスト: `request_lines` のソースのクエリが 2 本増え、1 本あたりも日の頭からの読み直しで最大で約 2 倍読む (3 節の表)。土台の後も U2 と U1 の異なりの列は日の単位のまま
- 引き受けるコスト: 1 日にログインした利用者が 10,000 を超えるアプリでは U1 が上限に当たり、分布の p50・p99 が欠ける (判定は変わらない)
- 引き受けるコスト: 土台が U1 を持つときに、U1 を時の単位の列 (件数) と日の単位の列 (異なり) に分けるか、U1 を日の単位のまま共用するかを、土台の担当が決める

## 手間の見積もり (0071 の見積もりの置き換え)

- `path_ids` の設定・`config check`・Insights の型の組み立て・Go の正規化との同値のテスト・ファズ: 2 日 (0071 のまま)
- U1・U2 のクエリ (日の単位、1 日ずつ)・日の値 (正確な異なり)・上位と分布の保存・doctor の本数: 2 日 (0071 の「U1 に足す列・U2・時の部品」を置き換え。U1 を作る分が増え、時の部品の分が減る)
- 3 つのチェック・playbook 3 つ・threats の更新・シミュレーターとゴールデン: 3 日 (0071 のまま)
- 合計 約 7 日 (土台を待たない)

## 未確認の点 (0071 の「未確認の点」への足し引き)

- 足す: 1 日分の範囲で、3 段の `stats` の 2 段目 (日, 利用者, 型, 対象 ID) の中間の結果の大きさの上限 (0071 は 1 時間で見積もっていた)
- 足す: 実データの、1 日あたりのログインした利用者の数と (利用者, ID のある型) の数 (U1・U2 の行の見込み)。アプリの利用者の ID の行が本番に入ってから
- 土台に移す: `request_lines` の時の境目と余白の扱い (シミュレーターで、時の単位で流した日の件数 = 日の頭から流した件数)
- そのまま: `fields` の `if` と `coalesce`、`parse` の区間、`stats` の後の `filter` (`part_floor`)、手元の枠組みで作る試しのログでの値

# 0058. 公開された攻撃の事例ごとに、arata で見える段階と見えない段階を、出典の URL 付きの対応表として持つ

- 日付: 2026-11-14
- 状態: 採用

## 背景

チェックは増えてきたが、「このチェックは、実際のどんな攻撃の、どの段階を見るためのものか」を示す文書が無かった。
利用者は、チェックを入れるかどうかと、入れても何が見えないかを、チェックの説明だけから判断していた。

2026-10 から 11 にかけて、GitHub のアカウントを乗っ取って CI の秘密を盗む攻撃が続けて報告された。
こうした攻撃の大半の段階 (GitHub の中、実行環境の通信) は arata の読む記録に無く、AWS に現れるのは一部の段階だけである。
「見える」とだけ書くと、利用者は守られていると誤解する。見えない段階と理由を、同じ場所に書く必要がある。

もう 1 つの問題は出典の読み方である。調査の記事には、被害の環境で観測したことと、スクリプトを解析して分かった機能が混ざっている。
区別せずに「この攻撃では AWS でアクセスキーが作られた」と書くと、出典が言っていないことを書くことになる。

## 決定

- 事例 1 つを 1 ファイル (`docs/ai/threats/<id>.md`) に書き、バイナリに埋め込んで `arata help ai threats [<id>]` で出す。人向けの入口は `docs/threats.md` (README から案内)
- 見出しは固定: 概要 / 出典 / 攻撃の段階と arata で見えるもの / arata では見えないもの / 予定している改善
- 段階の表は 5 列 (攻撃の段階 / 出典の書き方 / arata のチェック / 記録 / 出るもの)。「出典の書き方」は 観測 / 機能 / 推定 / 記述 / 想定 のどれか。
  出典に無く arata の側で想定した段階 (盗まれたキーが後で使われる、など) は「想定」と書いて区別する
- 出典は、一次情報か調査した会社の記事の URL と日付。書く人が自分で読んで確かめたものだけを入れる。文は写さず要約する
- 一覧の表とチェックごとの表は、事例の本文から作る。`docs/threats.md` には同じ表を置き、生成したものと一字一句同じことをテストで固定する (`help ai logs` の表と同じやり方)
- playbook の見出しに「関連する事例」を足す (6 つ目)。事例への案内か、「対応する公開の事例はまだ無い」を書く。事例の表と食い違えばテストが落ちる
- aratam が LLM の system に入れる playbook からは、この節を除く (`ai.PlaybookProcedure`)。aratam に渡る本文は、この決定の前と変わらない
- これから作るチェックは、表ではなく「予定している改善」に、予定と分かるように書く。表のチェックの名前は実在するものに限る (テストで固定)
- 攻撃の基盤の値 (IP、ハッシュ) は書き写さない (古くなる。必要な人は出典を読む)。利用者の環境で見た事実は書かない (ADR 0036)

## 検討した選択肢

- **`docs/threats.md` 1 つに全部書く**: 却下。埋め込みの文書と二重に持つとずれる。1 つにまとめて埋め込むと、事例が増えるたびに LLM が読む量が増える (文書は 150 行の目安)。
  事例ごとのファイルなら、要る事例だけを引ける (playbook と同じ形)
- **MITRE ATT&CK の技法の ID との対応表にする**: 却下。技法の単位では「この機能で何が見えるか」が利用者に伝わりにくく、出典が観測したのか機能なのかの区別も書けない。
  事例の単位のほうが、公開の記事と突き合わせて確かめられる。段階の名前は ATT&CK の戦術に近い言葉を使う
- **playbook には手を入れず、対応表からだけ引く**: 却下。指摘を受けた人が最初に読むのは playbook で、そこから背景へたどれないと使われない。
  ただし aratam の system にはこの節を入れない。入れてみると、既存のテストの run で playbook の合計が上限 (24 KiB) を超え、playbook が 1 つ丸ごと落ちた。
  対処手順が減るほうが害が大きい。aratam の LLM は help を引けないので案内も使えない
- **事例の無いチェックは何も書かない**: 却下。書き忘れと「探したが無い」を区別できない。決まった文言を書かせて、テストで確かめる
- **表に「予定」のチェックも並べる**: 却下。表を見た人が、今あると読み違える。予定は別の節に分ける

## 結果 (良い点・引き受けるコスト)

- 良い点: チェックを足す PR で、「どの攻撃のどの段階のためか」と「何が見えないか」を必ず書くことになる。利用者と LLM が同じ文書を引ける
- 良い点: 出典が観測と書いていない段階を、観測として伝えずに済む
- コスト: チェックの重大度や条件を変えるたびに、事例の表も直す。表の文言まではテストで縛れないので、レビューで確かめる
- コスト: 出典の URL は消える・書き換わることがある。リンク切れはテストで見ていない (テストは外に接続しない)。気づいたら直す
- コスト: playbook の見出しが 6 つになる (`arata help ai playbook <check> --format json` の sections が 1 つ増える。項目を足す変更で、スキーマは変わらない)。
  aratam は節を除いて渡すので、通知の要約には影響しない

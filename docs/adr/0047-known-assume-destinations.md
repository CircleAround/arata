# 0047. 外向きの引き受けは、行き先として既知のアカウントへの MFA ありのものだけ報告しない (`assume_destinations`)

- 日付: 2026-11-13
- 状態: 採用

## 背景

管理用のアカウント (例 `123456789012`) の社員 (IAM ユーザー) が、運用を受託している別のアカウント (例 `111122223333`) のロールに、
MFA 付きでスイッチロールするのが通常業務、という使い方がある。`unknown_assume_role` はこれを外向きの引き受けとして、
人 × ロールの組ごとに初回 high で報告し、人が ack してきた。受託先のアカウントや社員が増えるたびに、初回の報告と ack が組の数だけ増える。

既知リスト (`principals`) は **呼び出し元** の主体だけを照らす。社員を `principals` に書けば報告は止まるが、その社員の
**知らないアカウントへのスイッチロールまで止まる**。外向きの引き受けで危ないのは「自アカウントの主体 (の認証情報) が、知らない外部アカウントで使われた」
ことなので、呼び出し元の承認では守りが落ちる。

## 決定

**既知リストに、外向きの引き受けで「行き先として既知のアカウント」を書く節 `assume_destinations` を足す。
`unknown_assume_role` は、次の全部を満たす引き受けだけを報告しない。**

1. 向き (`direction`) が外向き (outbound。監査対象のアカウントの主体が、別のアカウントのロールを引き受けた)
2. 引き受けたロールのアカウントが、`assume_destinations` に **期限内で** 載っている (`roles` を書いた項目は、そのロールだけ)
3. MFA が「あり」(`mfa: true`。その組の窓内の全イベントで)

それ以外 (知らない行き先、MFA なし・不明・混在、内向き、内部、向きが決まらない、期限切れ、絞ったロールの外) は今までどおり high。

```yaml
assume_destinations:
  - account: "111122223333"        # 行き先のアカウント (12 桁)。必須
    note: 運用を受託しているアカウント   # 必須。なぜこのアカウントに入るのが通常業務か
    approved_by: alice
    approved_at: 2026-11-13
    expires: 2027-03-31            # 任意。契約の終わりに合わせる
  - account: "444455556666"
    roles: ["ReadOnly", "ops-*"]   # 任意。書けばこのロールだけ (ロール名の glob。ARN の role/ より後ろ)
    note: 読み取りと運用のロールだけ
```

細部:

- **`principals` の `account:` とは別の節にする。** あちらは「呼び出し元として既知」(そのアカウントの全主体を承認する) で、意味が逆。
  同じ `account:` という書き方に条件を足すと、片方のつもりで書いた項目がもう片方も通す。節を分け、行き先を既知にしても呼び出し元は承認されず、
  呼び出し元を承認しても行き先は既知にならない (ファズで固定する)
- **書けるのはアカウントと、任意のロール名の glob だけ。** `account` は 12 桁の数字 (glob やパターンでアカウントを広げられない)。
  `roles` は IAM がロールの名前とパスに許す文字と `*` `?` だけで、ARN は書けない (アカウントを決めるのは `account` だけ)。先頭から末尾までの一致。
  既定はアカウントの全ロール。受託先の中で管理者のロールだけは毎回見たい、という絞り方ができる
- **`note` は必須。** 行き先を既知にするのは「このアカウントに入るのは通常業務」という判断で、理由 (契約・受託の内容) の無い項目は後から外せない
- **MFA は「あり」と確かめられたときだけ。** `mfa` は記録に証拠があるときだけ true になる (設計書 6 章)。`unknown` (記録に項目が無い) を「あり」に寄せない。
  1 つの組の中で MFA ありとなし・不明が混ざった (`mixed`) ときは、組の全体を報告する
- **報告しなかった分は info で残す。** 行き先のアカウントごとに 1 行 (Key は `known-destination:<アカウント>`)。件数・呼び出し元・ロール
  (それぞれ 20 件まで。総数は `callers_total` / `roles_total`)・送信元 IP・失敗の有無を data に持つ。info は件数にも通知にも数えない (ai_path_usage と同じ)。
  Fingerprint は固定する (呼び出し元やロールの顔ぶれは毎時の窓で変わるので、入れると毎回 changed になる)
- **既知にした行き先なのに報告するとき**は、data に `destination_status` (approved / expired) を出し、見出しの括弧に理由を足す
  (「行き先は既知だが、MFA ありと確かめられないので報告」「行き先の承認は期限切れ」)。既知にしたのに報告が続く理由を、見出しだけで分かるようにする
- **Key・重大度・Fingerprint は変えない。** 既存の finding (ack 済みを含む) は changed にならない
- **既存の ack 済みの finding**: 行き先を既知にすると、次の evaluate の冒頭 (と `approve --destination` の直後) で、条件を満たす finding
  (外向き・その行き先・finding の `mfa` が true) を resolved にする (`resolved_reason: known_destination`)。open・acked・snoozed のどれも同じ。
  MFA が無い・不明の finding、この版より前に作られて `direction` / `mfa` を持たない finding は、そのまま残る (次に観測されたときに data が更新される)。
  行き先を消す・期限が切れると、次の引き受けは新規として報告される。info の行は、行き先の期限内の項目が無くなったら resolved にする (`destination_removed`)
- **`arata approve <id> --destination`** で、finding (unknown_assume_role の外向きで MFA あり) の行き先を `assume_destinations` の末尾に足せる
  (差し込み方は ADR 0010 と同じで、ほかの行は変えない。節が無ければファイルの末尾に足す)。主体は承認しない。
  `--destination-role <glob>` (複数可) でロールに絞れる (finding のロールに一致するものを求める)。MFA ありと確かめられない finding には使えない
  (行き先を足しても報告が続き、「approve したのに消えない」になる)。アカウントは finding の data (ログ由来の値) から取るので、
  12 桁のロールの ARN として読め、`role_account` と一致するときだけ書く。`arata review --format json` は、使える finding に `approve_destination` を出す
- **`arata config check`** (オフライン): 12 桁でない `account`・`note` なし・`expires` の形・空や不正な `roles`・知らないキーは ng (run も同じ理由で止まる)。
  重なる項目 (同じアカウントで、片方がアカウント全体か、絞ったロールの集合が同じ) と、期限の切れた項目は warn。
  期限切れを warn にするのは行き先だけ (主体の期限切れは finding が知らせる。行き先は、契約が続いているのに延ばし忘れると high が組の数だけ戻る)
- **`arata doctor`**: 行き先に監査対象のアカウントそのものを書いていたら ng。同じアカウントのロールの引き受けは内部で、この項目では止まらない
  (書いた人の期待と違う)。オフラインでは監査対象の ID が分からないので、doctor が `sts:GetCallerIdentity` で比べる (ADR 0045 と同じやり方)。
  行き先が無ければ問い合わせない

## 検討した選択肢

- **MFA があれば、行き先に関係なく報告しない** — 却下。書くものが無く、いちばん楽だが、守りが 3 つ落ちる。
  - **知らないアカウントへの移動**: 外向きで見たいのは「自アカウントの主体が、知らない外部アカウントで使われた」こと。MFA は本人確認で、行き先の妥当性は何も言わない。
    攻撃者の用意したアカウントのロールへの引き受けも、MFA があれば黙る
  - **MFA 後のセッションの奪取**: MFA 済みのセッション (コンソールのセッション、`GetSessionToken` の一時キー) を奪われると、その後の AssumeRole は
    「セッションが MFA で認証済み」として記録される。MFA の有無だけでは、本人と奪った者を区別できない
  - **本人の不正**: 正規の社員が、業務と無関係のアカウントのロールを引き受けても黙る
- **社員 (呼び出し元) を `principals` に書く** — 今もできる。知らないアカウントへの引き受けまで止まる (背景のとおり)
- **`principals` の `account:` に条件 (`as: destination` など) を足す** — 却下。呼び出し元の承認と行き先の既知を同じ節に混ぜると、
  片方のつもりで書いた項目の意味を取り違えやすい。`Principal` の照合 (new_principal・iam_changes なども使う) にも条件が入る
- **人 × 行き先の組で書く (`principal` と `account` の両方)** — 却下。社員が増えるたびに項目が増え、今の ack と手間が変わらない。
  新しい社員そのものは new_principal が報告する
- **ロールの ARN・`arn_pattern` で書く** — 却下。行き先はアカウントが単位 (契約の単位)。ARN の glob はアカウントの欄まで広げられ、
  アカウントを固定する検査 (ADR 0037) が別に要る。絞りたいときは `roles` (名前の glob) で足りる
- **報告しなかった分を何も残さない** — 却下。黙って消えると、既知リストの項目が効いているのか、引き受けが無かったのかを区別できない。
  件数だけを coverage に出す案は、誰がどのロールに入ったかを後から見られない
- **報告しなかった分を、組ごとに info で出す** — 却下。組の数だけ行が出て、減らしたかった行が info に移るだけになる
- **MFA なし・不明でも、行き先が既知なら重大度を下げる (medium)** — 却下。既知の行き先への MFA なしの引き受けは、漏れたアクセスキーの使われ方そのもの

## 結果 (良い点・引き受けるコスト)

- 受託先のアカウントを 1 件書けば、社員とロールが増えても初回の報告と ack が要らない。知らないアカウント・MFA の無い引き受けは今までどおり high
- 既知リストに、呼び出し元とは別の節が 1 つ増える。`account:` が 2 か所で違う意味を持つので、文書と `config check` の文言で区別する
- **残るリスク**: 既知の行き先への MFA ありの引き受けは、誰のものでも黙る。次は別の手段で補う
  - MFA 後のセッションの奪取: 行き先が既知なら、この規則では見えない。`principal_new_source` (いつもと違う送信元・リージョン) と、行き先のアカウント側の監査で補う
  - 行き先のアカウントの中で、より強いロールに入る: `roles` で絞る (絞ったロールの外は報告される)
  - 契約が終わった後も項目が残る: `expires` を契約の終わりに合わせる。終わったら項目を消す (`config check` が期限切れを warn にする)
  - 新しい社員・知らない主体: `new_principal` が報告する (行き先の既知は主体を承認しない)
- MFA の記録が取れない引き受け (長期のアクセスキーでの呼び出しなど。`mfa: unknown`) は報告が続く。止めたいなら、呼び出しに MFA を付ける運用に直す
- info の行が、行き先のアカウントごとに 1 つ増える (hourly のプロファイルなら毎時更新される)
- `config check` が出す既知リストの件数の行に `assume_destinations N` が増える (ゴールデン `config_check.txt` を更新)

# 0083. サービスが引き受けるロールでは、実行環境の下回りの書き込み (固定の一覧) を `principal_new_source` の新しい送信元の書き込みに数えない

- 日付: 2026-11-22
- 状態: 採用
- 関係する判断: ADR 0027 (`principal_new_source`。サービスが引き受けるロールの low を出さない)、0064 (主体の活動の集計を時ごとにする)、
  0037 (ログ由来の値は信用せず、守りを規則に置く)、0054 (機械が読む出力。項目を足すのは互換)

## 背景

実際の環境で、AWS Lambda が引き受けるロール (`service_assumed: true`) に `principal_new_source` の medium が出た。理由は `new_source_writes` だった。

- その日のそのロールの記録は 154 件。うち 132 件は `kms:Decrypt` (読み取り)。成功した書き込みは `logs:CreateLogStream` の 22 件だけ
  (user agent は Lambda の実行環境のもの)
- 関数は VPC の外にあり、送信元は実行環境ごとに AWS の EC2 の範囲の /24 で毎回変わる
- 今の作りでは、cloudtrail collector が成功した `readOnly=false` を `principal_source_writes` に数え、チェックは書き込みが `min_writes` (既定 5) 以上なら、
  サービスが引き受けるロールでも medium にする

Lambda の実行環境は、関数のログを書く前に、その実行環境の分のログストリーム (初回はロググループも) を関数のロールで作る。
送信元が毎回変わり、作る操作が書き込みなので、呼び出しの多い関数ほど毎日 medium になる。ADR 0027 でサービスが引き受けるロールの low を止めたのと同じ理由の誤報が、
medium の側に残っていた。

## 決定

1. **実行環境の下回りの書き込み**を、`eventSource` と `eventName` の組の**固定の一覧**で定める (`record.RuntimeWrite`)。今は
   `logs.amazonaws.com` の `CreateLogGroup`・`CreateLogStream` の 2 つ。設定では足せない。一覧に足すのは、次を満たす操作に限る (この ADR を置き換える ADR で足す):
   - その操作だけをされても、資格を持ち出した側が得るものが無い (読み出し・権限・設定・計算資源を変えない)
   - 実行環境が関数の代わりに必ず行い、呼び出しの多さに比例して増える
2. cloudtrail collector は、成功した書き込みのうち一覧の操作を、新しい metric `principal_source_runtime_writes` (key は `principal_source_writes` と同じ
   `<主体 ARN>|<送信元>`。0 なら出さない) にも数える。`principal_source_writes`・`principal_write_region` の数え方は変えない。
   collector は主体がサービスに引き受けられたかを知らないので、すべての主体について数える
3. `principal_new_source` は、**サービスが引き受けるロール** (保存済みの `AssumeRole` の呼び出し元がサービス主体。ADR 0027) のときだけ、
   新しい送信元からの書き込みから `principal_source_runtime_writes` を差し引いて `min_writes` と比べる
4. 変えないもの:
   - 新しいリージョンの判定 (`principal_write_region` は下回りの書き込みも数える。ふだん書かないリージョンでの書き込みは、下回りでも medium)
   - access_denied との相関 (新しい送信元 + 拒否の急増は high)
   - ほかの書き込み (一覧の外の書き込みは、サービスが引き受けるロールでも今までどおり数える)
   - IAM ユーザーと、サービスが引き受けないロール (差し引かない)
   - Fingerprint と Key
5. 足す前の版で集めた日には `principal_source_runtime_writes` の行が無い。その日は 0 として扱う (今までと同じ判定になる)。テストで固定する。
   過去の日を集め直さない限り、その日の誤報は残る (新しい版で集めた日から消える)
6. finding の data に `runtime_writes_excluded` (差し引いた件数。0 なら出さない) を足す。`writes_from_new_sources` と `new_sources` の `writes` は
   差し引く前の件数のまま (意味を変えない)。見出しには「うち実行環境の下回りの N 件は数えない」を添える
7. 期間レポートの推移表には出さない (ほかの主体の活動の集計と同じ)

## 検討した選択肢

- **user agent で見分ける** (Lambda の実行環境の user agent の書き込みを数えない): 却下。user agent は呼び出す側が自由に名乗れる。
  資格を持ち出した側が同じ値を名乗れば、どの書き込みも数えさせずに済む抜け道になる
- **invokedBy で見分ける**: 却下。`userIdentity.invokedBy` は AWS のサービスが主体の代わりに呼んだ記録に付くもので、
  実行環境がロールのセッションで呼んだ操作 (この誤報の記録) には付かない。見分ける材料にならない
- **allowlist の `source_ips` に AWS の範囲を書く**: 却下。持ち出した資格を使う攻撃者の EC2 も同じ範囲にある。その範囲を既知にすると、
  そのロールの新しい送信元が全く出なくなり、書き込み・拒否との相関まで鈍る
- **`min_writes` を上げる**: 却下。すべての主体の検知が鈍る。サービスが引き受けるロールだけに別の下限を持たせても、
  呼び出しの多い関数ほど下回りの書き込みが増えるので、下限を決められない (攻撃者の書き込みも下限まで隠れる)
- **サービスが引き受けるロールの `new_source_writes` をやめる** (書き込みの件数では medium にしない): 却下。持ち出したセッションでの書き込みを拾う唯一の材料
  (ADR 0027 の「持ち出したセッションの悪用は書き込みで medium 以上として拾う」) を捨てることになる
- **一覧を設定で足せるようにする**: 却下。利用者が書き込みの多い操作を足すと、そのまま検知の穴になる。一覧の条件 (決定 1) を満たすかは ADR で判断する

## 結果

- 良い点: Lambda などのロールで、ログの置き場所を作るだけの日の medium が出なくなる。ほかの書き込みが下限以上あれば今までどおり medium
- 良い点: 判定は `eventSource`・`eventName` の完全一致の固定の一覧だけに頼る。どちらも呼び出す側が偽れない (操作そのもの)
- 引き受けるコスト: 持ち出したセッションで `CreateLogGroup`・`CreateLogStream` だけをされても、新しい送信元の書き込みとしては出ない
  (サービスが引き受けるロールの low は元から出ないので、何も出ない)。得るものが無い操作なので引き受ける。新しいリージョンでなら出る
- 引き受けるコスト: metric の行が増える (下回りの書き込みのある主体 × 送信元 × 時)。主体の活動の集計の見積もり (設計書 5 章) の範囲に収まる
- 引き受けるコスト: 足す前の版で集めた日は、集め直すまで今までの判定のまま

# 0001. エンジンの責務は収集・保存・差分判定・レポート生成まで

- 日付: 2026-10-21
- 状態: 採用

## 背景

AWS ログの定期監査は CircleAround が運用を預かる複数の顧客システムで共通化できる一方、
「どう定期起動するか」「どこへ通知するか」「LLM で要約するか」は顧客ごとに判断が割れる
(オンプレ cron、Lambda、AgentConsole など)。また Lambda 方式には「侵入されると監査の仕組みごと改ざんされる」懸念がある。

## 決定

arata は **収集 → 保存 → 差分判定 → レポート生成 (report.json / report.md)** までを担い、
通知・起動・LLM 要約は行わない。組み込み側は終了コードと report.json の `summary` で通知を分岐する。

LLM の役割は「危険の判定を代行する」ことではなく「人が短時間で判断できる材料に整える」こと。
重大度の下限による緊急通知、LLM 失敗時の report.md 直接投稿、実行漏れの直接通知は組み込み側で規則として固定し、
LLM が critical を沈黙させる経路を作らない。

## 検討した選択肢

- エンジンに Slack 通知や Bedrock 呼び出しを内蔵する: 顧客ごとの差を設定で吸収しきれず、通知経路の障害とエンジンの障害が混ざる。却下
- エンジンを AWS 内 (Lambda) 専用にする: 侵害時の改ざんリスクと、オンプレ運用の顧客に合わない。却下

## 結果

- 同じバイナリがオンプレ cron でも Lambda でも動き、通知経路は顧客ごとに選べる
- 監査結果の「解釈」は LLM や人の側に残るため、エンジンのテストは決定的に書ける
- 組み込み側 (cron スクリプト、skill、SNS 連携) を別途用意する必要がある

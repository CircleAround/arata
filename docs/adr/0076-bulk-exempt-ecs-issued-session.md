# 0076. `bulk: exempt` で外すのを、ECS の `AssumeRole` で発行された認証情報が直後に使われた読み取りだけにする

- 日付: 2026-11-20
- 状態: 採用

## 背景

ADR 0073 は、allowlist の `secrets_access` の項目に `bulk: exempt` を書いた「主体 × 秘匿値」を、secret_access の一括読み出しの数から外した。
外すのは主体が AWS のサービスに引き受けられたロールのときだけ (0073 の 4 節) だが、**その主体の読み取りなら、いつ・どこからでも**外れる。
0073 の「引き受ける見逃し」のとおり、実行用のロールの一時的な認証情報を盗まれて外で使われ、外した組だけを読まれると、secret_access には何も出ない
(principal_new_source も、読むだけなら出ない)。0073 の 4 の 3 は「セッションの単位で絞る」形を、後で足せるものとして残していた。

使える印の候補と、それぞれ使えない理由は次のとおり (0073 と同じ):

- `invokedBy`: 実際の記録の読み取りには無い (0073 の背景の 6)
- `userAgent`: 呼ぶ側が書ける (ADR 0037・0055)
- 送信元 IP: この形の利用者は NAT を使わず、サービスのロールの送信元は毎回変わる (ADR 0027)。固定の出口で絞る形は 0073 で入れないと決めた
- デプロイの操作 (`UpdateService`・`RunTask` など) との突き合わせ: タスクはデプロイの外 (スケール・入れ替え・定時のジョブ) でも起動する。0073 で却下した理由 (攻撃者もデプロイの操作ができる) も残る

残るのは、AWS が発行した値で読み取りと発行を結ぶ形である。

### 実際の記録で確かめたこと (2026-11-19)

出典: 2 つの本番の環境の CloudTrail の過去 3 日を、2026-11-19 に開発リードが読んだ形。アカウント・ロール・パラメータの名前と値は書かない。

1. 実行用のロールの秘匿値の読み取り (`GetParameters`) は計 1033 件。**全件が**、同じセッション名 (16 進 32 桁) の `ecs-tasks.amazonaws.com` の `AssumeRole` の後にあった
2. `AssumeRole` から読み取りまでは最大 11 秒 (中央値 0〜1 秒、p95 4 秒以下)
3. `AssumeRole` の `responseElements.credentials.accessKeyId` と、読み取りの `userIdentity.accessKeyId` は全件一致した (読んだ範囲の時刻の端で、対になる記録が範囲の外にあった 1 件を除く)
4. 読み取りは全件 `invokedBy` が無く、`userAgent` は Fargate のエージェントの名乗り。`ecs-tasks.amazonaws.com` の `AssumeRole` には、セッション名が `ECSIAMRoleChecker-` で始まるものも多い (読み取りには使われていない)
5. タスクのロール (実行用でない) が秘匿値を読む記録は無かった

### 公式文書で確かめたこと

0073 の背景の「公式文書で確かめたこと」の 1 (実行用のロールの認証情報は ECS のエージェントが使い、タスクのコンテナからは直接使えない。信頼ポリシーの主体は `ecs-tasks.amazonaws.com`) を前提にする。
`AssumeRole` の応答の `credentials.accessKeyId` が CloudTrail の記録に入る形と、読み取りの `userIdentity.accessKeyId` は、上の実際の記録で確かめた
(CloudTrail のユーザーガイドの userIdentity の節にも `accessKeyId` の項目がある: <https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-user-identity.html>)。

## 決定

### 1. 外すのは「ECS が発行した認証情報が、発行の直後に使われた」読み取りだけ

`bulk: exempt` の項目に一致する秘匿値の読み取りを、一括読み出しの数から外すのは、次の全部を満たすときだけにする。

- (a) 読み取りの `userIdentity.type` が `AssumedRole` で、`userIdentity.accessKeyId` が一時的な認証情報の形 (`ASIA` + 英大文字・数字 16 桁)
- (b) 同じキーを `responseElements.credentials.accessKeyId` に持つ、成功した `AssumeRole` が保存済みである。その `AssumeRole` は
  呼び出し側が `userIdentity.type: AWSService` で `invokedBy` が `ecs-tasks.amazonaws.com`、`requestParameters.roleArn` が読み取りの主体 (ロール)
- (c) 読み取りの時刻が、その `AssumeRole` の時刻から `-5 秒` 以上、`bulk_exempt_within` (2 節) 以下
  (`-5 秒` は記録の時刻が秒の単位で、STS と SSM・Secrets Manager の記録の時刻が別に付くため。実際の記録では負の差は無かった)

1 つでも満たさない読み取りは今どおり数える。外すかは**秘匿値ごと**に決める: 窓のその主体の、その秘匿値の読み取りが**全部**外せるときだけ外す。
1 回でも外せない読み取りがあれば、その秘匿値は数える (同じ秘匿値を、起動時にも外からも読まれた形を隠さない)。

- 0073 の 4 節 (サービスに引き受けられたロールのときだけ) は残す。(b) を満たせば 4 節も満たすが、`bulk_exempt_ignored: not_service_role` の区別 (人の SSO のロールに書いた誤り) を残すため
- 外すサービスは `ecs-tasks.amazonaws.com` だけ (固定)。Lambda・EC2 のインスタンスプロファイルは、発行と使用の形を実際の記録で確かめていないので外さない
  (0073 では外れていた。挙動の変更で、Release の本文に書く。足すときは記録で確かめてから新しい ADR で)
- `ECSIAMRoleChecker-` のセッションは特別に扱わない。ECS が発行したキーであることは同じで、読み取りに使われなければ突き合わせに出てこない

### 2. 窓の長さは設定 `secret_access.bulk_exempt_within` (既定 2 分、上限 15 分)

```yaml
checks:
  secret_access:
    bulk_exempt_within: 2m    # bulk: exempt で外すのは、ECS が認証情報を発行してからこの時間内の読み取りだけ (ADR 0076)
```

- 既定は 2 分 (実際の記録の最大 11 秒の 10 倍ほど)。`config init` の雛形に書き、既存の設定には `config init --diff` で見える (ADR 0014)。
  値を書かなければ 2 分で動く (ほかのパラメータの既定と同じ扱い)
- 0 以下・15 分を超える値・解釈できない値は読み込みエラー。上限を置くのは、認証情報の有効期間 (時間の単位) に近い窓では 1 節が 0073 と変わらなくなるため
- 設定にする理由: 確かめたのは Fargate の 2 つの環境だけで、EC2 の起動タイプや大きなイメージで、発行から読み取りまでがどれだけ延びるかは分からない。
  延びた環境では読み取りが外れず medium で報告され (鳴る側)、data の `outside_window` (5 節) で分かるので、利用者がその環境の分だけ延ばせる
- 狭いほど、盗まれた認証情報が外れる時間は短い。既定を狭めに置き、延ばすのは利用者の判断にする

### 3. 窓の始まりをまたぐ発行・記録の欠け・遅れは、鳴る側に倒す

- 突き合わせる `AssumeRole` は、run の窓に限らず保存済みの注目イベント (`AssumeRole` は全部が注目イベント) から引く。
  範囲は `[読み取りの範囲の始まり - bulk_exempt_within, 読み取りの範囲の終わり + 5 秒)`。前日の終わりの発行と、日をまたぐ直後の読み取りも突き合わせられる
- 発行の記録が無い (収集していないリージョンの STS・取りこぼし・下の移行) ときは外さない
- 発行の記録が読み取りより遅れて届き、読み取りの窓の run の時点に無いときも外さない (その run で数える)。
  再走査 (ADR 0013 の `ingest_delay`) で両方が同じ run に入るのがふつうで、遅れて鳴ったら data の `no_issuance` で分かる
- 平常帯 (過去の日ごとの数) の側は、0073 のとおり `bulk: exempt` に一致する秘匿値を**突き合わせによらず**外す。
  外せなかった読み取りを平常帯に入れると、盗まれた認証情報で繰り返し読まれるほど閾値が上がるため。窓の側は外せない読み取りを数えるので、
  0073 の「両側で同じものを数える」は崩すが、崩れる向きは鳴る側 (平常帯が小さく、窓が大きい) だけである

### 4. 収集・保存: キーそのものではなくハッシュを、決まった記録にだけ残す

cloudtrail collector (LookupEvents と trail の S3 の共通の `normalizeRaw`) で、次の記録にだけ値を足す。

| 記録 | 足す項目 | 元の値 |
|---|---|---|
| 成功した `sts:AssumeRole` で、呼び出し側が `AWSService` の `ecs-tasks.amazonaws.com` | `data.issued_key_hash` | `responseElements.credentials.accessKeyId` |
| 秘匿値の読み取り (secret_access の対象の 5 つの操作) で、`userIdentity.type` が `AssumedRole` | `data.session_key_hash` | `userIdentity.accessKeyId` |

- 値は、キーが 1 節 (a) の形のときだけ、SHA-256 の先頭 32 桁 (16 進)。形に合わなければ何も残さない。キーそのものは残さない
  (キーの ID は秘密ではないが、ストアや report に認証情報の形の文字列を持ち込まず、秘密の検査 (gitleaks など) の誤検知とも混ざらないため。突き合わせには一致だけが要る)
- ハッシュは report・通知・info の data に出さない (突き合わせの内部の値)
- **セッション名は残さない** (ADR 0055・設計書 6 章の「roleSessionName は残さない」をそのまま守る)。キーの突き合わせだけでセッション名は要らない
- 保存の形: `events.data` の項目が増えるだけ (raw の `trail_event` の行の `data` にも入る)。rebuild (ADR 0033) は raw の `data` をそのまま入れ直すので、
  新しい版で集めた記録は同じに作り直せる。raw の新しい種類の行は要らない
- 移行: 以前の版で集めた記録にはハッシュが無い。窓の読み取りに無ければ外さない (`no_key`)。発行の側に無ければ突き合わせられない (`no_issuance`)。
  上げた直後の 1 回は、窓の始まりの前に以前の版で集めた発行と組む読み取りが外れず、5 節の medium (数によっては high) になりうる (鳴る側。Release の本文に書く)。
  平常帯は 3 節のとおり突き合わせによらないので、上げても変わらない
- 収集の量: 足すのは `ecs-tasks` の `AssumeRole` と秘匿値の読み取りの記録に 1 項目ずつ (どちらも既に注目イベントとして保存している)。API の呼び出し・権限は増えない

### 5. 外せなかった読み取りは medium で報告する

`bulk: exempt` を書いた組の読み取りは、正規には全部が ECS の発行の直後に起きる (背景の 1〜3。実際の記録で外れは 0 件)。
外せなかった読み取りは「起動の外での利用」(盗まれた認証情報の利用) の強い手がかりなので、数に入れる (1 節) のに加えて、閾値を超えなくても報告する。
外した組の 1〜2 個だけを外で読まれる形は、数に入れるだけでは閾値に届かず気づけないため。

- 条件: 主体がサービスに引き受けられたロール (0073 の 4 節) で、窓に `bulk: exempt` に一致する秘匿値の、外せなかった読み取りが 1 つ以上ある
  (`not_service_role` の主体は 0073 のとおり外さず数えるだけで、この報告は出さない)
- 重大度は **medium**。主体ごとに 1 件、Key は `bulk-exempt-unmatched:<主体の ARN>` (一括読み出し・初出の finding の Key `<主体の ARN>` とは別)
- data: `bulk_exempt_unmatched` (理由ごとの件数 `{no_key, no_issuance, outside_window}`。0 の理由は書かない)・`unmatched_secrets` (外せなかった秘匿値の数)・
  `ips` (外せなかった読み取りの送信元)・`bulk_exempt_max_delay_seconds` (`outside_window` の読み取りの、発行からの最大の遅れ。発行のあるものだけ)・`bulk_exempt_patterns`・`principal`
- 同じ窓で一括読み出しの high になったときは出さず、その high の data に同じ項目を載せる (重ねて出さない)。初出の low / medium とは別に出す
- Fingerprint は重大度と理由の集合 (秘匿値の顔ぶれや回数は入れない。毎回 changed にしない)
- ack は通常の medium と同じ (ADR 0068 が止めるのは high)。playbook には「ack の前に、起動の外での利用でないかを確かめる」(発行の記録・送信元・時刻・
  `bulk_exempt_within` の長さ) を書く。延びた環境の `outside_window` なら設定を延ばすのが直し方
- 移行 (4 節) の 1 回は `no_key` / `no_issuance` で鳴りうる。鳴らさない特例は入れない (鳴る側に倒す。Release の本文に書く)

### 6. 外さなかった読み取りの印と、info の項目

- 窓に `bulk: exempt` に一致する秘匿値があり、サービスに引き受けられたロール (0073 の 4 節) だが、外せない読み取りが 1 つでもあった主体の finding の data:
  - `bulk_exempt_ignored: session_unmatched` (新しい値。`not_service_role` はそのまま)
  - `bulk_exempt_unmatched`: 外せなかった読み取りの数の理由ごとの内訳 `{no_key, no_issuance, outside_window}` (0 の理由は書かない)
  - `bulk_exempted` (外した秘匿値の数)・`bulk_counted` (閾値と比べた数)・`bulk_exempt_patterns` は 0073 のとおり
  - 一括読み出しの high のときは 5 節の項目も
- info の行 (`bulk-exempt:<主体 ARN>`) に足す項目:
  - `bulk_exempt_sessions`: 突き合わせた発行の数 (起動の回数の目安)
  - `bulk_exempt_max_delay_seconds`: 発行から読み取りまでの最大 (2 節の窓をどれだけ使っているかを見る)
- info の行を出す条件は 0073 のとおり (外した秘匿値があり、何も報告しない)。外せなかった読み取りがあれば 5 節の medium が出るので、info の行は出さない。Fingerprint は固定のまま
- `distinct_secrets` の意味は変えない。足すのは項目と値だけなので互換 (ADR 0054。finding の `data` は型を決めていない)

### 7. ファズテスト (ADR 0041)

キーの形の判定とハッシュ (`record` の関数) と `normalizeRaw` の足した部分はログ由来の値を解釈するので、ファズで次の規則を固定する。

- 形に合うキーだけがハッシュになり、出力は常に 16 進 32 桁で、入力の文字列を含まない
- 同じキーは同じハッシュ (突き合わせの前提)
- `normalizeRaw` の出力の `data` に、`ASIA` で始まる認証情報の形の文字列が現れない。`issued_key_hash` は 4 節の発行の記録にだけ、`session_key_hash` は秘匿値の読み取りにだけ現れる

## 検討した選択肢

- **セッション名 (`roleSessionName` と `userIdentity.arn` の後ろ) で突き合わせる (16 進 32 桁の形のときだけ残す)**: 0073 の 4 の 3 で挙げた形。
  セッション名は `AssumeRole` を呼ぶ側が決める値で、人の SSO のセッション名はメールアドレスのことが多い。形で捨てても、残す値の判断が増える (ADR 0055 の「残さない」の例外を作る)。
  キーは AWS が発行の都度決める値で、発行と使用を 1 対 1 に結べ、人の値を含まない。実際の記録で両方が全件一致したので、キーにした。却下
- **キーそのものを残す**: 突き合わせだけならハッシュで足りる。認証情報の形の文字列を 90 日のストアに持たない方を選んだ。却下
- **窓を固定にする**: 設定が増えないが、確かめていない起動の形 (EC2 の起動タイプ・大きなイメージ) で延びたときに、利用者が直せない (high の resolve を続けるしかない)。却下
- **窓を置かない (発行されたキーなら、いつ使われても外す)**: 一時的な認証情報は有効期間 (時間の単位) のあいだ使えるので、盗まれた認証情報の外での利用を 0073 と同じく外してしまう。却下
- **発行の記録が無いとき、0073 のとおりロールの単位で外す (鳴らない側)**: 記録の欠けを攻撃者が作れる形 (収集していないリージョンの STS を使う等) で黙る。目的と逆。却下
- **平常帯の側も突き合わせで外す (両側で同じ規則)**: 3 節のとおり、外せなかった読み取りが平常帯に入り、繰り返されるほど閾値が上がる。却下
- **外せなかった読み取りを数に入れるだけにする (閾値を超えなければ報告しない)**: 外した組の 1〜2 個だけを外で読まれる形が、閾値に届かず info にも残らない。
  守りたいのはまさに「盗まれても気づけるか」なので却下 (レビューで決定)
- **外せなかった読み取りを low で報告する**: low は通知の中で埋もれやすい。実際の記録では外れが 0 件で、鳴るのは起動の外での利用か窓の設定の不足のどちらかだけなので、
  medium でも誤報は増えない。medium にした (レビューで決定)。high にしないのは、窓の設定の不足 (延びた環境) でも鳴り、high は ack できない (ADR 0068) ため
- **送信元 IP・デプロイの操作との突き合わせ**: 背景のとおり、使えない。却下
- **Lambda・EC2 のインスタンスプロファイルも外す**: 発行 (Lambda は `lambda.amazonaws.com` の `AssumeRole`、EC2 は `ec2.amazonaws.com`) と使用の形・時刻の差を記録で確かめていない。
  Lambda の実行環境は再利用され、発行から読み取りまでが窓を超えるのがふつうになりうる。確かめてから足す。今回は ECS だけ

## 引き受ける見逃し (評価。0073 の評価の書き直し)

`bulk: exempt` を書いた実行用のロールで、外した組だけを読まれたときに secret_access が何も出さない (info の 1 行だけ) のは、次の形に狭まる。

- **発行から `bulk_exempt_within` (既定 2 分) の内に、外で使われた場合**: ECS のエージェントに発行された認証情報を、発行の直後に盗み出して使う形。
  実行用のロールの認証情報はタスクのコンテナから直接使えない (0073 の公式文書の 1) ので、盗むにはエージェントか基盤の側に入る必要がある。
  窓の外 (2 分を過ぎて) の利用は、1 つでも medium (5 節)、外した組の数が閾値を超えれば high。
  0073 では有効期間のあいだずっと外れていたので、外れる時間は大きく縮む
- **外した組の外を読む・権限を探る場合**: 0073 のとおり初出・一括読み出し・access_denied に出る (変わらない)
- **コンテナの中から盗まれた場合**: 実行用のロールの認証情報はコンテナから使えないので、この形で `bulk: exempt` は効かない (数えられる)。
  **タスクのロール**に `bulk: exempt` を書いた場合は別で、コンテナの中の攻撃者はタスクのロールの認証情報を使え、認証情報の更新 (ECS による新しい `AssumeRole`) を見て、
  その直後の窓の内に読めば外れる。実際の記録ではタスクのロールが秘匿値を読む記録は無かった。playbook に「`bulk: exempt` は実行用のロールにだけ書く」と書く
  (規則では実行用とタスクのロールを区別できない。どちらも `ecs-tasks.amazonaws.com` が引き受けるため)
- **ECS の基盤そのもの (エージェント) を乗っ取られた場合**: 発行も使用も正規の形になる。arata のログの規則では区別できない (0073 と同じ。AWS の責任の範囲)

0073 の playbook の「arata の外の守り」(実行用のロールの権限をその組に絞る・`aws:SourceVpce` などの条件) はそのまま勧める。

## 結果 (良い点・引き受けるコスト)

- 実行用のロールの認証情報を外で使われたとき、発行の直後の窓の外なら、外した組の 1 つの読み取りでも medium で報告する (0073 の主な見逃しを閉じる)。
  起動時の正規の読み取りは、実際の記録の全件が外れる形 (最大 11 秒に対し既定 2 分)
- セッション名を残さない方針 (ADR 0055) を守ったまま、AWS が発行した値で突き合わせる
- 引き受けるコスト:
  - collector に 2 つの項目 (ハッシュ) と、その形の判定・ファズが増える。secret_access は発行の記録を引く問い合わせが 1 つ増える (`ecs-tasks` の `AssumeRole` だけ)
  - Lambda・EC2 のロールに書いた `bulk: exempt` は効かなくなる (挙動の変更。Release の本文に書く)
  - 上げた直後の 1 回、窓の始まりをまたぐ起動で medium (数によっては high) になりうる (移行。鳴る側。Release の本文に書く)
  - 窓の長さは利用者の環境に依る。延びた環境は medium の `outside_window` で分かり、設定で延ばす (上限 15 分)
  - 新しい finding の Key の形 (`bulk-exempt-unmatched:`) が増える (設計書 6 章の Key の表に足す)
- 実装: `record` (キーの形とハッシュ)・cloudtrail collector (2 項目)・config (`bulk_exempt_within` と検査・雛形)・secret_access (突き合わせ・data・info)。
  文書は playbook `secret_access.md`・`docs/ai` (index・onboarding)・設計書 6 章の決定。スキーマ (型のある出力) と権限は変えない。
  テストは、外す (窓の内・前日の終わりの発行)・外さない (キーが無い・発行が無い・呼び出し側が ECS でない・窓の外・同じ秘匿値を外からも読んだ)・
  medium の報告と high に載せる形・平常帯の側・移行 (ハッシュの無い記録)・設定の検査・info の項目を固定する

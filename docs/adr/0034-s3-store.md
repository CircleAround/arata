# 0034. S3 ストアは実行のたびに作業用の複製を出し入れし、確定は明示の Commit と条件付き書き込みで行う

- 日付: 2026-11-04
- 状態: 採用

## 背景

GitHub Actions のように毎回消える実行環境で arata を定期実行するには、ストア (JSONL の原本と SQLite) の置き場所が要る。
`dir://` の利用者には何も変えず、`store: s3://<bucket>/<prefix>` と書いたときだけ有効なオプションの機能として S3 を足す。

SQLite はローカルのファイルとしてしか安全に動かない。JSONL は日のファイルへの追記だが、S3 は追記できず丸ごとの置き換えになる。
同じ S3 の場所を 2 つの実行が同時に使い得る (定時の実行と、人の `ack`、ワークフローの再実行) ので、後から終わった実行が先の結果を消さないことが要る。

## 決定

- **方式**: `store.OpenS3` が一時ディレクトリに作業用の複製を作り、読み書きは今の `Dir` がそのまま担う。S3 のオブジェクトは `audit.sqlite.gz` (gzip)、`raw/<source>/<日付>.jsonl` (そのまま)、`reports/<profile>.{json,md}`
- **取得**
  - 開始時に SQLite と `reports/` を取得し、それぞれの ETag を覚える
  - raw は **日のファイルに初めて追記するときに取得する** (`Dir.AppendRaw` の内部のフック)。窓から日を予測して先に取ることはしない
  - 権限・通信の失敗は `STORE_UNAVAILABLE` で止める。「無い」(404) とだけ区別して空のストアで始める (取り違えると全部が new として報告され、rebuild を促す `STORE_CORRUPT` も誤りになる)
  - SQLite が無いのに raw があれば、消えた可能性が高いので書き込み系のコマンド (`init` を含む) は `STORE_CORRUPT` で止め、`arata rebuild --from-scratch` とバージョニングからの復元を案内する。読むだけの `report` / `review` は警告して続け、doctor は ng で示す。`rebuild` は止めない
- **確定**: `Engine.Commit(ctx)` を書き込み系のコマンドが成功したときだけ呼ぶ。呼ばずに `Close` すれば何も送らない。`dir://` の `Commit` は何もしない
  - 失敗・中断 (ctx)・パニックと、読むだけの `report` / `review` は同じ仕組みでアップロードされない
  - 中断は `INTERRUPTED` (終了コード 2) で、S3 に保存していないことと再実行を案内する。`CONFIG_INVALID` にしない (`dir://` でも同じ)。判定はエラーの型ではなく ctx で行う
  - `run` / `evaluate` は Commit してから report を出す。`STORE_CONFLICT` のときは report を出さず、確定していない結果を aratam が通知しない
  - `run` の partial (終了コード 3) は確定した結果なので Commit する
  - `init` は中断・部分失敗でも Commit する (中断された ctx を外す)。init は進捗を書いて `--resume` で再開する作りで、捨てると数時間分の収集を失うため。Commit に失敗したら、収集が失われたことと再実行の手順を出す
  - `approve` は allowlist を書いた後に衝突し得る。そのときは `arata resolve` で片付けるよう案内する
- **書き戻しの順序**: SQLite の ETag を HeadObject で確かめる → 変わった raw・reports → SQLite。**すべて条件付き** (`If-Match: <開始時の ETag>`、開始時に無ければ `If-None-Match: *`)。SQLite が書けたら確定
  - 412 (不一致)・409 (同時の条件付き書き込みの衝突)・404 (If-Match の対象が消された) は `STORE_CONFLICT` (終了コード 2)。何も上書きしない
  - 事前の確かめは、負けが確かな実行が raw を進めないためのもので、排他そのものは条件付きの書き込みが担う
- **raw だけが先に進んだとき** (SQLite の書き込みの失敗・衝突): 受け入れる。次の run は古い SQLite から同じ窓を引き直すので **SQLite では二重に数えない**。原本には同じ窓の行が重なる。rebuild では events は event_id で 1 件 (collected_at は早いほう)、metrics は行順の置き換え、スナップショットは最後の印で同じ結果になる。
  `principal_ips.count` だけは確定しなかった窓の分が増える。これは **rebuild でだけ起き、件数は判定に使っておらず (ADR 0011)、`init --resume` と同じ既知の過大**
- **rebuild**: `RebuildS3` は raw を全部取得して作り直し、SQLite だけを条件付きで置き換える。`.bak` は残さない (世代はバケットのバージョニングが持つ)。`--from-scratch` は壊れたオブジェクトを読まないが、その ETag を条件に使う
- **認証**: `store_profile` (省略時は SDK の標準の連鎖。`aws.profile` は使わない) と `store_region` (省略時は `aws.region`) で監査対象と分ける。`dir://` に書くと設定エラー
- **読み取り専用との区別**: 「arata は読み取り専用」は監査対象のアカウントへの約束で、ストアのバケットは arata を動かす側が用意する別のもの。必要な権限は `s3:GetObject`・`s3:PutObject`・`s3:ListBucket` (prefix に限定。If-Match の書き込みにも GetObject が要る)。doctor は読めるかだけを確かめて書き込みは試さず、この区別を `store_scope` の行と別の action の一覧で示す。
  推奨 (バージョニング・既定の暗号化・パブリックアクセスブロック) が満たされなければ warn、確かめる権限が無ければ飛ばす
- **依存**: `service/s3` だけを足す。全部 PutObject で送るので `feature/s3/manager` は足さない (SQLite の gzip は 5 GB の上限より十分小さい想定)。aratam の依存は増えない

## 検討した選択肢

- **SQLite を S3 上で直接動かす (Litestream の書き込みできる VFS など)**: 2026 年に出たばかりで、書き込みが続くと壊れる報告がある。書き手は 1 つが前提。却下
- **Mountpoint for S3 / s3fs**: 部分的な書き換えとロックに対応しておらず、SQLite を壊し得る。却下
- **ワークフローのシェルで `aws s3 cp`**: 条件付き書き込みと失敗時の扱いをシェルで書くことになり、壊れやすくテストしにくい。却下
- **GitHub の cache / artifacts**: 消えるのでストアにならない。却下
- **raw の日を窓から予測して開始時に取得する**: raw のファイルの日はレコードの時刻で決まるので、追いつきの run・`collect --window`・init・過去の日付の metrics は予測から外れ得る。外れた日のファイルを丸ごと置き換えると S3 の既存の行が消える。却下
- **raw を無条件で置き換え、順序だけで整合を取る (SQLite を最後に書く)**: A が完了した後に B が古い内容で raw を上書きしてから SQLite で 412 になると、A の原本の行が消える。順序では防げない。却下
- **Close の中で失敗を判定して書き戻す**: `defer e.Close()` からは成否が分からず、読むだけのコマンドも見分けられない。SQLite は開くだけでファイルが変わり得るので、内容の比較でも判定できない。却下
- **SQLite に確定時の raw のサイズを持たせ、次の run が raw の末尾を切り詰める**: count の過大は防げるが、「原本は追記のみ」を崩し、複雑さに見合わない。却下
- **SQLite が無く raw があっても警告だけで続ける**: 定時の実行は止まらないが、空の SQLite を Commit して findings・承認・ack の状態を空で上書きし、次からは警告も出ない。止めれば aratam が「実行されていない」と知らせるので人が気づける。却下
- **`store_profile` の省略時に `aws.profile` を使う**: 監査の読み取りロールでストアを書く設定になりやすい。分けることが目的なので標準の連鎖にした

## 結果

- 良い点: サーバーを持たずに定期実行できる。同時に動いても後から終わった実行が失敗するだけで、SQLite も原本の行も消えない。`dir://` の動きは変わらない
- 引き受けるコスト: 実行のたびに SQLite 全体を出し入れする (gzip で減らす)。人の `ack` と定時の実行が重なるとどちらかが `STORE_CONFLICT` になり、再実行が要る。衝突した実行の収集は捨てる (次の run が同じ窓を引き直す)。
  ローカルの `audit.lock` は一時ディレクトリの中で効くだけで、実行どうしの排他は条件付きの書き込みが担う (同時の実行を止めたいときは起動側で止める)。prune は対象外

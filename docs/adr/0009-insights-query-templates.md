# 0009. Logs Insights のクエリテンプレートは前処理・集計・後処理の 3 層で組み、UTC 日次の集計を置き換えで保存する

- 日付: 2026-10-21
- 状態: 採用

## 背景

ADR 0006 で「形式プロファイルの実体は Insights クエリのテンプレート集」と決めたが、テンプレートの組み方は決まっていなかった。
形式 (nginx / ALB / WAF / JSON / regex) と集計 (sign-in 失敗・機密パス探索・WAF BLOCK) の組み合わせごとにクエリを書くと、
形式 5 × 集計 5 のように掛け算で増え、顧客ごとのパスや閾値も埋め込めない。

また、平常帯 (直近 14 日の中央値) を計算するには日単位の値が要るが、run の窓 (例: 07:00 JST の daily なら 22:00〜22:00 UTC) は日の境界と揃わない。
窓の分だけ集計して日次値に「加算」すると再収集や追いつき (設計書 3 章) で二重に数え、「置換」すると窓が日の途中から始まる日を部分値で上書きする。

## 決定

- クエリは 3 層で組み立てる (`internal/collect/cwlogs`)。
  1. **前処理** (形式プロファイルごと): ストリームの絞り込みと、生ログ → 正規化フィールド (`ip`, `method`, `path`, `status` ...) の変換 (`parse` / `fields ... as ...`)
  2. **集計** (正規化レコードの種類ごと): 前処理が作ったフィールド名だけを使う `filter`。パス・ステータスは設定の `checks:` から入れる
  3. **共通の後処理**: `stats count(*) as <metric> by bin(1d) as day, <key> | sort | limit 10000`
- 結果の値の列名は metric 名にする (`as sign_in_failures`)。結果が自己記述的になり、テストのフェイクもクエリ中の metric 名で応答を選べる。
- 解釈率のクエリ (`lines_total` / `lines_matched`) も同じ前処理を使う。解釈率が閾値未満なら集計クエリを流さない。
- 集計クエリの範囲は **窓に重なる UTC 日の 0 時から窓の終わりまで**。metrics は (date, source, metric, key) で**置き換える**。
  同じ日を何度引いても後の値ほど完全なので、再収集・追いつき・`collect` の手動実行で二重に数えない。日は UTC (`bin(1d)` が UTC で切る)。
- Insights の方言に依存する箇所 (`parse` の正規表現、`in [...]`、`like /.../`、`by ... as`) はテンプレートの 1 ファイルに集め、`doctor` が実環境で構文検査する。
  検査対象は集計クエリだけでなく、解釈率・サンプル・doctor 自身のクエリを含む全テンプレートとする。
- 前処理で定義したフィールド (`parse` の名前付きキャプチャ、`fields ... as`) は後段の `fields` で列挙し直さない。
  Insights は `Ephemeral field is already defined` で拒否する (2026-10-21、本番の doctor で確認)。判定の値が要るときは `ispresent(x) as <別名>` のように新しい名前で出す。

## 検討した選択肢

- 形式 × 集計ごとに完成したクエリを持つ: 読みやすいが組み合わせが増え、設定値の差し込みが散る。却下
- 窓の分だけ集計し、metrics に加算する: 窓が重なる・追いつくと二重に数える。冪等にするには窓ごとの記録が別に要る。却下
- 窓の分だけ集計し、`MAX(既存, 新)` で保存する: 簡単だが、ログの遅延到着や再集計で値が減るべきときに追随できない。却下
- 時間単位 (`bin(1h)`) で保存し、日次は手元で合算する: 窓と揃えられるが metrics の行数が 24 倍になり、設計書 5-2 の「日次集計」から外れる。却下
- JST の日で切る: 日本の顧客には自然だが、`bin(1d)` は UTC で、オフセット計算をクエリに入れると方言依存が増える。UTC のまま report.md に `(UTC)` を明記する

## 結果

- 新しい形式は前処理 1 つ、新しい集計は `Aggregates` に 1 行足すだけで全形式に効く
- 1 回の収集のスキャン量は最大で窓 + 24h 分になる (daily なら最大約 2 日分)。`max_scan_gb` はこれを見込んで決める
- その日の値は run ごとに途中経過で置き換わり、翌日の run で丸 1 日分に確定する。チェックは窓に重なる日を評価するので、確定前の日も一度は評価される
- Insights の実際の挙動はフェイクでは確かめられない。導入時に `doctor` で確認する前提。
  2026-10-21 に本番の nginx_access 2 ソースで集計 4 本 (`in [...]` / `like` / `by bin(1d) as day`) の受理を確認し、doctor のサンプルクエリの再宣言の問題を見つけて直した

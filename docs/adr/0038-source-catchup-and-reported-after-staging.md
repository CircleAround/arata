# 0038. 失敗したソースはソースごとの位置から追いつき、報告済みの印は出力の準備の後に付ける

- 日付: 2026-11-04
- 状態: 採用

## 背景

公開の前の点検で、監査の結果が無言で失われる経路を 2 つ再現した。

1. 全ソースが AccessDenied でも run は `partial` で、次の run の窓は前回の `window_to` から始まる。失敗した期間のイベントは二度と引かれず、権限が戻った run は終了コード 0 で「問題なし」に見える
2. Diff はチェックごとに finding を確定する。run が途中で止まると、一度も報告していない finding が次の run で `still_open` になる。`saveReport` や出力の失敗では「本日報告済み」にもなる

## 決定

### ソースごとの追いつき

- run の stats に `source_covered_to` (source の id → 取り終えた時刻) を持つ。成功したソースは窓の終わりへ進め、失敗したソースは前の位置のままにする。前の位置が無ければ窓の始まりにする
- 位置を持たない古い run は、全ソースがその `window_to` まで取れたものとして扱う
- 次の run は、遅れたソースだけを前の位置から引く。下限は `max_catchup` で、超えた分は `SOURCE_CATCHUP_TRUNCATED` の WARN を出して諦める
- 追いついたことは `SOURCE_CATCHUP` の WARN と stats の `catchup_from` で分かる。Logs Insights は読み取り量に費用がかかるので、doctor の cost の行にも書く。費用の上限は既存の `max_scan_gb` と coverage の報告が担う
- 評価: イベントは ADR 0013 の「遅れて届いたもの」と同じ扱いにする。集計のソースが遅れたらチェックの窓も広げる
- 途中まで取れたソースは進めない。`CoveredUntil` は新しい側の端で、古い側が未取得のまま残るため。引き直しは event_id と日次の置き換えで重複しない

### 報告済みの印

- open で `ReportedAt` がゼロの finding は、ID と初出を保ったまま new にする
- 出力を 2 段にする: 準備 (`--format` の検証、`--out` の一時ファイルへの書き込み) → saveReport → 報告済みの印 → FinishRun → Commit → 公開 (rename・標準出力)
- 準備に失敗した run は `failed` にする。窓は進まず、印も付かない

## 残る失敗の窓

- 公開の rename と標準出力は Commit の後なので、ここで失敗すると「報告済みなのに届かない」が残る。準備で同じディレクトリへの書き込みが成功しているので起きにくい。S3 の Commit は 1 回だけで未確定の結果を通知しない (ADR 0034) ので、この順序は崩せない
- dir で印の後に止まると Commit の概念が無く、その run の finding は報告済みのまま失われ得る。印の前に止まれば次の run で new になり、同じ finding が 2 度出ることがある。取りこぼしより重複を選ぶ
- aratam の送信失敗は別の話で、report.json と `.aratam-notified` で再送できる

## 検討した選択肢

- **新しい表に位置を持つ**: 却下。移行と rebuild の carriedTables の変更が要る。runs の stats なら rebuild で引き継がれ、S3 では SQLite と一緒に確定する
- **全ソースが失敗した run だけを `LastRun` から外す**: 却下。一部のソースの失敗で同じ穴が残る
- **集計のソースは追いつかず coverage に出すだけ**: 却下。費用は増えないが、総当たりなどの検知の穴が残る
- **公開の後に印を付ける**: 却下。S3 で 2 回目の Commit が要り、衝突の扱いが増える

## 結果

- 良い点: 権限の一時的な失敗で監査の結果が失われない。出力できない run が finding を消費しない
- 引き受けるコスト: 回復後の run は読み取り量が増える。同じ finding が重複して通知されることがある。`dir://` の run は途中の状態を SQLite に残したままで、1 つのトランザクションにはしていない

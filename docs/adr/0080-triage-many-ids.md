# 0080. ack / snooze / resolve に複数の finding ID を渡し、全部を確かめてから 1 回で書く

- 日付: 2026-11-21
- 状態: 採用

## 背景

`arata ack|snooze|resolve` は finding の ID を 1 つしか取らなかった。見本の arata-triage.yml (ADR 0068) の `finding_id` も 1 件だけだった。

S3 のストアは条件付きの書き込みで排他する (ADR 0034)。片付けのワークフローを並べて流すと、後に終わったほうが STORE_CONFLICT で失敗する。
そのため片付けは、監査と同じ concurrency の group で 1 件ずつ順に流すことになる。1 件に約 1 分 (取得・認証・ストアの取得と書き戻し) かかるので、
日次の指摘 42 件を片付けた利用者は 40〜50 分待った。

## 決定

### 1. ack / snooze / resolve は複数の ID を取る

- 引数は 1 つ以上。各引数を、空白 (スペース・タブ・改行) とカンマで分ける (`arata ack <id> <id>`、`arata ack <id>,<id>`)。全角の空白と CR は区切りにしない
- 同じ status・`--reason`・`--by`・`--until`・`--force` を全部の ID に当てる
- ストアへの書き込みは 1 つのトランザクション (`store.SetFindingStatuses`) で、確定 (`Commit`) は 1 回。S3 のストアでも、取得と書き戻しは 1 回

### 2. 全部を確かめてから書く (全部か無しか)

- 書く前に、全部の ID について、形 (12 桁の小文字の 16 進)・重複・件数・finding の有無と状態 (既に resolved)・片付けの表 (ACK_REFUSED。ADR 0068・0077)・期日を確かめる
- 1 件でも通らなければ、何も書かずに止める。止めた ID と理由を全部出す (人向けの一覧と、止めた ID ごとに code の付いた ERROR のログ 1 行)
- 同じ ID が 2 回あればエラーにする (打ち間違いか、取り違えの兆し。黙って 1 回にしない)
- 終了コードは 2。code は、止めたのが全部 ack の守りなら ACK_REFUSED、ほかが混ざれば CONFIG_INVALID。ID ごとの code はログと `--format json` にある
- 一部だけ書く形は採らない。どれが書けてどれが書けなかったかを、人が読み解いて残りを流し直す手間と、取り違えの余地が増える

### 3. 上限は 100 件

- 日次の片付けの実例 (42 件) の 2 倍を超える。ワークフローの Summary に ID ごとの中身を出しても、人が確かめながら読める量に収まる
  (100 件で数十 KB。Summary の上限 1 MiB にも十分に収まる)
- これを超える片付けは、中身を確かめずに流す片付けになりやすい。分けて実行する
- arata (`engine.MaxFindingIDs`) と見本のワークフローの入力の検査で同じ値にする

### 4. `--format json` で ID ごとの結果を出す (ADR 0054)

- スキーマは `triage-result` (版 1)。ID ごとに `result` (`changed` = 書いた / `would_change` = 試しで通った / `refused` = 止めた / `not_written` = 通ったが書いていない)、
  操作の前後の状態、`forced`、止めた理由の `code`
- 見本のワークフローの Summary はこれを読む (人向けの文を読まない)。止めたときも JSON を出す (止めた ID と code が要る)
- `--dry-run` も複数を取り、ID ごとに何がどう変わるかを出す

### 5. 見本のワークフロー (arata-triage.yml)

- `finding_id` に空白かカンマで区切った複数の ID を書ける。入力の検査 (認証の前) で、ID ごとに今の正規表現 (`^[0-9a-f]{12}$`) で確かめ、重複と件数も確かめる。
  通らない値は位置 (何番目) だけを出し、値そのものはログに写さない。分けた並びを validate の出力 `ids` に書き、後の step はそれを使う
- 1 回の `arata` に全部の ID を渡す。Summary に、ID ごとの中身 (操作の前。今までと同じく 12 桁の数字を伏せ、コードの中に入れる。長い値は 200 文字で切る) と結果を出す

## 検討した選択肢

- **ID を書いたファイルを入力にする (`--ids-file`)**: 引数で 100 件は十分に渡せ (コマンド行の長さの上限に遠い)、ワークフローの入力は文字列なのでファイルを経ると一手増える。
  ファイルの形 (改行・コメント・BOM) という読む規則がもう 1 つ増える。却下
- **ワークフローで ID を 1 件ずつ回す (1 つのジョブの中で arata を ID の数だけ呼ぶ)**: 取得・認証は 1 回になるが、S3 のストアの取得と書き戻しは ID の数だけ起き、
  途中で止まると一部だけ書いた状態が残る。全部か無しかにできない。却下
- **ワークフローを ID ごとに並べて流す (matrix)**: STORE_CONFLICT になる (ADR 0034)。順に待たせても今と同じ時間がかかる。却下
- **通った ID だけ書き、止めた ID を報告する**: 2 節の理由で却下。止めた ID を直して、同じ並びをもう一度流せば済む
- **重複を黙って 1 回にする**: 2 節の理由で却下

## 結果

- 42 件の片付けは 1 回の実行 (約 1 分) で済む
- 1 件でも通らなければ全部が止まるので、止めた ID を外す (または直す) 手間はある。止めた ID と理由は全部出るので、1 回で直せる
- ストアに `SetFindingStatuses` が増える (1 件の `SetFindingStatus` はその特別な場合)
- テストの ID (偽の `NewID`) を arata が振る形 (12 桁の 16 進) にそろえた。ゴールデンの ID の表記が変わった

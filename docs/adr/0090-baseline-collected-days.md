# 0090. 平常帯の中央値は、そのソースを収集した日だけで取る。収集していない日 (導入の前・収集の抜け) は数えず、収集した日で値の無い日は 0 と数える

- 日付: 2026-11-26
- 状態: 採用 (2026-11-26、開発リードの判断)

## 背景

平常帯を「過去 `baseline_days` 日の日ごとの値の中央値 × factor」で作るチェックがある。いくつかは、`baseline_days` の**すべての日**を並べ、値の無い日を 0 として中央値を取っていた。
値の無い日には 2 つある。

- 収集した日で、値が 0 だった日 (その主体・IP がその日は何もしなかった)
- 収集していない日 (導入の前、収集が止まった日、run が失敗した日)

後者まで 0 と数えると、導入の直後や収集の抜けの後は中央値が下がる (半分以上が抜けなら 0 になる)。
ふだんどおりの件数 (たとえば、監査を回す CI のロールの OIDC の引き受けや、毎日一定数失敗する社内の NAT) が平常帯を超えて見え、誤報が出る。

ADR 0071・0087 の利用者ごとのチェック (`user_probe.go`) は、#177 のレビューで「アプリの記録のある日だけ」に直した。
`endpoint_abuse` (ADR 0030) は最初から「ログを収集した日 (lines_total のある日)」で p99 を取っている。ほかのチェックにも同じ考え方を当てる。

## 決定

### 1. 中央値に入れる日

平常帯の中央値に入れるのは、`baseline_days` の日のうち**そのソースを収集した日**だけにする。
収集した日で値が無いのは 0 のまま数える (「その日は何もしなかった」は事実で、平常帯を下げるべき値)。収集していない日は数えない (中央値の母数から外す)。

収集した日は、ストアにある事実から決める。

| ソース | 収集した日 |
|---|---|
| CloudTrail (`trail_event`) | run の stats に `trail_collected` のある run の窓が丸 1 日を覆う日 (ADR 0027 の `collectedDays`)、**または**そのチェックが読む記録 (events) のある日 |
| アクセスログ (`http_access`) | `http_access` のソースの `lines_total` (ログの総行数) が 0 より大きい日 (ADR 0030 の `httpCollectedDays`)、**または**その metric の値のある日 |

決定: 「値 (記録) のある日」も収集した日に足す。値があるなら、その日は (少なくとも一部は) 収集している。

- 足さないと、`trail_collected` の印を付ける前の版で集めた過去や、`lines_total` の無い行しかない日を、値があるのに外してしまう
- 引き受けること: 日の一部だけを収集した日 (init の途中で止まった日、導入した日) も、記録があれば入る。その日の値は小さいので、中央値をわずかに下げる側に効く。以前はすべての日を入れていたので、今より悪くはならない
- 複数のソースの値を合算する metric (detectSpikes) は、どれか 1 つのソースを収集した日を収集した日とする。あるソースだけが抜けた日は、そのソースの 0 を数える (ソースごとに分けると集計の形が変わるので、後の課題)

### 2. 収集した日が足りない間

導入直後 (収集した日が `min_baseline_days` に満たない間) の扱いは、**各チェックの今の扱いを変えない**。変えるのは中央値の日だけ。

| チェック | 足りない間 | 数える日 |
|---|---|---|
| `oidc_assume_role` (平常帯の行) | 判定しない | CloudTrail を収集し終えた日 (変えない) |
| `secret_access` の一括読み出し | 判定する (下限 `min_distinct`)。初出は判定しない | 収集し終えた日 (変えない) |
| `access_denied` | 平常帯を 0 とみなし、絶対の閾値だけで判定する | 拒否のある過去日 (変えない。設計書の「ADR 0027 で見直し、変えない」) |
| `login_bruteforce`・`probe_paths` | 閾値超えは判定する (下限 `min_count`)。初出 (`new_top_ip`) は判定しない | データのある過去日 (変えない) |
| ip_list の `sign_in_failure` (ADR 0069) | 件数 (と日数) だけで判定する | データのある過去日 (変えない) |

決定: 足りない間に coverage.notes へ「あと N 日」を出すのは、この ADR では足さない。利用者ごとのチェック (ADR 0087) は、足りない間はまったく判定しないので注記を出す。
上の表のチェックは、足りない間も下限の閾値で判定する (`oidc_assume_role` の平常帯の行と、初出だけが判定しない)。注記を出すなら、初出を待つ `principal_new_source`・`secret_access` とそろえて、別に決める。

### 3. 適用の範囲

| チェック | 平常帯 | この ADR |
|---|---|---|
| `oidc_assume_role` (平常帯の行。`volume:`) | 組ごとの日ごとの回数の中央値 | 当てる |
| `access_denied` | 主体ごとの日ごとの件数・種類の中央値 | 当てる |
| `secret_access` (一括読み出し) | 主体ごとの日ごとの異なる秘匿値の数の中央値 | 当てる |
| `login_bruteforce`・`probe_paths` (`detectSpikes`) | IP ごとの日ごとの件数の中央値 | 当てる |
| ip_list の `sign_in_failure` (チェックではないが同じ形) | IP ごとの日・窓の件数の中央値 | 当てる (`lines_total` を読む metric に足す) |
| `user_denied`・`user_id_enumeration`・`user_path_breadth`・`user_kind_mismatch` | 利用者ごと・アプリの中央値 | 当て済み (#177。アプリの記録のある日) |
| `endpoint_abuse` | 幅ごとの p99 | 当て済み (ADR 0030。`lines_total` のある日) |
| `waf_block_trend`・`principal_new_source`・`login_bruteforce` の `new_top_ip` | 初出 (過去に一度も無い) | 当てない。中央値を取らないので、収集していない日は「見ていない」だけで値を下げない |

finding の data に `baseline_days_collected` (中央値に入れた日数) を足す (`access_denied`・`login_bruteforce`・`probe_paths`)。項目を足すだけなので互換 (ADR 0054)。
`oidc_assume_role`・`secret_access` の `baseline_days_with_data` は、もとから収集し終えた日の数で、意味を変えない。

### 4. secret_access の一括読み出しの問題との関係

`docs/roadmap.md` の「`secret_access` の一括読み出し」(起動時にまとめて読む主体は、読まない日が 0 件で中央値が 0 のまま、デプロイの日ごとに high) は、**この ADR では直らない**。
その 0 は収集した日の 0 (読まなかった事実) で、1 節の規則でも 0 と数えるため。別の判定 (読んだ日だけの中央値、想定件数など) を別の ADR で決める。

## 検討した選択肢

- **実行の予定から期待値を作る (schedule-aware)**: 設定の `schedule` や cron から「収集したはずの日」を作り、それと比べて抜けを決める。**却下**。
  arata は予定を知らない (cron は GitHub Actions などの arata の外にある)。予定があっても、実際に収集できたかは run の記録でしか分からない。
  予定を設定に足すと、暗黙の既定を持たない (ADR 0014) 規則のもとで、利用者が書く値が 1 つ増える。run の記録 (事実) だけで決まるので、予定は要らない
- **「値のある日」だけで中央値を取る** (利用者ごとのチェックの本人の帯の前の形): **却下**。収集した日の 0 が消え、ふだんは少ない主体の中央値が、たまにある多い日の値になる (平常帯が上がり、見逃しが増える)。ADR 0027 が「データのある日」をやめた理由と同じ
- **収集していない日を前後の値で補う**: **却下**。値を作ることになり、根拠を data で説明できない
- **CloudTrail で「収集し終えた日」だけを使い、記録のある日を足さない**: **却下**。`trail_collected` の印の無い run (以前の版) で集めた過去が、値があるのに外れる。テストのストアのように run の無い記録も同じ

## 結果 (良い点・引き受けるコスト)

- 良い点: 導入の直後と収集の抜けの後に、ふだんどおりの件数で鳴らない。平常帯は「収集した日の事実」だけで決まり、data の `baseline_days_collected` で説明できる
- 引き受けるコスト
  - 収集した日が少ない間は、少ない日の中央値になる (たまたま多い日が続けば平常帯が上がる)。下限 (`min_count`・`min_distinct`) と、初出の判定が `min_baseline_days` を待つことは変えない
  - 日の一部だけを収集した日は、記録があれば入る (1 節)
  - 収集した日を決めるのに、ストアから runs (CloudTrail) か `lines_total` (アクセスログ) を 1 回多く読む

# 0049. 試しの実行 (`run --dry-run`) はストアの複製の上で評価し、複製を捨てる

- 日付: 2026-11-13
- 状態: 採用

## 背景

定時の実行の前に「いま流したら何が出るか」を見たいことがよくある (設定や既知リストを直した後、何かを変えた後の確かめ)。
これまでは `arata run` をもう 1 回流すしかなく、2 つの問題があった。

1. **結果が本番のストアに残る。** 出た finding は報告済みになり、窓の終わり (`window_to`) も進む。翌朝の定時の通知には出ない。
   試しただけのつもりが、通知を 1 回飲み込む
2. **毎回プロファイルの窓 (daily なら 24 時間) を見直す。** CloudTrail の LookupEvents は毎秒 2 リクエストで時間がかかり、
   Logs Insights はスキャン量に応じて費用がかかる。前回の `window_to` からの追いつきもあるので、短くもできない

## 決定

**`arata run --profile <名前> --dry-run [--window <期間>]` を足す。ストアを一時ディレクトリへ複製し、その上でふだんと同じ収集と評価を行い、複製を捨てる。**

### ストアに何も書かない

- **dir://**: SQLite (と、異常終了で残っていれば `-wal`) をバイトのまま一時ディレクトリへ写し、写した側を開く。元のディレクトリでは SQLite を開かない
  (WAL モードは読むだけでも `-wal` / `-shm` を作り、チェックポイントで本体を書き換え得る)。raw は写さない (run は読まない)。
  収集した raw・events・principals・metrics・findings・runs・reports はすべて複製に書かれ、終了時に複製ごと消える
- **s3://**: 元から「一時ディレクトリへ取得して作業し、Commit で書き戻す」作り (ADR 0034) なので、SQLite だけを取得し、Commit で何も送らない。
  raw への追記の前の取得と `reports/` の取得もしない
- **ロック**:
  - dir:// は **複製する間だけ** `audit.lock` を取る。書き込み中の実行がいれば `STORE_LOCKED` で止まる (途中の状態を読まない)。
    複製が済んだら放すので、試しの収集の間も定時の実行は動ける。ロックのファイルは作らない (無ければ、まだ誰も書いていないストアとしてそのまま読む)
  - s3:// は取らない。S3 のストアにロックは無く、排他は Commit の条件付きの書き込みが担う。読むだけの実行は SQLite を 1 回取得するだけで整合した状態を得る
- **取り違えを両側で止める。** 複製でないエンジンは dry-run を断り (本番のストアに書かせない)、複製のエンジンは dry-run 以外を断る
  (結果が捨てられるのに成功に見える)。S3 の複製は `Commit` を呼ばれても何も送らない
- ストアがまだ無ければ、空の複製で始める (全部が新規として出る)。ストアのディレクトリは作らない
- 既知リスト (`allowlist.yaml`) は読むだけ (run は元から書かない)

テストで固定する: 試しの実行の前後で、dir:// はストアの全ファイルの名前・権限・更新時刻・内容が同じ、s3:// は PUT が 0 件でオブジェクトが同じ。
その後の定時の実行は、試しの実行が無かったときと同じ指摘を新規として出し、窓も前回の `window_to` から続く。

### 窓

- 窓は `[now - window, now)`。`--window` を省くとプロファイルの `window`
- 前回の `window_to` からの追いつき (設計書 3 章) と、失敗したソースの追いつき (ADR 0038) を **しない**。`RUN_MISSED` も出さない。
  追いつきは定時の実行の仕事で、試しの実行は短く見るのが目的
- `ingest_delay` の再走査 (ADR 0013) は同じ
- `--window` は `--dry-run` のときだけ使える。付けずに `--window` を渡すと `CONFIG_INVALID` (終了コード 2) で、ストアを開く前に止まる。
  定時の実行の窓は前回の続きで決まるもので、手で変えると取りこぼしか二重の評価になる

### 判定は「定時の実行ならどう出るか」の先取り

新規・変化・再発の判定は、ストアの今の状態 (平常帯・既知の主体・finding の状態) に対して、定時の実行と同じコードで行う。

- **差分判定の境界 (再発と「本日報告済み」) は、定時の実行の窓の始まりに合わせる。** 試しの窓の始まりを境界にすると、
  前回の run で見た事象が続いているだけで、last_seen が境界より前になり「再発」と出る (定時の実行では「未対応」か「変化」)。
  境界は「試しの窓の始まり」と「いま定時の実行を流したときの窓の始まり」の早いほうにする (試しの窓のほうが長いときに、見直した古い事象を再発にしない)
- 新規の finding の id は複製の中で振るので、**ストアには無い**。`arata review` / `approve` では引けず、定時の実行で付け直される。report.md の冒頭に書く

### レポートと通知

- report.json に `"dry_run": true` を足す (定時の実行では出さない。`omitempty`)。`window` は実際に見た範囲
- `coverage.notes` (文の配列。無ければ出さない) を足し、見た範囲が定時の実行より狭いときに 2 つを書く:
  1. 見た範囲と、定時の実行なら見る範囲。その差の期間に起きたことはこの報告に入っていない
  2. 日次集計を使うチェック (cloudwatch-logs のソースが出す種類を使うもの) は、窓に重なる UTC の日だけを評価する。
     定時の実行なら評価する日 (例: 前日) を評価していないので、結果が違うことがある。評価しなかった日を並べる
- report.md は冒頭に「試しの実行」であること、カバレッジに注記を出す
- **aratam は `dry_run: true` の報告を送らない。** `DRY_RUN_REPORT` の WARN を出して終了コード 0。LLM も呼ばず、通知済みの印も付けず、`--force` でも送らない。
  誤って定時の経路に流しても通知が飛ばない。`aratam notify --dry-run` (標準出力に出すだけ) では、冒頭に注記を足して文面を表示する
- 既存の書き込み系 (`init` / `run` / `collect` / `evaluate`) の振る舞いは変えない。定時の実行の report.json は 1 バイトも変わらない

### GitHub Actions の見本

`arata-audit.yml` / `arata-audit-multi.yml` の手動実行に入力 `dry_run` (boolean) と `window` (string) を足す。

- `dry_run` のときは `arata run` に `--dry-run` (と `--window`) を付け、**aratam notify を呼ばず**、WAF の提案の全文もバケットへ置かない
- 結果は件数と重大度だけを Actions のログに出す (`dry-run-summary`)。既存の方針どおり、個々の finding の中身 (主体・IP・要約) と注記の文は出さない。
  数・決まった語彙の重大度・時刻の形の値だけを選んで出す
- 排他の group を定時の実行と分ける。同じ group だと、待っている定時の実行を試しの実行が取り消し得る。試しの実行はストアに書かないので排他は要らない

## 検討した選択肢

1. **メモリ上の重ね合わせ (Store を包み、書き込みをメモリに持って読み取りに重ねる)** — ディスクを使わないが、Events の絞り込み・日次集計の置き換え・
   finding の upsert・スナップショットの置き換えを Go で作り直すことになる。SQL と同じ結果を返す保証をテストで持ち続ける必要があり、
   ずれると「試しでは出なかったのに定時で出た」になる。**却下。** 複製なら判定のコードは 1 つで、S3 のストアとも同じ作りになる。
   複製の費用は SQLite 1 つの写し (設計書の見積もりで年に数百 MB まで)
2. **元の SQLite を読み取り専用で開き、書き込みを別の SQLite に ATTACH する** — WAL モードのファイルを開くだけで `-shm` ができ、
   「1 バイトも変えない」を守れない。immutable で開くと、書き込み中の実行と重なったときに壊れた状態を読む。**却下**
3. **本番のストアに書き、後で巻き戻す (`run` の後に finding の報告済みと runs を戻す)** — 途中で止まると戻らない。S3 では Commit が 1 回なので成り立たない。**却下**
4. **`--dry-run` を付けず、`--window` だけを `run` に足す** — 短くはなるが、結果がストアに残る問題がそのまま。定時の窓を手で変えられると取りこぼす。**却下**
5. **dir:// でもロックを取らずに複製する** — 書き込み中の SQLite を写すと、本体と WAL の時点がずれた複製になり得る。
   複製の間だけロックを取れば足り、待たせる時間は写しの数秒。**却下**
6. **aratam が dry_run の報告を「入力の問題」(終了コード 4) として緊急用に知らせる** — 試しただけで緊急の通知が飛ぶ。**却下。** 送らずに WARN を残す
7. **試しの窓の始まりをそのまま差分判定の境界にする** — 実装は 1 行少ないが、続いている事象が「再発」と出て、定時の実行の結果と食い違う (テストで再現)。**却下**

## 結果 (良い点・引き受けるコスト)

- 定時の前に何度でも試せる。通知を飲み込まず、窓も進まない。`--window 1h` なら LookupEvents も Insights のスキャンも短く済む
- 判定の規則は 1 か所のまま。試しの実行と定時の実行で同じコードが動く
- 引き受けること:
  - SQLite を 1 回写す時間とディスク (一時ディレクトリ。終了時に消す。中断すると残ることがある — S3 の作業用の複製と同じ)
  - 短い窓の結果は定時の実行と同じではない。見ていない期間の出来事は出ず、日次集計のチェックは評価する日が減る。注記で分かるようにした
  - 失敗したソースの追いつきをしないので、追いつき中のソースの結果も定時の実行と違う (見た範囲の注記に含まれる)
  - 複製した後に定時の実行が進めば、試しの結果は少し古い状態に対するものになる (試しの実行は何も書かないので、害は無い)
  - `dry_run` を知らない古い aratam は、試しの報告を通常どおり送る。試しの実行を使うなら aratam も同じ版にそろえる
  - AWS の読み取り (LookupEvents・Logs Insights) は実際に行う。Insights の費用は窓の長さに応じてかかる

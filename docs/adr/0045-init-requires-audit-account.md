# 0045. `config init` は監査する側のアカウントを必ず選ばせ、選んだ結果を設定と既知リストに残す

- 日付: 2026-11-13
- 状態: 採用

## 背景

arata を GitHub Actions などで動かす構成では、実行用ロール (`deploy/github-actions/runner.yaml`) が、監査対象のアカウントの読み取り専用ロール
(`deploy/iam/readonly-role.yaml`) を引き受けて監査する。実行用ロールが監査対象とは別のアカウント (例 `111122223333`) にあると、
監査対象 (例 `123456789012`) の CloudTrail には「外部アカウント 111122223333 が読み取り専用ロールを引き受けた」と毎回記録される。

既知リストにそのアカウントが無いと、`unknown_assume_role` が監査そのものを high で報告する。これまでは人が既知リストに後から足す運用で、
手順書 (`examples/github-actions/README.md`) に書いてあるだけだった。監査対象を足したときに書き忘れ、誤った通知が出た。
人が後から足す運用では、監査対象を足すたびに同じことが起き得る。

ロール側 (監査対象) の CloudTrail の記録には、別のアカウントからの呼び出し元は **アカウント ID と principalId しか残らない**
(どのロールかは残らない)。arata はこれを「外部アカウントそのもの」(`arn:aws:iam::NNN:root`) に正規化するので、止められるのは既知リストの `account:` の項目だけである。

## 決定

**`arata config init` は、監査する側のアカウントを `--audit-account` で必ず選ばせる。既定は持たない。**

| 指定 | 意味 | 書くもの |
|---|---|---|
| `--audit-account <12 桁の ID>` | 別のアカウントのロールが、監査対象の読み取り専用ロールを引き受けて監査する | 設定に `audit_account: "<ID>"`。既知リストの `principals` に `account: "<ID>"` (note つき) |
| `--audit-account none` | 外から監査しない (監査対象と同じアカウントの中で動かす・手元の認証で直接動かす) | 設定に `audit_account: none`。既知リストには書かない |
| 指定なし・それ以外の値 | — | エラー (`CONFIG_INVALID`、終了コード 2)。エラー文で 2 つの選択肢と意味を示す。何も書かない |

細部:

- **選んだ結果は設定と既知リストに残る。** 設定の `audit_account` は「選んだ」ことの記録で、`none` も書く (書いていない = 選んでいない、と区別できる)
- **`audit_account` は判定に使わない。** 承認は既知リストだけが持つ (人が見て承認した一覧を 1 か所に保つ。ADR 0004)。
  `audit_account` は、既知リストとの食い違いを機械が確かめるための材料にする
- **既知リストの項目**: `account: "<ID>"`、理由の `note`、`approved_at` は今日 (UTC)
  - `approved_by` は `--by` を付けたときだけ書く。init は承認者を知らない。`approve` のように OS のユーザー名を既定にしない
    (雛形を作る人と承認する人は別でよく、承認は既知リストの PR のレビューが担う)
  - `expires` は付けない (監査が続く限り要る)
  - `dynamic_source` は書かない。principal_new_source が見るのは IAM ユーザーとロールで、外部アカウントそのものは対象でない (書いても効かない)
  - 既知リストが既にあれば、approve と同じ差し込み (ADR 0010) で `principals` の末尾に足す。ほかの行は変えない。同じ `account:` があれば足さない。
    既知リストが壊れていて足せないときは、設定も書かない
  - 場所は雛形の `allowlist: allowlist.yaml` (`--out` と同じディレクトリ)。`--out -` (標準出力) では既知リストを書かず、足す項目を標準エラーに出す
- **受け付ける値** は ASCII の数字ちょうど 12 桁か `none` だけ。大文字・前後の空白・ARN は直さずに断る。値は YAML にそのまま書くので、
  数字以外を通さないことをファズで確かめる (ADR 0041)
- **食い違いの検査**:
  - `arata config check` (オフライン): `audit_account` に ID を書いたのに、期限内の `account:` の項目が既知リストに無ければ ng (終了コード 2)。
    `arn:` / `arn_pattern:` の項目は数えない (ロール側の記録を止められない)
  - `arata doctor`: 同じ検査に加えて、その ID が監査対象のアカウントそのもの (`sts:GetCallerIdentity`。権限不要) なら ng。
    「監査する側」を「arata を動かしているアカウント」と読んで監査対象の ID を書くと、`account:` が監査対象の全主体を承認し、
    new_principal などが黙ってしまう。オフラインでは分からないので doctor で止める
- **この項目より前の版で作った設定** (`audit_account` が無い):
  - `run` / `doctor` / `evaluate` は今までどおり動く (止めない)
  - `config check` は warn (終了コード 0)。`config init --diff` は `[missing_key] audit_account` を出す。どちらも直し方を文に含める
  - 直し方: 設定に `audit_account: none` か `audit_account: "<12 桁の ID>"` を 1 行足す。ID を書くなら既知リストに `account: "<同じ ID>"` を足す

## 検討した選択肢

1. **人が後から既知リストに足す (これまで)** — 手順書に書くだけ。書き忘れが実際に起き、誤った high の通知になった。却下
2. **`run` が実行時に自分の呼び出し元を調べて自動で除く** — `sts:GetCallerIdentity` で監査する側が分かっても、それを黙って除くのは暗黙の既定で
   (ADR 0014)、既知リスト (人が承認した一覧) の外に承認が増える。読み取り専用ロールを別の主体が引き受けたときとの区別も設定に残らない。却下
3. **`audit_account` をそのまま判定に使う (既知リストに書かない)** — 承認の場所が 2 か所になり、`arata approve`・期限・レビューの流れから外れる。却下
4. **`--audit-account` に既定 (`none`) を持たせる** — 選ばなかった人は今と同じ誤報に当たる。「必ず選ばせる」ことが目的なので却下
5. **`audit_account` を設定の必須項目にする (無ければ `run` も止める)** — 版を上げただけで既存の利用者の監査が止まる。監査が止まるほうが誤報より悪い。
   必須にするのは init (新しく作るとき) だけにし、既存の設定には warn と差分で知らせる。却下
6. **既知リストに無いとき `run` も止める** — 5 と同じ理由で却下。その状態の run は `unknown_assume_role` (high) で知らせるので、黙っては進まない
7. **実行用ロールの ARN を受け取り、`arn:` で書く** — 別のアカウントからの引き受けは、ロール側の記録にアカウント ID しか残らないので効かない。
   同じアカウントの中の実行用ロールは `arn:` で書けるが、それは `none` の構成で、今回は手で足す手順のままにする (下の「引き受けるコスト」)

## 結果 (良い点・引き受けるコスト)

- 監査対象を足すたびに init を使えば、監査そのものの AssumeRole の誤報は起きない。書き忘れは PR の `config check` で止まる
- 選択が設定に残るので、「別のアカウントから監査している」ことが設定から読める。LLM が finding を調べるときの手がかりにもなる (`arata help ai approve`)
- **init の互換性が壊れる**: `--audit-account` の無い `arata config init` はエラーになる。手順書・スクリプトは `--audit-account none` か ID を足す
- `config check` の規則は run / doctor の起動時の検証と同じ、という ADR 0042 の原則に例外が 1 つできる (既知リストとの食い違いは check と doctor だけが止め、run は止めない)。
  理由: ADR 0042 の原則は「check が通した設定は run でも読め、逆も同じ」ことを守るためのもので、設定と既知リストの **形** の規則は今も同じ (`config.Load`・`allowlist.Parse`)。
  ここで足したのは形ではなく 2 つのファイルの間の食い違いの検査で、run でも止めると、版を上げた・期限が切れただけで監査が止まる (選択肢 5・6)。
  食い違いのある run は `unknown_assume_role` (high) で知らせるので黙っては進まず、check は同じ問題をマージの前に止める。例外はこの 1 つに限る
- `account:` はそのアカウントの全主体を承認する。ロール側の記録の限界で、これより狭くは書けない。読み取り専用ロールを引き受けられる主体は、
  信頼ポリシー (`TrustedPrincipalArn`) で実行用ロールだけに絞る
- 同じアカウントの中の実行用ロール (`none` の構成) は、今までどおり `arn:` で手で足す。init はそれを書かない (init の出力と手順書で案内する)。
  ここも選ばせるかは、使われ方を見て決める
- `audit_account` の無い設定は warn にとどまるので、既存の利用者は自分で 1 行足すまで検査の恩恵を受けない

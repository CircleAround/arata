## 背景

今の cloudwatch-logs のソースは 1 行ずつ解釈する (`parse @message` のあと、そのまま `stats`)。1 リクエストが 1 行で完結するログ
(nginx・ALB・JSON の行ログ) はこれで足りる。

アプリの標準のログは 1 リクエストが複数行に分かれることがある。Rails の既定のログは次の形で、送信元とパスは最初の行、ステータスは最後の行にある。
本番の既定では各行の本文の前に `[<request_id>]` のタグが付く (`config.log_tags = [:request_id]`)。
タグは行頭には来ない。Ruby の Logger の既定の formatter では、重大度・時刻・プロセス番号の後ろに付く (下の例)。
独自の formatter では、行頭に別の角括弧 (ホスト名やコンテナの ID など。英数字とハイフン) が付くこともある。

```
I, [2026-11-01T01:02:03.000000 #1]  INFO -- : [5b0c…e1] Started POST "/users/sign_in" for 203.0.113.10 at 2026-11-01 01:02:03 +0000
I, [2026-11-01T01:02:03.004000 #1]  INFO -- : [5b0c…e1] Processing by Devise::SessionsController#create as HTML
I, [2026-11-01T01:02:03.005000 #1]  INFO -- : [5b0c…e1]   Parameters: {…}
I, [2026-11-01T01:02:03.016000 #1]  INFO -- : [5b0c…e1] Completed 422 Unprocessable Content in 12ms
```

(認証ライブラリの既定では、ログインの失敗は入力画面の再表示で 422 になる。古い設定では 200。`login_bruteforce` の `failure_statuses` で合わせる。`docs/ai/logs.md`)

1 行ずつの `regex` プロファイルでは「このパスへのリクエストが失敗のステータス (422 など) だった」を数えられない (設計書 2 章は Rails を `regex` で扱うとしていたが、拾いきれない)。
アプリの前に nginx や ALB のログが無い利用者では、`http_access` を使うチェック (`login_bruteforce`・`probe_paths`・`endpoint_abuse`) が skip されたままになる。

### 確かめた事実 (実環境の Logs Insights)

- 1 つのクエリの中で `stats` を 2 段に重ねられる。`parse` で request_id と行ごとの項目を取り出す → `stats … by <request_id>` で 1 リクエスト 1 件にする →
  `stats … by <軸>` で集計する、が 1 回のスキャンで動いた。複数行のログからリクエスト単位の記録を作り、手元に引かずにそのまま集計できる
- ユーザー ID が取れるかはアプリによって違う:
  (a) ログのどこにも出ない。
  (b) debug レベルの SQL の行 (認証ライブラリがセッションから利用者を読み込む `WHERE "<表>"."id" = $1 ORDER BY … LIMIT` の形) から取れる。ただし本番で debug が出ているのは誤設定で、直されれば消える。
  (c) アプリが 1 行足せば取れる
- (b)(c) のどちらでも、ログイン前の画面・webhook・ヘルスチェックなど、ID の無いリクエストは必ず残る
- `login_bruteforce` は今もパスとステータスでログインの成否を判断している。アプリにログを足さなくても動く

### 主題

「ログを理想の形に直してもらう」ことを前提にしない。**アプリごとに取れる項目が違う中で、取れた分だけ分析する**。
取れない項目に頼るチェックは黙って 0 件にせず、動いていないことを報告に出す。

## 決定

### 1. リクエスト単位にまとめるのは、形式プロファイルの前処理で行う (レコードの種類は増やさない)

- 新しい形式プロファイル `request_lines` を足す。設定に「まとめる鍵 (request_id) の取り出し方」と「行の種類ごとの取り出し方」を書く。
  arata はこれを Insights の前処理 (ADR 0009 の 3 層の 1 層目) に変換する: 行ごとの `parse` のあと `stats … by <request_id>` を 1 段目として置く。
  2 段目は今の `http_access` の集計 (`sign_in_failures`・`probe_hits`・`probe_paths`・endpoint_abuse の集計) をそのまま使う

```yaml
sources:
  - id: rails_app
    kind: cloudwatch-logs
    log_group: prod-app.log
    format: request_lines                 # yields は http_access (ユーザー ID が取れる設定なら http_user も)
    request:
      id: ' -- : \[(?P<request_id>[A-Za-z0-9-]{1,255})\] '   # 前の区切り (既定の formatter の ` -- : `) まで含めて書く
      max_duration: 60s                   # 問い合わせ範囲の前後に足す余白 (6 節)
      lines:
        - name: started
          regex: 'Started (?P<method>[A-Z]+) "(?P<path>[^"?]*)[^"]*" for (?P<ip>\S+) at '
        - name: completed
          regex: 'Completed (?P<status>\d{3}) '
        - name: no_route                  # Completed の行が出ないリクエストの補い (確かめが要る点)
          regex: 'ActionController::RoutingError'
          set: { status: 404 }
    user_id:                              # 4 節。既定は from: none
      from: app_line
      regex: 'actor kind=(?P<user_kind>[a-z_]{1,32}) id=(?P<user_id>[A-Za-z0-9_-]{1,64})$'
    expected_match_rate: 0.8              # request_id の付いた行の割合
    expected_complete_rate: 0.8           # ip と path が揃ったリクエストの割合
```

```
# クエリの形の例 (sign_in_failures。値を拾う関数は実装のときに固定する)
parse @message / -- : \[(?<rid>[A-Za-z0-9-]{1,255})\] /
| parse @message /Started (?<m>[A-Z]+) "(?<p>[^"?]*)[^"]*" for (?<i>\S+) at /
| parse @message /Completed (?<s>\d{3}) /
| filter ispresent(rid)
| stats earliest(m) as method, earliest(p) as path, earliest(i) as ip, latest(s) as status, count(m) as starts by rid
| filter path = "/users/sign_in" and method = "POST" and status = 422
| stats sum(starts) as n by ip
```

- `request_lines` のソースは **`http_access` を出す**。1 行で完結するログは「1 行 = 1 リクエスト」で、1 段目が要らないだけの同じもの。
  チェック (`login_bruteforce`・`probe_paths`・`endpoint_abuse`) は変えない。metric の名前・key・平常帯の計算も同じ。
  「リクエスト単位の記録 (http_request)」はクエリの中の中間の形の呼び名で、ストアのレコードの種類にはしない
- 取り出せる項目は決まった名前だけ (`request_id`・`ip`・`method`・`path`・`status`・`ua`・`duration`・`user_kind`・`user_id`)。知らない名前のキャプチャは `CONFIG_INVALID`。
  Parameters の行のように利用者の入力が入る行から任意の値を取り出す設定は書けない
- `http_access` の必須は今と同じ `ip` と `path`。Rails の既定のログには UA が無い。無い項目を使う集計は 0 件になる (今の規則) のに加えて、
  どの項目が取れているかを coverage に出す (2 節)
- 解釈率は 2 つ測る。どちらも run の stats と `coverage.formats` に出す (設計書 2-2 の拡張)
  - 行の解釈率 = request_id の付いた行 / 全行。`lines_total` / `lines_matched` は今の意味のまま (ロググループ全体の行数。endpoint_abuse の「収集した日」に使う)。`expected_match_rate` 未満で `FORMAT_MISMATCH`
  - まとめられた割合 = `ip` と `path` が揃ったリクエスト / request_id の数 (`requests_total` / `requests_complete`)。`expected_complete_rate` 未満でも `FORMAT_MISMATCH`。
    ステータスの取れた割合・ユーザー ID の付いた割合も添える
- **request_id の正規表現は、前の区切りまで含めて書く。行頭にも「最初の角括弧」にも頼らない**。
  行頭に固定すると、既定の formatter のログでは 1 行も当たらない (これは行の解釈率が 0 になるので気づける)。
  固定を外して「最初の `[…]`」を取ると、時刻やホスト名の角括弧を request_id と取り違え、全部の行が数個の鍵にまとまる。
  このときは行の解釈率もまとめられた割合も高く出るので、**黙って数が壊れる**。そこで
  - 設定の見本と `arata help ai` は、区切りを含む形 (既定の formatter なら ` -- : \[…\] `) だけを載せる。独自の formatter では、その形の区切りを利用者の見本の行から書く
  - doctor と run は「request_id の異なりの数」と「最初の行 (Started) の数」を比べる。異なりの数が最初の行の数より極端に少ない
    (既定の案: 半分未満。閾値は実装のときに実データで見直す。`request_id_reused` が大半を占める形) なら取り違えとみなし、doctor は ng、run は `FORMAT_MISMATCH` にして集計を保存しない
    (平常帯を汚さない。設計書 2-2 と同じ扱い)
    。送る側が ID を大量に使い回してもこの検査に当たり得るが、そのときも黙って数えずに失敗として報告に出るほうを選ぶ (終了コード 3 で気づける)
  - テストの性質に入れる: 既定の formatter の行・行頭に別の角括弧がある行の見本で、見本の設定がリクエストの数だけ鍵を作ること。
    取り違える設定 (最初の角括弧) を与えると、上の検査が必ず止めること
- **request_id は信用しない** (ADR 0037)。Rails は、リクエストに `X-Request-Id` ヘッダーがあればその値 (英数字とハイフン、255 文字まで) を request_id に使う。
  送る側が値を選べるので、次の規則を置く
  - 鍵の正規表現は UUID の形に絞らない。絞ると、形の違う ID を付けたリクエストが「request_id の無い行」になり、全部のチェックから外れる
  - 同じ ID を使い回されても数が減らないように、件数は「まとめた件数」ではなく最初の行 (Started) の数で数える (上の例の `starts`)。
    1 つの ID に最初の行が 2 つ以上あるものは項目が混ざるので、その数を集計 (`request_id_reused`) として残し、doctor と coverage に出す
  - この 2 つは守る規則としてテストとファズテストに書く (ADR 0041: 「同じ ID を何度使っても、数えたリクエストの数は最初の行の数より減らない」)
  - 利用者には、前段 (リバースプロキシなど) で `X-Request-Id` を上書きする設定を文書で勧める (勧めるだけで、前提にはしない)
- 同じアプリに 1 行のログ (ALB など) と複数行のログの両方があるときは、両方が `http_access` を出すと件数が重なる。
  チェックごとにソースを選ぶ今の方式 (`endpoint_abuse` の `sources`) を他の `http_access` のチェックにも広げる。
  目安: 段 0 の項目は項目の揃う 1 行のログ (UA がある) から、ユーザー ID はアプリのログから取る。2 つのソースを 1 リクエストに突き合わせることはしない (却下した案)

### 2. 取れる項目を段で整理し、チェックは要る項目を yields の種類として宣言する

| 段 | 取れるもの | 要る準備 |
|---|---|---|
| 段 0 | ip・パス・メソッド・ステータス・時刻 (あれば UA) | ログの設定だけ。アプリは変えない |
| 段 1 | + ユーザー ID (種類と ID) | 4 節のどれか |
| 段 2 | + 重要な操作の定義 (名前・パスの glob・メソッド・ステータス)、対象 ID の位置の定義 | 設定に書く (ログは変えない) |

段は説明のための並びで、入れ子ではない (UA の無い段 1、ユーザー ID の無いまま重要な操作だけ定義した段 0 + 定義、がある)。
そこで仕組みは「段の番号」ではなく**項目と定義の有無**で持つ。

- ログから取れる項目は、ソースの yields の種類で表す。今の `http_access` (段 0) に、ユーザー ID を取り出す設定があるソースだけが出す `http_user` を足す。
  チェックは今と同じ `Needs()` で宣言する。`http_user` を出すソースが無ければ「設定不足」で skip し、`coverage.checks_skipped` に `no http_user source` と出る (既存の仕組みのまま。設計書 2 章・4-2)
- 設定に `user_id` を書いていても、その run でユーザー ID の付いたリクエストが 0 件なら、そのソースはその run では `http_user` を出さなかったものとして扱い、
  段 1 のチェックを skip して coverage に理由を出す (「取れなくなった」を「何も起きていない」と取り違えない。4 節)
- 設定で決まる定義 (重要な操作・対象 ID の位置) は、`endpoint_abuse` の `endpoints` と同じく既定は空 = 何もしない (ADR 0014)。足した既定値は `config init --diff` で見えるようにする
- doctor は、ソースごとに「取れている項目」と「それで動くチェック・動かないチェックと理由」を表で出す

段ごとに動かせるチェック (新しいものは案。名前は仮。作る順は 7 節):

| チェック | 要るもの | 見るもの |
|---|---|---|
| login_bruteforce / probe_paths / endpoint_abuse (既存) | 段 0 | 今のまま。`request_lines` のソースでも動く |
| id_enumeration (新) | 段 0 + 対象 ID の位置 | 1 つの送信元 (/24・/48) が、同じ形のパス (`/orders/:id` など) で触った異なる ID の数が、ふだん超え。403・404 の割合を根拠に添える |
| target_fan_in (新) | 段 0 + 対象 ID の位置 | 本人しか触らないはずの対象 (`/accounts/:id/settings` など) 1 つに、別々の送信元から来た数が、ふだん超え。乗っ取り・ID の共有の兆候 |
| sensitive_new_source (新) | 段 0 + 重要な操作 | 重要な操作 (パスワード・連絡先の変更、出力、管理の操作) をした送信元が、過去 N 日にこのアプリへ来たことのない送信元。段 0 では「送信元にとって初めて」までしか言えない |
| source_multi_user (新) | 段 1 | 1 つの送信元から使われた異なるユーザー ID の数が、ふだん超え。認証情報の使い回しの成功・アカウントの量産の兆候 |
| user_multi_source (新) | 段 1 | 1 つのユーザー ID が 1 日に使った異なる送信元の数が、ふだん超え。セッションの横取り・共有の兆候 |
| sensitive_new_source (段 1 の版) | 段 1 + 重要な操作 | そのユーザーが、重要な操作を初めての送信元から行った (`principal_new_source` のアプリ版。ADR 0027) |
| sensitive_action_volume (新) | 段 1 + 重要な操作 (段 0 では送信元ごと) | ユーザーごとの重要な操作の件数が、ふだん超え。大量の出力・一括の変更 |

- 段 0 のユーザー寄りの見方 (id_enumeration・target_fan_in・sensitive_new_source) は、ユーザー ID の代わりに**パスの中の対象 ID** と**送信元の履歴**を手がかりにする。
  アプリを変えずに全部の利用者で動くので、段 1 のチェックより先に作る
- どのチェックも事実 (件数・異なり数・ふだんの上限) を報告し、遮断の提案にしない (ADR 0030 と同じ)。NAT (事業所・携帯の回線) の送信元は多数のユーザーをまとめるので、
  ふだんとの比較と `trusted_cidrs` で扱い、重大度は medium までにする
- 段 1 のチェックが見るのは ID の付いたリクエストだけ。ID の無いリクエストは段 0 のチェックが見る。ID の付いた割合を coverage に出し、「見ていない範囲」を隠さない

### 3. ストアに置くのは日次の集計だけ (リクエストの行は置かない)

- 新しい集計は `metrics` に、主体の活動の日次集計 `principal_source` (ADR 0027) と同じ形で置く: key は `<軸>|<軸>`、値は件数か異なり数、日は UTC、後の値で置き換える。
  rebuild の規則 (ADR 0033) も今のまま当てはまる
- 理由:
  - S3 のストアは SQLite を実行のたびに丸ごと取得し、書き戻す (ADR 0034)。リクエスト単位の行は 1 日で数万〜数百万になり、実行の時間と転送量がそのまま増える
  - Insights が 1 回で返す件数には上限 (10000) がある。リクエスト単位の行を手元に引く方式は、量のあるログでは最初から成り立たない。Insights の中で集計まで終える形だけが量に耐える
  - 値の原文を持たない方針 (ADR 0030: IP と UA の原文を保存しない。2-2: サンプル行を報告に出さない) と合わない。リクエストの行はパスの全部・時刻・送信元の組で、個人の行動の記録になる
  - 原本は CloudWatch Logs に残る。調べるときは報告の key (送信元・ID・日) で Insights を引けばよい (playbook にクエリの例を書く)
- 行数を抑える規則: 「ユーザー × 送信元」を全部のリクエストについて持つと、利用者の多いアプリでは 1 日に利用者の数だけ行が増える。そこで
  - 異なり数の集計 (id_enumeration・target_fan_in・source_multi_user・user_multi_source) は、**設定の下限を超えた key だけ**を日ごとに上位 N 件 (既定の案 50。`top_paths` と同じ考え方) 保存し、
    ふだんの比較のために分布 (p50・p99・最大) を 1 行ずつ持つ
  - 送信元の履歴 (sensitive_new_source) は、**重要な操作をしたリクエストの**「(ユーザー ID または対象 ID) × 送信元の /24・/48」だけを持つ。ふだんの閲覧の送信元は持たない。
    そのぶん「重要な操作としては初めての送信元」しか言えない。履歴が `min_baseline_days` に満たない間は報告しない (ADR 0007 の baseline と同じ考え方)
  - 見積もり: 重要な操作が 1 日 500 件・送信元が 1 人 1〜2 個なら 1 日 1,000 行未満、400 日で 40 万行未満 (endpoint_abuse の見積もりと同じ桁)
- ユーザー ID・対象 ID は key にそのまま置く (報告で主体を ID で表すため。メールアドレス・氏名は置かない)。形は規則で絞る:
  `[A-Za-z0-9_-]` の 64 文字まで。合わない値 (`@` を含むなど) は捨てて数に残す。メールアドレスを ID に使うアプリでは、段 1 を使わないか、アプリの側で別の ID を出してもらう。
  パスの key は今と同じ正規化と伏せ字 (設計書 2 章)

### 4. ユーザー ID の取り方は設定で選び、消えうる取り方はそう書く

`user_id.from` (既定は `none` = 段 0):

| 値 | 取り方 | 安定さ |
|---|---|---|
| `none` | 取らない | — |
| `app_line` | アプリが意図して出す 1 行を `regex` で読む | 安定。**勧める形** |
| `debug_sql` | debug レベルの SQL の行 (セッションから利用者を読み込む問い合わせの束縛値) を `regex` で読む | **消えうる**。下の注意 |
| (json 形式) | 今の `fields.user_id` の対応 | 安定 |

- `debug_sql` の注意を設定の雛形・doctor・`arata help ai` に書く: 本番で debug レベルのログが出ているのは誤設定で、直されればこの取り方は予告なく 0 件になる。
  debug のログは秘密や個人の値を含み得るので、arata のために残すことを勧めない。問い合わせの形はライブラリの版でも変わる。`app_line` へ移るまでのつなぎとして使う
- 消えたことを見つける規則: ID の付いたリクエストの割合を run ごとに記録し、0 件ならその run で段 1 のチェックを skip (2 節)、
  直近の平均から大きく落ちたら `FORMAT_DRIFT` と同じ扱いの警告を出す。doctor は `debug_sql` を使っている間ずっと warn を出す
- アプリに足してもらう 1 行の勧める形 (種類と ID だけ。メールアドレス・氏名・ログイン名は出さない):

```
I, [2026-11-01T01:02:03.010000 #1]  INFO -- : [<request_id>] actor kind=user id=42
```

```ruby
# Rails の例 (ApplicationController)。ログインしているリクエストだけ 1 行出す
after_action { logger.info("actor kind=user id=#{current_user.id}") if current_user }
```

  `kind` は利用者の種類 (`user`・`admin` など。同じ番号の別の種類を区別する)、`id` は内部の番号か不透明な ID。
  行の形は固定の語で始め、request_id のタグの中に出す。JSON の行ログ (lograge など) を使うアプリでは、同じ 2 つを項目として足す。
  実装のときに、この節を `arata help ai logs` (記録の集め方) に入れる
- ID の無いリクエスト (ログイン前・webhook・ヘルスチェック) は残る前提にする。ログインの成否は今のままパスとステータスで判断し、ユーザー ID を要求しない

### 5. 導入は LLM が設定を書き、規則で確かめる。実行時は規則だけ

- 設定 (`request:` と `user_id:` の正規表現) は、利用者の環境の LLM (Claude Code など) が見本の行から書く。`arata help ai` に、`request_lines` の設定の書き方・既知の形 (Rails の既定) の見本・確かめ方を足す。
  arata 自身は LLM を呼ばない (ADR 0001)
- 確かめる手順は道具で固定する:
  1. `arata config check` (オフライン。正規表現が RE2 で読めるか、キャプチャの名前が決まったものか、必須の項目があるか)
  2. `arata doctor` (行の解釈率・まとめられた割合・ステータスの取れた割合・ID の付いた割合・request_id の異なりの数と最初の行の数の比 (取り違えの検査)・`request_id_reused`・行の種類ごとの当たった数・スキャン量の見積もり)。
     行の種類ごとの数が出るので、LLM は当たらない行の種類を見て直せる
  3. `arata run --dry-run` (ADR 0049) で、実際に出る指摘を見る
- LLM の書いた設定は「利用者のファイル」として信用しない入力に当たる。解釈する関数にはファズテストを足す (ADR 0041)。
  実行時に効くのは設定に書かれた規則だけで、ログの値で振る舞いを変えない (ADR 0037)
- 見本の行を LLM に渡すときの注意 (メールアドレスの伏せ字は doctor のサンプルと同じ規則。氏名は伏せられないので、利用者が渡す範囲を決める) を文書に書く

### 6. 上限・費用・窓の境界

- **件数の上限**: 最後の `stats` の結果は 10000 行まで (今と同じ)。当たったら範囲を半分に分けて引き直し、それでも当たれば `truncated` に残す (ADR 0031 の規則)。
  新しい集計は Insights の中で上位 N 件と分布まで絞るので、当たりにくい
- **stats の段数**: 1 段目をまとめに使うので、`request_lines` のソースで集計に使える `stats` は残り 1 段になる見込み (段数の上限は確かめが要る点)。
  今の `http_access` の集計は 1 段なのでそのまま載る。異なり数は 2 段目で `count_distinct` (概数) を使う。下限との比較に使う値なので概数を引き受け、根拠にも「概数」と書く。
  1 行のログのソースでは今までどおり 2 段を使って正確に数えられる
- **費用**: Insights の課金はスキャン量で、1 本ごとに範囲のログ全体を読む。まとめる 1 段目はスキャン量を増やさない。増えるのは本数の分:
  `request_lines` のソースは既存の 3 本 (解釈率 + `probe_paths`、`sign_in_failures` + `probe_hits`、endpoint_abuse) が同じ本数のまま、
  新しい集計は軸の和集合で 1〜2 本にまとめる (ADR 0031)。アプリのログは行が多い (1 リクエスト数行 + SQL) ので、1 本あたりのスキャン量は nginx のログの数倍を見込む。
  `max_scan_gb` と doctor の見積もり (ADR 0028) がそのまま効く。新しいチェックをプロファイルに入れなければ、その集計のクエリは流さない (設計書 3 章)
- **窓の境界**: 集計は今と同じく UTC の日の 0 時から窓の終わりまで引き、日次集計を置き換える (ADR 0009・0013)。リクエストの行が境界をまたぐので、
  - 問い合わせの範囲を前後に `request.max_duration` (既定の案 60 秒) だけ広げ、リクエストは**最初の行の時刻の日**に数える。最初の行が範囲に無いものは数えない (前の日の分)
  - 窓の終わり (今) で途中のリクエストは、次の run が日の頭から引き直すので後で揃う。余白より長いリクエスト (長い出力・ストリーミング) は、まとめられた割合の分母に残り、項目が欠ける
  - 範囲を半分に分けて引き直すときも、分けた境目に同じ余白を付ける

## 確かめが要る点 (実装の前に sandbox で)

- 1 つのクエリに置ける `stats` の数 (2 段は動いた。3 段以上が使えるか。公式文書の記述と実際の動き)
- 1 段目 (`by <request_id>`) の中間の結果に件数の上限があるか。あるなら、黙って切れるのかエラーになるのか (件数の分かっているログで、2 段目の合計が合うかを見る)
- 行をまたいで値を拾う関数 (`earliest`・`latest`・`sortsFirst` など) が、値の無い行を飛ばすか。飛ばさないなら別の書き方にする
- 1 段目で作った時刻 (`min(@timestamp)`) を 2 段目の `bin()` に渡せるか (日・endpoint_abuse の時間幅の切り分けに要る)。渡せなければ 1 段目の `by` に `bin()` を入れ、境界で割れたリクエストを Go で合わせる
- `set: { status: 404 }` のような固定値の補いを、1 段目のあとの `fields` で書けるか
- 量のあるログ (1 日数百万リクエスト) で `by <request_id>` が時間内に終わるか。終わらなければ範囲を分ける (今の待ちの上限は 15 分)
- 経路の無いパスへのリクエストなど、Completed の行が出ないリクエストの実際の行の形 (`probe_paths` は 404 に頼る)
- アプリのログの `for <ip>` が、前段のプロキシではなく利用者の送信元になっているか (アプリの信頼するプロキシの設定による。doctor では判定できないので、導入の文書に確かめ方を書く)
- `X-Request-Id` を付けたリクエストの実際のログ (ID の使い回し、長い ID)

## 検討した選択肢

- **リクエスト単位の行を手元に引き、Go でまとめて集計する**: まとめ方を自由に書け、正確に数えられる。Insights の結果の上限 (10000) で量のあるログでは成り立たず、
  行の原文 (Parameters を含む) が実行環境を通る。却下。Insights の中でまとめる
- **リクエスト単位の行をストアに置く** (`requests` の表や raw の JSONL): 後から別の切り口で集計し直せる。S3 のストアの出し入れ・値の原文を持たない方針・保持の責任が合わない (3 節)。
  原本は CloudWatch Logs にあるので、切り口を足したいときは集計を足して引き直す。却下
- **新しいレコードの種類 `http_request` を作り、チェックを別に書く**: 既存の 3 つのチェックを二重に持つことになり、平常帯も別になる。
  1 行のログも「1 行 = 1 リクエスト」なので、前処理の違いとして吸収する。却下
- **最初の行 (Started) だけを 1 行ずつ読む**: 今の `regex` で書ける。ステータスが無いので `login_bruteforce` (失敗のステータス)・`probe_paths` (403・404) が判定できない。却下
- **アプリに 1 行の JSON のログ (lograge など) へ変えてもらうことを前提にする**: 一番きれいだが、アプリの変更とログを読む他の仕組みへの影響があり、導入が利用者の開発の都合で止まる。
  勧める道として文書に残し、前提にはしない。変えたアプリは今の `json` 形式でそのまま読める
- **ユーザー ID の無いリクエストを、同じ送信元・近い時刻のリクエストの ID で補う**: 推測で主体を決めることになり、NAT の後ろで別の利用者に付く。却下。ID の無いものは無いまま数える
- **debug の SQL からの取り出しを組み込みの既定にする**: アプリを変えずに段 1 になるが、誤設定に依存し、直された日に黙って止まる。設定で明示して選ぶものにし、消えうることを書く (4 節)
- **1 行のログ (ALB) とアプリのログを 1 リクエストに突き合わせる**: UA とユーザー ID が同じ記録に揃う。共通の鍵が既定では無く (アプリの request_id は ALB のログに出ない)、
  時刻と送信元で合わせるのは推測になる。却下。チェックごとにソースを選ぶ
- **チェックに「要る段の番号」を宣言させる**: 段が入れ子でない (UA の有無、定義だけある場合) ので番号では表せない。yields の種類 (`http_user`) と定義の有無で表す
- **request_id を UUID の形に絞る**: 設定が読みやすい。ヘッダーで別の形の ID を送ればチェックから外れられる。却下 (1 節)
- **実行時に LLM にログの形を判断させる**: 形の変化に追従できる。ログの値で振る舞いが変わり、判定を規則に置く方針 (ADR 0001・0037) に反する。却下。LLM は導入のときに設定を書くだけ

## 結果 (良い点・引き受けるコスト)

- 良い点: アプリの標準のログしか無い利用者でも、アプリを変えずに既存のチェックが動く。取れる項目が増えるごとに動くチェックが増え、
  取れていない項目に頼るチェックは skip として報告に出る。リクエストの行を手元にもストアにも持たない
- 引き受けるコスト:
  - アプリのログは行が多く、Insights のスキャン量が nginx・ALB のログより大きい。項目の揃う 1 行のログがあるなら、段 0 はそちらを勧める
  - `request_lines` のソースでは異なり数が概数になる。境界をまたぐリクエスト・余白より長いリクエストは項目が欠ける (割合を報告に出す)
  - 送信元の履歴を重要な操作に絞るので、「ふだんの閲覧では使っていた送信元」を初めてと報告することがある
  - `debug_sql` は消える。消えたことは報告に出るが、その間の段 1 のチェックは動かない
  - 設定 (正規表現) が増える。書くのは LLM でも、確かめるのは `config check`・doctor・`--dry-run` で、利用者がその結果を読む必要がある
  - request_id を送る側が選べる限り、ID の使い回しで項目を混ぜることはできる。件数は減らさず、使い回しの数を報告に出すところまでを守りにする

## 確かめた結果と実装で変えた点 (2026-11-14)

「確かめが要る点」の答え (本番相当のログの Logs Insights):

- `stats` は 3 段でも動く
- 1 段目の中間の結果は、1 日 1 万弱のリクエストでは切れなかった。量の多いログでの上限は未確認のまま
- `earliest` / `latest` は、その項目の無い行を飛ばす
- 1 段目で作った時刻は 2 段目の `bin()` などに渡せない。1 段目の前に `fields bin(1d) as <名前>` を置き、1 段目で `min(<名前>) as day`、2 段目で `by day` とする
- `stats` の後の `fields if(<条件>, "404", <項目>) as <別の名前>` は動く
- 経路の無いリクエストは最後の行が出ず、例外の行は Logger の前置きの無い続きの行 (行頭が `[<request_id>] `) になる
- `count_distinct` は概数で、数 % 多く出た例がある

実装で変えた点 (設計書 2-4 が正):

- **request_id の正規表現**: 「行頭に頼らない」は「行頭だけに頼らない・最初の角括弧に頼らない」と読み替える。続きの行は行頭に鍵が来るので、
  見本は「前置きのあと」と「行頭」の両方を受ける (`(?:^| -- : )\[…\] `)。行頭に別の角括弧が付く formatter では、行頭の選択肢を外して書く
- **鍵の文字の集まり**: Rails が `X-Request-Id` から通す文字は英数字・`_`・`-`・`@`。見本はこれを全部受ける (本文の例は `_` と `@` が抜けていた)。
  記号だけの値を送ると request_id のタグ自体が付かないので、タグの無い最初の行の数を数えて報告に出す
- **余白は後ろだけ**: 6 節の「前後に広げる」をやめた。最初の行が範囲に無いリクエストは最初の行の数が 0 でどの件数にも入らず、前に広げると前の日の集計を一部だけの値で置き換える
- **範囲を分ける境目**は最初の行の時刻の区切りに揃う所だけ。日次の集計は 1 日より細かく分けない
- **request_id の数は概数にしない**: 2 段目の `count(*)` (1 段目の結果の行数) で数える。`count_distinct` は使わない
- 同じ項目を 2 つの行の種類が取り出すことはできない。`set` で補えるのは `status` だけ

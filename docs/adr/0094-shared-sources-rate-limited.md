# 0094. 人の多い送信元 (`shared_sources`) を allowlist に置いて別のしきい値で見、429 の集まった IP を、同じ IP からログインできた利用者の数を添えて報告する (`rate_limited_ip`)

- 日付: 2026-11-28
- 状態: 採用 (2026-11-28、ユーザーの判断)

## 背景

### 守りたいこと

アプリにログインの回数の制限 (rack-attack など) を入れ、数える場所を共通の Redis にすると、IP ごとの制限は全タスクの合計で効く。
学校・試験の会場・社内の回線のように、NAT の内側の多くの人が 1 つの IP から一斉にログイン・申し込みをする場面では、正しい利用者に 429 が返りうる。
アプリの側は上限を上げて合わせるが、上げすぎると総当たりに甘くなる。どの送信元が「多くて当たり前」かを、ログから判断する材料が要る。

逆に、arata の側にも同じ問題がある。人の多い送信元からのログインの失敗は、1 つの IP に集まるので `login_bruteforce` の平常帯を超えやすい。
今の逃げ道は allowlist の `source_ips` だけで、これは丸ごと外す (その回線からの本当の攻撃も見えなくなる)。

### 今の arata で見えること・見えないこと (main を読んで確かめた)

- `login_bruteforce` は、http_access の sign-in の送信先・メソッド・失敗のステータス (`failure_statuses`) で、IP ごとの日の件数を数える (`sign_in_failures`)。
  失敗を 200 で返すアプリでは、数えるのは 200 だけになり、**429 はどの検出でも数えていない**
- ALB のアクセスログ (`alb_access`) の status には、アプリが返した 429 も残る。数える材料はある
- allowlist の `source_ips` の IP は、`login_bruteforce`・`probe_paths` の対象から外れる (`SourceIPAllowed`)。外すか外さないかの 2 つだけで、別のしきい値は無い
- request_lines のソースで `request.user_id` を読む設定 (ADR 0052) では、ログインした利用者の ID と、そのリクエストの IP (最初の行の `ip`) が同じ行の組で取れる。
  利用者ごとの 3 つのチェック (ADR 0071・0087) は利用者の軸で数え、IP の軸の数は持っていない
- IP の素性 (どの事業者・国・組織か) を引く仕組みは無い。AWS の IP の範囲の同梱は ADR 0091 (提案) で決めている

### 判別に使えるもの

「学校の回線」と「クラウドからの総当たり」を、通知を見ただけで分けたい。候補を比べる:

- **逆引きのドメイン名 (PTR)**: 逆引きの名前は IP の持ち主が自由に書ける。攻撃者は自分の IP に学校らしい名前を付けられるので、判別の根拠にならない。
  正引きで同じ IP に戻るか (forward-confirmed) を確かめても、持ち主の自己申告であることは変わらない。引けば、相手の DNS に「調べられた」ことも伝わりうる
- **同じ IP からログインできた利用者の数**: 学校なら、429 と同時に、ログインに成功した利用者が何十人もいる。総当たりなら、失敗と 429 ばかりで、ログインできた利用者はほとんどいない。
  アプリのログから arata が数えるので、送信元が偽れない (偽るには、正規の利用者として多数ログインする必要がある)
- **AS 番号・組織名・国・クラウドの事業者**: 公開のデータから引ける。持ち主の自己申告ではない (RIR の割り当て、事業者が公開する範囲の一覧)。
  クラウドの事業者の範囲は、学校・会場の回線ではありえないことの強い材料になる

## 決定

### 1. 人の多い送信元を allowlist に置く (`shared_sources`)

```yaml
shared_sources:                  # NAT の内側に多くの利用者がいる送信元 (学校・会場・社内の回線)。外すのではなく、別のしきい値で見る
  - cidr: 198.51.100.0/24
    note: 試験の会場 (2026-12 の試験の日だけ)
    approved_by: alice
    approved_at: 2026-11-28
    expires: 2026-12-20          # 任意。過ぎたら普通の送信元に戻る (allowlist の今の期限の扱いと同じ)
```

- 置き場所は allowlist にする。承認者・承認の日・期限の記録の仕組みがあり、「既知の送信元」の判断は allowlist に集める今の決まりに合わせる
- `source_ips` とは分ける。`source_ips` は丸ごと外す (自社の拠点など)。`shared_sources` は外さず、しきい値を上げて見る。両方に当たる IP は `source_ips` を優先する (外す)
- 効く検出:
  - `login_bruteforce`: `shared_sources` の IP は、平常帯の下限を `checks.login_bruteforce.shared_min_count` (既定は `min_count` の 5 倍) にする。
    「その日の最多 IP が初出」(`new_top_ip`) は報告しない (試験の日に初めて最多になるのは当たり前)
  - `rate_limited_ip` (下の 2): 下限を `shared_min_count` にする
  - `endpoint_abuse` には効かせない。endpoint_abuse の下限は、時間幅の中の**全 IP の件数の和**と**異なり IP の数**で、1 つの IP のしきい値を持たない (1 つの IP を上げる意味が無い)
- `config check` は CIDR の形・`source_ips` との重なり (warn)・期限切れ (warn) を確かめる

### 2. 429 の集まった IP を報告する (`rate_limited_ip`。daily、event、low)

- 集計: http_access のソースで、IP ごとの日の件数のうち、ステータスが `checks.rate_limited_ip.statuses` (既定 `[429]`) のもの (`rate_limited`、key = ip)。
  `paths` (接頭辞。空なら全パス) で絞れる。ADR 0031 に合わせ、新しいクエリを足さず、`sign_in_failures`・`probe_hits` のクエリ (http_hits) の条件に 3 つ目の選択肢として足す
- 判断の材料: **同じ IP からログインできた利用者の数** (`ip_users`、key = ip)。
  - request_lines のソースで `request.user_id` を読み、`checks.rate_limited_ip.user_sources` に書いたソースだけ (書かなければ数えず、材料に添えない)。
  - 数えるのは代わりにログインした操作 (`by`) を除いた、ログインした本人のリクエスト。(日, IP) ごとの異なる利用者の数で、利用者の ID は Insights の中で数えるだけに使い、結果に出さない (ADR 0071 と同じ)
  - ストアに残すのは、値が `ip_users_store_min` (既定 3) 以上の IP を、日ごとに多い順に `ip_users_store_top` (既定 200) まで。
    429 の無い IP も残す (人の多い送信元を、429 が出る前に見つける材料になる。下の「確かめが要る点」)
  - クエリは U1・U2 と別の 1 本 (U3)。利用者の軸の U1 に IP の軸を足すと、行が (利用者 × IP × 型) に増える
- 判定: その日の `rate_limited` が下限 (`min_count`、既定 20。`shared_sources` の IP は `shared_min_count`、既定 200) 以上の IP を low で報告する。
  平常帯は持たない (429 はアプリの制限そのものの結果で、「ふだんより多い」より「この日にこれだけ止めた」が判断の単位)
- 報告の中身 (`data`): IP、429 の件数、その日の `ip_users` (数えたときだけ)、その日の `sign_in_failures`、`shared_sources` に当たるか (と note)、IP の素性 (3 が入れば)。
  理由 (`reasons`):
  - `suggest_shared`: `shared_sources` に無く、`ip_users` が `suggest_min_users` (既定 10) 以上。「`shared_sources` に足す候補」(アプリの上限も見直す候補)
  - `few_users`: `ip_users` を数えていて、`suggest_min_users` 未満。総当たり・機械的な送信の疑い。`login_bruteforce` の指摘と並べて読む
  - `shared_heavy`: `shared_sources` の IP で `shared_min_count` を超えた。正しい利用者が止められている疑い (アプリの上限の見直しの材料)
  - 理由が付かない (`ip_users` を数えていない) ときは、件数だけを報告する
- 通知に IP はそのまま出す (今の `login_bruteforce` と同じ。通知の先は利用者自身の Slack)
- playbook (`docs/ai/playbooks/rate_limited_ip.md`) と攻撃の事例の対応表を書く (ADR 0025・0058)

### 3. IP の素性を添える (段階を分ける)

- (a) **クラウドの事業者か**: ADR 0091 の AWS の範囲の同梱に、範囲の一覧を公開している事業者 (GCP・Azure など) を足し、`rate_limited_ip`・`login_bruteforce` の `data` に事業者の名前を添える。
  同梱するのでオフラインで引け、IP を外に送らない。一覧の出どころ・版の固定・更新は ADR 0091 の決め方に合わせ、実装の前に別の ADR (か 0091 の改訂の ADR) で決める
- (b) **国と AS 番号・組織名**: 公開のデータ (RIR の割り当ての一覧、IP と ASN の対応表) を版を固定して同梱する。データの出どころ・ライセンス・大きさ・更新の方法は、実装の前に別の ADR で決める
- (c) **逆引きのドメイン名 (PTR)**: 既定では引かない (背景の「判別に使えるもの」)。要るとはっきりしてから、設定で明示したときだけ、正引きで確かめた名前を「参考」として出す形で別に決める

### 順番

ADR (この文書) → 2 (`rate_limited_ip` と `ip_users`) → 1 (`shared_sources`) → 3 (a) → 3 (b)。3 (c) は保留。

## 検討した選択肢

- **`source_ips` に `shared: true` を足す**: 却下。`source_ips` は主体の送信元 (principal_new_source など、AWS の主体の拠点) と同じ一覧で、外すのが意味。
  アプリの利用者の NAT とは見る検出も意味も違い、1 つの項目に 2 つの意味を持たせると読み違える
- **`shared_sources` を checks の設定 (`arata.yaml`) に置く**: 却下。承認者・期限の仕組みが無く、送信元の判断が 2 か所に分かれる (`waf_review.trusted_cidrs` は WAF の集計条件で、性質が違うので今のまま)
- **`shared_sources` の IP を丸ごと外す**: 却下。学校の回線からの総当たり (乗っ取った端末、内部の利用者) も見えなくなる。しきい値を上げるだけにする
- **429 に平常帯を持たせる**: 却下。429 はアプリの制限が働いた結果で、ふだんの量より「その日どれだけ止めたか、それが誰か」が判断の単位。平常帯にすると、毎日 429 を受ける学校が「ふだんどおり」で消える
- **判別に逆引きのドメイン名を使う**: 却下 (既定)。持ち主の自己申告で偽れ、引くと相手に伝わりうる。ログインできた利用者の数と組織名のほうが確か
- **IP の素性を外部の API で引く**: 却下。IP を外の事業者に送ることになり (顧客の利用者の IP)、API の可用性と鍵の管理も増える。同梱のデータで引く

## 結果

- 良い点:
  - 「この送信元を例外にすべきか」の候補が、ログインできた利用者の数という偽りにくい材料付きで出る。アプリの上限の見直しにも使える
  - 人の多い送信元を丸ごと外さずに済み、その回線からの総当たりも高いしきい値で見え続ける
  - IP の素性はオフラインで引き、利用者の IP を外に出さない
- 引き受けるコスト:
  - U3 の分、Logs Insights の読み取りが request_lines のソースで 1 日 1 本増える (数 MB/日のソースなら小さい。doctor の費用の行に入れる)
  - `ip_users` で、ストアに IP を key とする日の値が増える (`sign_in_failures` と同じ扱い。保持の期間に従う)
  - allowlist の項目の種類が 1 つ増える (`approve` で足す手順・`config check`・`arata help ai` の文書)
- 確かめが要る点 (実装の PR で確かめる):
  - request_lines の最初の行の `ip` が、ALB のログの client の IP と同じ値か (Rails の `remote_ip` が信頼するプロキシの設定次第で、ALB の内側の IP になりうる)。
    違えば `ip_users` は 429 の IP と突き合わせられない。doctor に「`ip_users` の上位の IP が、http_access の IP に現れる割合」の行を出して確かめる
  - rack-attack が返す 429 が、アプリのログ (request_lines) に `Completed 429` として残るか (ミドルウェアの順による)。この ADR では 429 を ALB のログで数えるので、残らなくてもよい
  - 既定のしきい値 (`min_count` 20・`shared_min_count` 200・`suggest_min_users` 10) は仮の値。実データで見直す

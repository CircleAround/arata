# endpoint_abuse: 画面への分散した集中と連鎖

## この指摘の意味

アプリのログで、設定した画面 (`checks.endpoint_abuse.endpoints`。会員登録・メッセージ送信・ログイン・モバイルアプリの API など) への
リクエストが、短い時間幅 (`window`、既定 10 分) の中でふだんより多くの IP から集中した、または「A の画面に来た IP がすぐ B の画面に来た」
連鎖 (`follow_ups`) が、ふだんより多かった (daily)。使い捨てのメールアドレスでの連続登録や、登録の直後にスパム・フィッシングのメッセージを送る流れの兆候。
**事実 (件数・異なり IP・同じ UA の広がり・ふだんの上限) の報告であり、遮断の提案ではない。**

- Key は画面の名前 (`signup` など)、連鎖は `<from>><to>` (`signup>message` など)。重大度は medium まで
- 理由 (`reasons`): `distributed_burst` 異なり IP 数が下限 (`min_distinct_ips`) 以上かつ平常帯 × factor 超え (medium) /
  `volume` 件数が下限 (`min_count`) 以上かつ平常帯 × factor 超え (low) / `same_user_agent` 同じ UA がふだんより多くの IP にまたがった (根拠に添えるだけ) /
  `follow_up` 連鎖した IP 数が下限 (`min_ips`) 以上かつ平常帯 × factor 超え (medium)
- data: `bin_start`・`bin_end` (最も IP の多い幅、UTC)、`count`、`distinct_ips`、`baseline_p99_ips`・`baseline_p99_count` (ふだんの上限 = 過去の幅の p99)、
  `ua_hash`・`ua_ips` (UA はハッシュの先頭 8 文字だけ。原文は保存しない)、`bins` (超えた幅、最大 10)、`baseline_used` (false なら平常帯が未確立で絶対の閾値だけで判定)
- IP の一覧は保存しない (件数だけ)。login_bruteforce は「IP ごとの sign-in の失敗」、こちらは「画面全体への分散した集中」を見るので、ログインの画面に両方を使ってよい

## まず確かめること

1. `arata review --format json` で同じ日の login_bruteforce・probe_paths・waf_block_trend を探す。同じ時間帯ならまとめて扱う
2. `baseline_used` が false なら導入直後。`min_distinct_ips`・`min_count` だけで判定しているので、キャンペーン・告知・メールの配信の直後の正規の集中でないかを先に確かめる
3. その幅のアプリの記録 (アプリの管理画面・DB) で、登録・送信されたものを確かめる: 使い捨てのメールのドメイン、似た名前の連番、同じ文面、
   登録の直後の送信。利用者の特定と確認はアプリの運営者が行い、レポートや通知に個人を書かない
4. ログで時間幅と画面に絞って IP と UA を確かめる (Insights はスキャン量で課金されるので期間を `bin_start`〜`bin_end` に絞る)。
   例 `fields @timestamp, @message | filter @message like "POST /signup" | sort @timestamp asc | limit 200`
5. `ua_ips` が大きいとき: 一般的なブラウザの UA も多くの IP にまたがる。平常帯 (`baseline_p99_ua_ips`) と比べて、ふだんより明らかに多いかを見る

## 判断の分かれ目

- **正規の可能性が高い**: 告知・メール配信・広告の直後、同じ社内の回線からの研修・試験、外部の監視。登録・送信の内容に不自然さが無い
- **要確認**: 使い捨てのメールのドメイン・連番の名前が多い、同じ UA が多くの IP にまたがる、登録の直後のメッセージ送信 (`follow_up`) が重なる
- 1 件ずつ別の IP からの登録は、IP ごとの連打 (login_bruteforce・WAF のレートベースのルール) では拾えない。件数が少なくても内容を確かめる価値がある

## 対処の選択肢

**止めることを勧めない。** 確認と保留の運用へつなぐ。変更は人が判断して実行する。LLM は提案まで。

1. **確認・保留**: その時間幅に登録されたアカウント・送られたメッセージを、アプリの運営者が確認する (公開・送信の保留、運営の承認待ちの運用があればそこへ回す)
2. **承認**: 対象外 (主体の承認ではない)。IP ごとの判定ではないので allowlist の `source_ips` は効かない。正規の集中が繰り返すなら閾値の見直しを人に提案する
3. **expected_denied**: 対象外
4. **ack / snooze**: 告知などで説明がつく集中は ack
5. **設定の修正**: 平常帯が高すぎ / 低すぎるなら `min_distinct_ips`・`min_count`・`factor` を見直す。アプリ側の登録の確認 (メールの確認・電話の確認) の強化を運営者と相談する

## やってはいけないこと

- メールアドレス・利用者名・メッセージの本文を要約や通知に書かない (件数と画面の名前だけ)
- 多数の IP をまとめて拒否する・登録を一律に止めることを勧めない (正規の利用者を止める。利用者の方針は「拒否せず保留して確認」であり得る)
- UA のハッシュから原文を推測して書かない

# user_denied: ログインした利用者の拒否の急増

## この指摘の意味

アプリのログ (`format: request_lines` でユーザー ID を読むソース) で、1 人のログインした利用者への拒否 (`checks.user_denied.statuses`、既定 401・403) が、
1 日 (または直近 `window` 日) にふだんより多かった (daily)。権限の無い画面や操作を試して回る動き (認可の抜け漏れの探り) の兆候。
**事実 (拒否の件数と平常帯) の報告であり、遮断の提案ではない。**

- Key は利用者 (`<kind>:<id>`。例 `user:42`)。重大度は medium
- 理由 (`reasons`): `above_app_band` アプリの平常帯 (ふだんの日の、いちばん多い利用者の値の中央値 × `app_factor`) を超えた / `above_user_band` 本人の平常帯も超えた /
  `new_user` 本人の平常帯が無い (新しい利用者。アプリの帯と下限 `min_count` だけで判定) / `window` 直近 `window` 日の和で超えた (ゆっくりした試し)
- data: `user` (`kind`・`id`)、`day` (UTC)、`value` (その日の件数)、`app_band`、`user_band`、`window` (`days`・`sum`・`days_with_value`・`app_band`・`user_band`)、`related`
- 3xx は数えない (送信の後の転送とログから見分けられない)。404 も既定では数えない (リンク切れ・古いブックマークで日常的に出る)。拒否を 404 で返すアプリは `statuses` に足せる
- 代わりにログインした操作 (`by` の付いた要求) は数えない

## まず確かめること

1. `related` と、同じ利用者の `user_id_enumeration`・`user_path_breadth` を `arata review --format json` で見る。束で出ていれば同じ試しとして扱う
2. 原本の Insights で、その日・その利用者の要求を引き、どの画面・操作が拒否されたかを見る (期間は `day` の 1 日に絞る):
   `fields @message | filter @message like "actor kind=user id=42" | parse @message /\[(?<rid>[A-Za-z0-9_@-]+)\]/ | stats count(*) by rid | limit 1000` で request_id を集め、
   `fields @timestamp, @message | filter @message like "<request_id>"` で Started・Completed の行を見る
3. 拒否が 1 つの画面に集中しているか (壊れた画面・期限切れのセッションの再試行など、利用者のせいでない拒否) を見る。多くの画面・管理画面に広がっていれば試しの形
4. `new_user` なら、アカウントを作った時刻と最初の拒否が近いかをアプリの記録で確かめる (作ったばかりのアカウントで試すのが典型)

## 判断の分かれ目

- **正規の可能性が高い**: 1 つの画面に集中した拒否 (画面の不具合・権限の設定の誤り)、セッションの切れた端末の自動の再試行、権限を変えた直後の利用者
- **要確認**: 多くの画面・管理画面への拒否、作ったばかりの利用者、何日にも分けた試し (`window`)、同じ日の `user_id_enumeration`・`user_path_breadth`

## 対処の選択肢

**止めることを勧めない。** 確認と保留の運用へつなぐ。変更は人が判断して実行する。LLM は提案まで。

1. **確認**: 拒否された画面と操作を、アプリの運営者が確かめる。画面の不具合ならアプリの開発者に回す
2. **承認**: 対象外 (主体の承認ではない)。正規の利用者が繰り返し出るなら閾値の見直しを人に提案する
3. **expected_denied**: 対象外 (CloudTrail の拒否の設定)
4. **片付け**: 下の「片付け」の節
5. **設定の修正**: `min_count`・`factor`・`app_factor`・`window` (どれも仮の値。実データで見直す)

## 片付け

| 重大度 | 上がる余地 | 許す操作 |
|---|---|---|
| medium | なし | snooze・resolve |

上がる余地は、同じ Key のまま、より重い重大度で観測されうるか。ack を許すのは余地のある行だけ (ack 中に出直すのは重大度が上がったときだけ)。このチェックは event 型 (観測されなくても解消にならない)。

- resolve: 説明のついた拒否 (画面の不具合・権限の変更)
- snooze: アプリの側の確認・修正が終わるまで
- 表で許さない ack は arata が止める (`ACK_REFUSED`)。終わった出来事だと確かめたうえでどうしても ack するなら、人が `--force --reason "<理由>"` を付ける (記録に force が残り、週次の報告に出る)。LLM は `--force` を提案しない

## やってはいけないこと

- 利用者の氏名・メールアドレス・画面の中身を要約や通知に書かない (利用者は `<kind>:<id>`、件数だけ)
- 利用者のアカウントを止める・利用者に連絡することを LLM が決めない (アプリの運営者が判断する)

## 関連する事例

公開の事例で、このチェックが当たる段階 (一覧と読み方は `arata help ai threats`)。指摘がその攻撃だと断定する材料ではない。

- `arata help ai threats artex-2026-10`: エージェントが `200` / `403` の応答で開けるパスを探す段階。出典はログインの有無を書いていない。ログインした利用者の操作なら、拒否の多さをこのチェックが見る

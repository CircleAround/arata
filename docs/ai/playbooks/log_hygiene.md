# log_hygiene: アプリのログに残った「載せるべきでない値」

## この指摘の意味

アプリのログ (CloudWatch Logs) に、載せるべきでない値の**形**をした行がある (weekly、状態型)。arata が持つのは種類ごとの**行数だけ**で、
値もサンプルの行も引かない。どの行かは arata では分からない (探し方は下)。

- Key は `<ソースの id>|<種類>` (ロググループ × 種類で 1 件)。種類と重大度:
  - `secret_aws_access_key` (high): 長期のアクセスキーの ID の形 (`AKIA` + 16 字)。署名付き URL の中のものは除く
  - `secret_slack_token` (high): Slack のトークンの形 (`xoxb-` などの接頭辞)
  - `secret_private_key` (high): PEM の秘密鍵の先頭の行
  - `presigned_url_long_term_key` (medium): 長期のアクセスキーで署名した S3 の署名付き URL (`X-Amz-Credential=AKIA…`)
  - `presigned_url` (medium): それ以外の署名付き URL (`X-Amz-Signature=`)
  - `unfiltered_param` (medium): 設定の `param_fields` に書いた送信項目が、`"<項目>"=>"<値>"` か `"<項目>":"<値>"` の形で、隠されずに残っている
  - `debug_sql` (low): 実行時間の付いた SQL の文 (本番での debug の出力)
- data: `log_group`、`kind`、`count` (行数。1 行に複数あっても 1)、`retention` (`set` / `never` = 無期限 / `unknown`) と `retention_days` (`set` のときだけ)、
  `fields` (`unfiltered_param` だけ。項目名 → 行数)、`window_hours` (見た範囲)
- **解消は「直近 7 日のログに無い」という意味で、古い行が消えたという意味ではない。** 直した週は窓に直す前の行が残るので、解消はその次の週になる。
  古い行は保持期間が過ぎるまで (無期限なら消すまで) 読める。秘密の値は、解消しても無効化が済むまで終わりではない
- **0 件でも「ログに個人情報が無い」ことにはならない。** 拾うのは形の決まったものだけ (自由文の住所・本文、設定に書いていない項目名、値が `[` で始まる項目は数えない)。
  導入より前の行 (窓より前) も出ない
- 収集に失敗した週 (権限・`max_scan_gb` の超過・タイムアウト) は前回の指摘を維持する (coverage の `sources_failed` に出る。直ったとは限らない)

## まず確かめること

1. `arata review --format json` で、同じロググループの他の種類と、credential_hygiene・secret_access・principal_new_source を探す
   (ログに出たキーが使われていないか。キーの廃止は credential_hygiene の対処とつながる)
2. `kind`・`count`・`retention` を見る。秘密の値 (high) は 1 行でも対処する。保持期間が長い・無期限なら、古い行の扱い (下の 6) も決める
3. **場所を探す** (ログを読む権限のある人が、自分のコンソールで行う)。値を画面に出さず、時刻とログストリームだけを返す:

   ```
   filter @message like /"(name|tel)"\s*(=>|:)\s*"[^"\[]/
   | display @timestamp, @logStream
   | sort @timestamp desc
   | limit 20
   ```

   `filter` の条件は種類で変える: 項目は上の形 (名前を `fields` の項目に)、キー ID は `/AKIA[A-Z0-9]{16}/`、Slack は `/xox[abeprs]-/`、秘密鍵は `/PRIVATE KEY-----/`、
   署名付き URL は `/X-Amz-Signature=/`、SQL は `/ms\)\s+(SELECT|INSERT|UPDATE|DELETE) /`。arata が流すクエリそのものは `arata doctor` が構文を確かめている
4. 時刻とログストリームから、出力元 (どのアプリのどの処理・どのデプロイから) を突き止める。`unfiltered_param` は `fields` の項目名から送信元の画面が分かる
5. 秘密の値: そのキー・トークンが今も有効か、何に届くかを持ち主に確かめる (キー ID は `aws iam list-access-keys`、最終使用は `aws iam get-access-key-last-used`)
6. ログを読める主体と、複製の先を確かめる: `aws logs describe-subscription-filters --log-group-name <ロググループ>`、`aws logs describe-export-tasks`、
   ロググループを読める IAM の主体

## 判断の分かれ目

- **急がなくてよい**: `debug_sql` だけ (それ自体は漏えいではない。ただし値が SQL に入り、他の種類を増やす原因になる)。
  期限の短い署名付き URL で、ログを読める人が元から対象のオブジェクトを読める
- **誤検知のことがある**: `name` などの項目が個人情報でない (商品名など)。テスト用の値・文書の例の文字列。キー ID だけの行 (シークレットが並んでいない)。
  どれも、場所を探して確かめてから判断する (値を見ずに誤検知と決めない)
- **要対応**: 秘密の値 (high)。漏れたものとして扱う。長期のキーで署名した URL (期限が最長 7 日で、キー ID が残る)。個人情報の項目が隠されていない。
  保持期間が無期限で、ログを読める範囲が広い・外部へ転送している

## 対処の選択肢

緊急度の順。封じ込めと設定の変更は**人が判断して実行する**。LLM は提案まで。

1. **封じ込め (秘密の値)**: 先に無効化と作り直し (アクセスキーの無効化・削除、Slack のトークンの失効、鍵の差し替え)。次にそのキーの利用を CloudTrail で確かめ、
   最後に出力元 (環境変数や設定を丸ごと書き出す処理) を直す。順番を逆にしない
2. **隠されていない項目**: Rails なら `config.filter_parameters` に項目を足す。足した次の次の週に解消する (足した週は窓に前の行が残る)
3. **署名付き URL**: URL をログに出さない (クエリ文字列を落として書く、オブジェクトのキーだけを書く)。期限を短くする。
   長期のキーでの署名は、ロール (一時的な認証情報) での署名へ移し、キーを廃止する
4. **本番の debug**: 本番のログレベルを info 以上にする
5. **承認 / expected_denied**: 対象外
6. **残った行**: 保持期間を決める (無期限をやめる)。必要なら、値の残るログストリームを利用者が消す。ログを読める主体と、転送先 (サブスクリプションフィルター・エクスポート) の複製も見直す
7. **入口で伏せる**: CloudWatch Logs のデータ保護ポリシー (取り込みの時点で決まった形の値を伏せる。利用者が設定する書き込みで、取り込み量に費用がかかる) を検討する
8. **ack / snooze・誤検知**: 確かめたうえで理由を付けて ack する (種類ごと。`unfiltered_param` は別の項目が当たり始めたら changed で出直す)。
   個人情報でない項目は、ack より設定の `param_fields` から外す・より限定した項目名にするほうがよい (理由が設定の履歴に残る)。対処の予定が決まっていれば snooze

## やってはいけないこと

- LLM のエージェントが、値を表示するクエリ (`@message` を返すもの) を流さない。場所を探すのは権限のある人で、値を会話・通知・Issue・PR に写さない
- 「解消した」を「ログから消えた」と読まない。秘密の値は無効化が済むまで終わりにしない
- 0 件を「個人情報がログに無い」ことの証明として報告しない
- キー ID だけだからと、確かめずに ack を勧めない (同じ行にシークレットが並ぶことが多く、arata は値を見ていない)
- LLM がキーの無効化・ログの削除・保持期間の変更・ack を実行しない

# artex-2026-10: LLM のエージェントが、盗んだ資格情報で攻撃の後の段を自動で進める (ARTEX とその同類)

## 概要

- 公開日: 2026-10-31 (日本語版は 2026-11-02)
- Go で書かれた、LLM で動く自律型のマルチエージェントのペンテスト兼攻撃用の C2 (ARTEX) と、その同類のフレームワーク (Hexstrike、CAIRN、PentAGI など) が、
  2026 年 8 月下旬以降に攻撃で使われているという、Google Threat Intelligence Group と Mandiant の報告
- エージェントは、偵察・足場の確立・権限の昇格・内部の偵察・横の移動・居座り・目的の達成 (持ち出しの準備など) を自律的に進める。
  出典は、複数の事例で「攻撃者は標的組織の盗まれた認証情報を ARTEX に与え、攻撃ライフサイクルの後続フェーズを実行するよう命令していました」と書く
- 防御として、ID とワークロードごとの行動の平常帯、認証の送信元の変化 (パターンから外れた成功した認証)、制御面の速さ (管理 API の呼び出し・権限の試し・資源の列挙のバースト) の検知を勧める

## 攻撃の段階と arata で見えるもの

| 攻撃の段階 | 出典の書き方 | arata のチェック | 記録 | 出るもの |
|---|---|---|---|---|
| 初期の偵察: 500 回以上の Web のリクエストで、ディレクトリのファイル名や拡張子を試し、`200` / `403` で開けるものを探す | 観測 | `probe_paths` | アクセスログ (http_access): 探索パス (`probe_paths.paths`) への 403 / 404 | 設定した探索パスへの 403 / 404 が IP ごとの平常帯を超えれば low。**それ以外のパスへの試しと、開けた (200) ものは数えない** |
| 盗んだ資格情報を与えられたエージェントが、AWS で動き始める | 観測 | `principal_new_source` | CloudTrail: その主体の API 呼び出し | 既知の主体が、ふだん使わない送信元 (/24・/48) から使われれば low。新しい送信元からの成功した書き込みが下限以上なら medium |
| 権限の確認: 盗んだ IAM ユーザーの権限を `DryRun` とプレースホルダーの ID で試す (EC2・EBS・スナップショット。23 秒に 27 件のイベント) | 観測 | `access_denied` | CloudTrail: 拒否された呼び出し (`Client.UnauthorizedOperation` など、`error_codes` のもの) | 拒否された API の種類が下限 (既定 5) 以上か、主体の平常帯を超えれば medium か high。**許された `DryRun` は拒否でない (権限がある) ので数えない** |
| 権限の昇格・居座り: 書き込める admin の印を見つけ、`is_admin=true` のアカウントを作る | 観測 | — | (アプリの中の操作) | 見えない。対象のアプリは出典に書いていない。AWS の記録には残らない |

## arata では見えないもの

- **ログインした利用者の中の、パスや ID の総当たりと、その中の成功**: 出典は、エージェントが他の利用者のファイルを読もうとしたことや、Web のパスを総当たりしたことを書く。
  arata のアプリ層のチェックは、決まった探索パスへの 403 / 404 (`probe_paths`) と、設定した画面への集中 (`endpoint_abuse`) だけを数え、利用者ごとの試しや、その中の 200 は見ない
- **許された権限の試し**: `DryRun` が許された呼び出し (権限がある操作) は拒否でないので、`access_denied` に数えない。制御面の速さ (短い時間の API の集中) を主体ごとに見るチェックは無い
- **アプリの中のアカウントの作成と admin の印**: アプリのデータベースの操作で、CloudTrail にもアクセスログにも残らない
- **盗んだ資格情報が、ふだんと同じ送信元の帯から使われた場合**: `principal_new_source` は /24 (IPv6 は /48) の単位で見る
- 出典の Azure・Kerberos・データベースの段階 (arata は AWS の記録だけを読む)

## 予定している改善

- 予定 (まだ決めていない): ログインした利用者ごとの、パスや ID の試しの数と、その中の成功を数えるチェック。アプリのログの利用者 ID (ADR 0051・0052) を使う形になる

# artex-2026-10: LLM のエージェントが、盗んだ資格情報で攻撃の後の段を自動で進める (ARTEX とその同類)

## 概要

- 公開日: 2026-10-31 (日本語版は 2026-11-02)
- Go で書かれた、LLM で動く自律型のマルチエージェントのペンテスト兼攻撃用の C2 (ARTEX) と、その同類のフレームワーク (Hexstrike、CAIRN、PentAGI など) が、
  2026 年 8 月下旬以降に攻撃で使われているという、Google Threat Intelligence Group と Mandiant の報告
- エージェントは、偵察・足場の確立・権限の昇格・内部の偵察・横の移動・居座り・目的の達成 (持ち出しの準備など) を自律的に進める。
  出典は、複数の事例で「攻撃者は標的組織の盗まれた認証情報を ARTEX に与え、攻撃ライフサイクルの後続フェーズを実行するよう命令していました」と書く
- 防御として、ID とワークロードごとの行動の平常帯、認証の送信元の変化 (パターンから外れた成功した認証)、制御面の速さ (管理 API の呼び出し・権限の試し・資源の列挙のバースト) の検知を勧める
- Microsoft は、Storm-0940 が ARTEX を「偵察、パスワードスプレー、OAuth のアプリの悪用」に使ったと書く。同じ報告は、2026-10-10〜14 に 8 組織の 327 アカウントへの
  自動のパスワードスプレーで、失敗のログオンが 151,000 件以上 (10-11 のピークは毎分 2,900 件)、応答の約 98% がロックアウト、成功は観測されなかった、と書く
  (このスプレーを ARTEX によるものと明言した文は無い)
- AhnLab ASEC は、標的に記録されるのはエージェントの名前ではなく、ツールが実際に送ったリクエストとその後の実行だと書く。User-Agent は記録されないことも、
  攻撃者が変えることもできるので、特定の User-Agent だけを根拠に検知・遮断するのは難しいとする (`artex-selfupdate` は GitHub に送るリクエストで、標的のアクセスログには残らない)

## arata では見えないもの

- **ログインしていない状態での、パスや ID の総当たりの中の成功**: 利用者ごとの 3 つのチェック (`user_denied`・`user_id_enumeration`・`user_path_breadth`) は、ログインした利用者の要求だけを数える。
  ログインの前の試しは、決まった探索パスへの 403 / 404 (`probe_paths`) と、設定した画面への集中 (`endpoint_abuse`) だけで、その中の 200 は見ない。
  利用者ごとのチェックも、ユーザー ID の行を出すアプリ (`arata help ai user_id`) で、`sources` を書いたときだけ動く
- **許された権限の試し**: `DryRun` が許された呼び出し (権限がある操作) は拒否でないので、`access_denied` に数えない。制御面の速さ (短い時間の API の集中) を主体ごとに見るチェックは無い
- **アプリの中のアカウントの作成と admin の印**: アプリのデータベースの操作で、CloudTrail にもアクセスログにも残らない
- **盗んだ資格情報が、ふだんと同じ送信元の帯から使われた場合**: `principal_new_source` は /24 (IPv6 は /48) の単位で見る
- 出典の Azure・Kerberos・データベースの段階と、Microsoft 365 へのパスワードスプレー (arata は AWS の記録と自分のアプリのログだけを読む。
  自分のアプリのサインインの画面への同じ形の総当たりなら `login_bruteforce` が IP ごとの失敗を数えるが、この事例の出典にその段は無い)
- **ツールの印 (User-Agent など)**: arata は User-Agent の値を IOC として照合しない。出典も、User-Agent は変えられ、検知の根拠にしにくいと書く

## 予定している改善

- 予定 (まだ決めていない): 主体ごとに、短い時間の `DryRun` で「権限がある」と返った呼び出しの集中と、異なる API の種類の多さを見るチェック (出典の「23 秒に 27 件」の形)。
  EC2 の API は、権限があれば `DryRunOperation`、無ければ `UnauthorizedOperation` を返す (AWS の公式文書: https://docs.aws.amazon.com/AWSEC2/latest/APIReference/errors-overview.html)。
  CloudTrail の `errorCode` に `Client.DryRunOperation` として残ることは、AWS の公式文書では確かめられていない (AWS のブログの CloudTrail Lake のクエリには、その値が出てくる)。
  作る前に sandbox で記録の形を確かめる。今の arata は、拒否のコード (`access_denied.error_codes`) 以外のエラーの付いた呼び出しを events に残さないので、残す種類も足す
